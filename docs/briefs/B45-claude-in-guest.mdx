## Decisions you can make now

The issue bundles six sub-decisions. Items 4 and 5 wait on X01-model-credential in part or in full. You can settle the rest now.

| # | Sub-decision | Recommendation | Decide |
|---|---|---|---|
| 1 | Install and update | Install a signed, pinned Claude Code build in the image in a system directory that project users can't write to. Set `DISABLE_UPDATES` in the guest's managed settings. A new version arrives with `wb image build`. Never allowlist the download host. | now |
| 2 | Permission mode | `wb-guestd` writes `permissions.defaultMode: "bypassPermissions"` in the project user's settings. A user who wants prompts passes `--permission-mode` after `wb claude`, which reaches Claude Code unchanged and takes precedence over user settings. | now |
| 3 | User configuration | Option A below: an allowlist, minus the keys that run commands or hold secrets. | now |
| 4 | Commands that don't fit | `claude update` is refused by `DISABLE_UPDATES`. `/ide` can't reach a host editor (SEC05-default-deny) and the agent spec says so. `/login` waits for X01-model-credential. | partly |
| 5 | Telemetry and other endpoints | The *model API* profile lists only what Claude Code needs to work. The endpoint list waits for X01-model-credential, which lists them. | after X01-model-credential |
| 6 | Agent interface (V1-02-claude-only) | The agent spec defines the interface as what Claude Code needs (image install step, configuration carry-in rules, credential bindings, endpoint profile, launch environment), with Claude Code as its only implementation. No general design before a second agent exists. | now |

## Options for the user's configuration

The issue gives a proposal without alternatives, so these options are the brief's.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Carry in an allowlist, filtered

At each session start, `wb-hostd` copies `CLAUDE.md`, `agents/`, `skills/`, `commands/` and `settings.json` from `~/.claude/`. It removes the `hooks`, `env`, `apiKeyHelper` and MCP keys from the settings, leaves out plugins, and runs the image seal's secret scanner over the result. Anything left out is listed. The user can add hooks or MCP servers by name.

- **Cost:** a filter in `wb-hostd`, kept current with Claude Code's settings keys. A missed secret depends on the scanner, which is heuristic.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="caution" /> <Badge text="SEC03-no-host-exec" variant="success" /> <Badge text="FR01-drop-in" variant="success" />

</div>
<div class="wb-option">

### B. Start each project with an empty configuration

Each project user starts with an empty Claude Code configuration. The user sets it up inside the guest, and FR13-claude-state keeps it per project.

- **Cost:** no code. Each project starts without the user's `CLAUDE.md` and skills, so `wb claude` doesn't feel like `claude`.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" />
- **Weakens:** <Badge text="FR01-drop-in in practice" variant="caution" />

</div>
<div class="wb-option">

### C. Copy both files and the directory whole

Copy `~/.claude/` and `~/.claude.json` as they are.

- **Cost:** a copy. It puts the user's sign-in session, MCP server tokens and any token in a hook or `env` block into the guest.
- **Weakens:** <Badge text="SEC04-no-guest-secrets" variant="danger" />, a spec change, and not allowed by `AGENTS.md`.

</div>
</div>

<Aside type="note" title="Missing from the issue">
The issue proposes an allowlist of *files*. That isn't enough. One file, `settings.json`, can hold hooks, an `env` block with tokens in it, or an `apiKeyHelper` command. The filter has to remove those keys from inside the file. MCP server definitions and the sign-in session are not in `~/.claude/` at all but in `~/.claude.json`, which A never copies. Plugins can bundle their own hooks and MCP servers. A leaves them out by default. The copy goes one way only: configuration changed in the guest never returns to the host, because the guest controls it (SEC03-no-host-exec). Changes to a repository's own `.claude/` already return as flagged paths (S08-workspace-and-git).

Since Claude Code 2.1.283, its built-in starting mode is *auto*, where a classifier model reviews each action. On API accounts each check counts toward token use. Claude Code's documentation names `bypassPermissions` as the mode for isolated VMs. In the guest it runs as the project user, never as root.
</Aside>

## Evidence

- <Badge text="verified" variant="success" /> `~/.claude.json` holds "your sign-in session, MCP server configurations, per-project state such as trust decisions" ([Claude Code settings](https://code.claude.com/docs/en/settings)).
- <Badge text="verified" variant="success" /> Settings precedence is managed, command line, project local, shared project, user. A `--permission-mode` flag takes precedence over a mode set in user settings, and `bypassPermissions` takes effect from user, `--settings` or managed settings, not from project files (same page).
- <Badge text="verified" variant="success" /> `wb claude` passes its arguments to Claude Code unchanged (FR01-drop-in, S05-cli "Agent commands"), so the user's `--permission-mode` reaches it.
- <Badge text="verified" variant="success" /> Claude Code's documentation recommends `bypassPermissions` for "isolated containers and VMs only", and refuses it as root or under `sudo` ([permission modes](https://code.claude.com/docs/en/permission-modes)). Project users are never root (S13-guest-confinement, "Layer 1").
- <Badge text="verified" variant="success" /> Auto mode is the built-in starting mode from Claude Code 2.1.283. Its classifier checks count toward token use on API accounts (same page). `claude --version` on this host prints 2.1.289.
- <Badge text="verified" variant="success" /> `DISABLE_AUTOUPDATER` stops only the background check. `DISABLE_UPDATES` blocks every update path, `claude update` included ([advanced setup](https://code.claude.com/docs/en/setup), "Disable auto-updates").
- <Badge text="verified" variant="success" /> Each release has a GPG-signed `manifest.json` with a SHA-256 checksum per binary, and the macOS binary is signed by Anthropic and notarized (same page, "Binary integrity"). The native installer puts versions under the user's home, so a per-machine install in the image needs another route.
- <Badge text="verified" variant="success" /> `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` turns off updates, telemetry and error reporting, and also feature-flag fetching, which some features need ([environment variables](https://code.claude.com/docs/en/env-vars)).
- <Badge text="verified" variant="success" /> The image seal scans for secrets and fails the build on a find (S06-vm-lifecycle, "Images"). The guest environment is built from an allowlist (S09-policy-credentials-audit, "Never in the guest").
- <Badge text="inferred" variant="note" /> With the download host not allowlisted, a guest that turns updates back on can't download a new binary (SEC05-default-deny). `DISABLE_UPDATES` stops the attempt and its error messages. It isn't the control.
- <Badge text="assumed" variant="caution" /> That the image seal's scanner catches the tokens users put in `CLAUDE.md`, skills, and agent files. The scanner isn't written yet. The implementation of the seal (V1-M2-walking-skeleton) should test it on real `~/.claude/` directories.
- <Badge text="assumed" variant="caution" /> That Claude Code works with a placeholder credential, and which login Wraith Box owns. That is X01-model-credential (I15).

<details>
<summary>Details and glossary</summary>

**Why carry-in is per session.** The user edits `~/.claude/` on the host between sessions. Copying at session start keeps the guest current. The copy is small, so it shouldn't move NFR01-startup, but the implementation should measure it.

**Why the user's own hooks stay out.** Hooks are commands Claude Code runs at points in a session. On the host they run as the user. Carried into the guest they would run as the project user, with any token they hold now in the guest. Some hooks only make sense on the host (desktop notifications, editor integration). A user who wants one in the guest lists it by name.

**Version skew.** The host's Claude Code and the guest's can differ. Only configuration files cross, and Claude Code ignores keys it doesn't know, so an older guest build with a newer host configuration is expected to work. The agent spec should say what `wb` prints when it doesn't.

**Glossary**

- **Permission mode:** how Claude Code decides whether to ask before acting. `bypassPermissions` never asks. *auto* asks a classifier model. The default mode asks the user.
- **Managed settings:** a settings file in a system directory that takes precedence over every user and project setting. Guest root can change it. In the guest it sets defaults and doesn't enforce anything.
- **Hook:** a command Claude Code runs on an event, configured in settings.
- **MCP server:** a tool server Claude Code connects to. Its definition can hold API keys in its environment.
- **Plugin:** a bundle of skills, agents, hooks and MCP servers installed from a marketplace.
- **Placeholder credential:** a fake token in the guest that `wb-proxyd` replaces with the real one on the host side (SEC04-no-guest-secrets).
- **Image seal:** the scan for secrets that runs before an image can be used (S06-vm-lifecycle).

</details>

---
title: Can the dependency gate refuse young packages without breaking installs?
description: Yes, with conditions. Hide too-young versions from registry metadata so installers pick older ones, keep refusing too-young downloads, use the checksum database as Go's clock, and leave Homebrew ungated.
---

**Answered 2026-10-04: yes, with conditions.** Source: I32, X21-dep-gate-registries. Changes S07-egress-gateway and S11-verification-and-spikes. Opens I73.

<Aside type="tip" title="What we learned">
Yes, with conditions. Refusing every download younger than 7 days, as S07-egress-gateway said, failed the fresh install of all 10 real projects tried. Removing those versions from the registry's metadata as well let 9 of 10 install older versions, and the download refusal still catches lockfile pins. Recommended: **A**, now in S07-egress-gateway. Separately, refusing known vulnerabilities at HIGH would fail 8 of the 10 lockfile installs. That default is unchanged here, and I73 asks you to decide it.
</Aside>

## Options

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Filter the metadata, refuse the download

`wb-proxyd` removes too-young versions from the version lists of npm, PyPI, crates.io and the Go module proxy, and still refuses a too-young download. Homebrew isn't gated.

- **Cost:** `wb-proxyd` rewrites metadata responses, and fetches publish times itself (one extra request per package the first time). Fresh installs: 1 of 10 failed. Lockfile installs with a version pinned in the last 7 days: 2 of 10 failed, with a message that says when it becomes allowed.
- **Keeps:** <Badge text="SEC07-dep-gate" variant="success" />

</div>
<div class="wb-option">

### B. Refuse the download only

What S07-egress-gateway said before this spike.

- **Cost:** least code. Fresh installs: 10 of 10 failed, because each project resolved at least one dependency released in the last week. Users would override the gate on most projects.
- **Keeps:** <Badge text="SEC07-dep-gate" variant="success" />

</div>
<div class="wb-option">

### C. Rely on the installers' own cooldowns

npm (`min-release-age`), pnpm (`minimumReleaseAge`) and uv (`exclude-newer`) can skip young versions themselves, if configured in the guest.

- **Cost:** no proxy work. But the setting is in the guest, which the agent controls, and pip, go and cargo have no equivalent.
- **Weakens:** <Badge text="SEC07-dep-gate" variant="danger" /> the guest can turn it off. Needs a spec change.

</div>
<div class="wb-option">

### D. Filter the metadata only

Like A, without refusing downloads.

- **Cost:** no lockfile install ever fails on age. A lockfile, or a URL typed by the agent, fetches any version.
- **Weakens:** <Badge text="SEC07-dep-gate" variant="danger" /> young downloads get through. Needs a spec change.

</div>
</div>

<Aside type="caution" title="The vulnerability half needs your decision">
SEC07-dep-gate also refuses a download with a known vulnerability at or above a threshold, default HIGH. In the same 10 lockfiles, 8 contain a package with a HIGH or CRITICAL advisory in OSV, mostly in development tools. At CRITICAL it is 2 of 10. Some advisories have no severity. This result doesn't change the default. I73 lays out the options and recommends refusing malicious-package reports and CRITICAL, and reporting HIGH.

## Evidence

- <Badge text="verified" variant="success" /> Fresh installs of 10 projects (5 npm, 3 uv, 2 pip) through the spike's proxy: refuse failed 10 of 10, filter 1 of 10. The failure asks for `PyJWT>=2.15.1`, uploaded 6 days earlier (X21-dep-gate-registries, "Installs with a 7-day minimum age").
- <Badge text="verified" variant="success" /> Lockfile installs: refuse failed 3 of 10, filter 2 of 10. Both failures pin versions from the last 7 days.
- <Badge text="verified" variant="success" /> Go and cargo: `go get @latest` of five modules and a fresh `cargo fetch` of nine crates failed with refuse and passed with filter. Lockfile fetches passed with both.
- <Badge text="verified" variant="success" /> Publish times: npm `time` in the full packument, PyPI `upload-time` per file, crates.io `pubtime` on all 2,873 index lines sampled. `npm ci` and `uv sync --frozen` don't fetch metadata, and every download was still mapped from its URL.
- <Badge text="verified" variant="success" /> Go's `.info` Time is the commit time. 173 of 200 versions first seen by the module proxy in the last week had one more than 7 days older. Checksum database record numbers grew with first-seen time over 14 days.
- <Badge text="verified" variant="success" /> Homebrew: 61 of the 190 most installed core formulae had a bottle younger than 7 days. `brew` checks the signature of `formula.jws.json` (`Library/Homebrew/api.rb`, `verify_and_parse_jws`). OSV doesn't list a Homebrew ecosystem.
- <Badge text="verified" variant="success" /> OSV: about 240 ms per lookup. For axios (633 downloads), `npm ci` took 31 to 33 s with a lookup before each download, against 18 to 23 s without OSV. Overlapped with the download, it took 15 s, no slower than without OSV. Coalescing into `querybatch` didn't help.
- <Badge text="inferred" variant="note" /> The checksum database clock needs one calibration point, the record number of a version that `index.golang.org` lists as first seen 7 days ago. The spike checked the ordering, not a full implementation.
- <Badge text="assumed" variant="caution" /> That the 10 projects are typical. They are active, popular projects, pinned to their commits of late September and early October 2026.

## What this unblocks

- The dependency gate in `wb-proxyd` for V1-M5-approvals (SEC07-dep-gate), to the rewritten S07-egress-gateway section.
- I73, the vulnerability threshold, which the gate's implementation also needs.
- Part of the exit criterion of V1-M1-spikes-closed.

<details>
<summary>Details and glossary</summary>

**Why two layers.** A fresh install resolves version ranges against the registry's list of versions and then downloads what it picked. A lockfile install skips the list and downloads exact versions. Filtering the list fixes the first. Only refusing the download covers the second, and also a URL the agent types by hand.

**Why not Go's own time.** The module proxy reports the time of the commit that a version tag points at. Anyone can tag an old commit, or set the commit date, so a version published today can look years old. The checksum database adds a record the first time a version is looked up, in order, and nobody can backdate it.

**Why not Homebrew.** `brew` installs the one current version of a formula, from metadata that Homebrew signs. `wb-proxyd` has no older version to fall back to and no list `wb-proxyd` could change without breaking the signature. A minimum age would only refuse, and would refuse a third of popular formulae.

**Glossary**

- **Registry metadata:** the list of versions of a package, with download addresses and publish times, that an installer reads first.
- **Packument:** npm's name for that list. The full one has publish times. The abbreviated one npm asks for by default doesn't.
- **dist-tag:** a named pointer to a version, like `latest`.
- **Lockfile:** a file in the project with the exact version of every dependency, such as `package-lock.json` or `uv.lock`.
- **Caret range:** `^1.2.0`, any version from 1.2.0 up to the next major version.
- **Sparse index:** crates.io's version lists, one file per crate.
- **Checksum database:** `sum.golang.org`, a public append-only log of the hash of every Go module version.
- **OSV:** a public database of vulnerabilities in open-source packages.

</details>

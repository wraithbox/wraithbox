---
title: Can project homes on a data disk survive a new system disk?
description: Yes, with conditions. A volume the guest formats APFS is lost with its system disk, so the host formats each new data disk APFS before the first boot, and the users are recreated with the same IDs from host state.
---

**Answered 2026-10-12: yes, with conditions. Awaiting decision.** Source: X08-data-disk (I22). Changes S06-vm-lifecycle ("Updates", "Disks", "Projects and sessions inside a VM"). Related: I44 (the host-mount control), I138 (deleting a project user's record), I135 (Claude Code's state layout in a guest).

<Aside type="tip" title="What we learned">
**Yes, with conditions.** Recreated with the same UID, GID and `GeneratedUID` on a fresh system disk, every file in the homes compared equal, and every check passed: Claude Code state, keychain, ACLs, and one project user unable to read another's home. But the data disk S06-vm-lifecycle described doesn't survive: a volume the guest formats APFS is encrypted at rest with a key that only the old system disk can unwrap. You are deciding who formats the data disk instead. Recommended: the host, APFS, before the first boot.
</Aside>

## Decision: who formats the data disk?

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. The host, APFS, before the first boot

`wb-hostd` creates the sparse file, attaches it without mounting, checks the device is that image, makes one APFS volume, and detaches it. It never attaches the image again.

- **Cost:** host code that runs `diskutil` on a disk device, which must never pick the wrong one. About 1.2 s per new disk.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="caution" /> with the mount options and host-kept IDs. The I44 host-mount control needs to name this exception next to image building.

</div>
<div class="wb-option">

### B. The guest, HFS+

`wb-guestd` formats the blank disk Mac OS Extended. HFS+ has no encryption at rest, and survived the swap the same way.

- **Cost:** no clones or snapshots on the data disk, and its speed against NFR02-fs-speed isn't measured (X05-fs-benchmark measured APFS).
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="caution" /> as A. The host never touches a disk.

</div>
<div class="wb-option">

### C. The guest, APFS (as S06 said)

What S06-vm-lifecycle described before this spike.

- **Cost:** not viable. Every system disk swap loses every home, so FR13-claude-state fails on each update. A passphrase volume failed the same way, and a USB disk is refused by TCC.

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> A guest-formatted APFS volume reported "Encrypted at rest", and on a fresh clone of the image it failed to mount at boot and by hand (`failed to unwrap volume key`). Its own system disk mounted it again. Source: X08-data-disk, "Answer" part 1, `results/boot2.jsonl`.
- <Badge text="verified" variant="success" /> A passphrase APFS volume failed to unlock on the fresh system disk (`xart error: -3`). Source: "Answer" part 2, `results/boot4.jsonl`.
- <Badge text="verified" variant="success" /> A USB data disk is refused to every guest process by TCC, including root and a launchd job. Source: "Answer" part 3, `results/boot3.jsonl`.
- <Badge text="verified" variant="success" /> A host-made APFS volume and a guest-made HFS+ volume mounted on three system disks, and after recreating the users with the same IDs, a snapshot of every file and every behavior check were identical. Source: "Answer" parts 4 to 6, `results/snap-boot5-*.txt`, `results/snap-boot6-*.txt`.
- <Badge text="verified" variant="success" /> With a new `GeneratedUID`, ACL entries that name the user stop applying, and a deny entry then allows. Source: "Answer" part 9, `results/check-boot8-c3a.txt`.
- <Badge text="verified" variant="success" /> Without `nosuid`, a setuid-root file in a home gave a project user root, also after the swap. Source: "Answer" part 10, `results/boot7.jsonl`.
- <Badge text="verified" variant="success" /> macOS refuses to change a user's `GeneratedUID` or home path once the record has a UID and a group, and setting `GeneratedUID` first works. Source: "Answer" part 11, `results/boot1.jsonl`.
- <Badge text="inferred" variant="note" /> The guest-made volume's key needs the old system disk, not only the auxiliary storage: the log names xART, which is on the system disk. Not isolated by experiment.
- <Badge text="assumed" variant="caution" /> That the guest never turns encryption on for a volume the host made. It held for four boots. Option A rests on it.
- <Badge text="assumed" variant="caution" /> That the host-made volume gives freed space back to the host like a guest-made one. X05-fs-benchmark measured only the guest-made one.

## What it unblocks

I44 (the data disk settings and the host-mount control), the update path in S06-vm-lifecycle, and the project user code of `wb-guestd` in V1-M2-walking-skeleton.

<details>
<summary>Details and glossary</summary>

**Why the guest's own volume is lost.** On Apple Silicon, macOS encrypts every APFS volume on an internal disk, even with FileVault off, using keys the Secure Enclave guards. In a VM the Secure Enclave is virtual, and the kernel log points at state on the system disk. The data disk looks internal to the guest, so its volume gets such a key. A fresh clone of the image has its own state, and can't open the old volume.

**Why the host's volume is different.** On the host, a disk image is not internal storage, so the APFS volume `diskutil` makes on it isn't encrypted at rest. The guest mounts it as it is.

**Why the IDs matter.** Files belong to a numeric UID and GID, so a recreated user with the same numbers owns its home again. ACL entries name a user by its `GeneratedUID` instead, so that has to match too. If another project's user got the same numbers, it would own the old home, so `wb-hostd` never reuses them.

**Why the mount options.** Guest root can leave a setuid-root program in a home. If the data volume allowed setuid, the project user could run it and become root, also on a new system disk. `nosuid` stops that, `nodev` stops device files, and ownership on makes the guest honor the owners on the volume.

- **GeneratedUID:** the UUID macOS gives each user and group, used in ACLs.
- **ACL:** access control list, extra allow and deny rules on a file beyond its mode.
- **Disk Arbitration:** the macOS service that mounts disks at boot.
- **TCC:** macOS's privacy controls, which ask a person or MDM before a process can use protected data such as external disks.
- **HFS+:** the macOS filesystem before APFS, still supported.

</details>

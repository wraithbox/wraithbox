---
title: Can project homes on a data disk survive a new system disk?
description: Yes, with conditions. A volume the guest formats APFS can't be opened from a new system disk, so a small host shim formats each new data disk APFS before the first boot, and the users are recreated with the same IDs from host state.
---

**Answered 2026-10-12: yes, with conditions. Decided 2026-10-12: 1A and 2A.** The decisions are in the I22 comment that starts `Decision (2026-10-12):`. The assumptions stay with I228. Source: X08-data-disk (I22). Changes S06-vm-lifecycle ("Updates", "Disks", "Projects and sessions inside a VM") and S04-architecture (`wb-diskfmt`). Related: I44 (the host-mount control), I138 (deleting a project user's record), I135 (Claude Code's state layout in a guest), I218 (also edits the S04-architecture launcher table). Follow-ups: I228 (does a host-made volume stay unencrypted and give space back, and does a confined `diskutil` format), I229 (a command for a new data disk).

<Aside type="tip" title="What we learned">
**Yes, with conditions.** Recreated with the same UID, GID and `GeneratedUID` on a fresh system disk, every file in the homes compared equal, and every check passed: Claude Code state, keychain, ACLs, and one project user unable to read another's home. But the data disk S06-vm-lifecycle described doesn't survive: a fresh system disk and auxiliary storage couldn't unwrap the key of a volume the guest formats APFS. Decided 2026-10-12: the host formats the data disk APFS before the first boot (1A), and the format runs in a small shim started through `wb-launcher` (2A).
</Aside>

Both options of decision 1 come with the same guest-side controls in S06-vm-lifecycle: the data volume found by the UUID the host recorded, mounted `nosuid` and `nodev` with ownership on, its flags read again before every session, the volume root and every home checked with `lstat`, and user IDs that the host allocates and never reuses for any project on any data disk of this host.

## Decision 1: who formats the data disk?

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. The host, APFS, before the first boot

The formatting process creates the image under a temporary name with `O_CREAT|O_EXCL`, attaches it with `diskutil image attach --noMount`, checks that the device is backed by that file, and runs `diskutil eraseDisk APFS`. That mounts the new, empty volume on the host once. It records the volume UUID, unmounts and detaches it, and renames the file to its final name. A file at the final name is never attached again.

- **Cost:** host code that formats a disk device, which must never pick the wrong one. About 1.2 s per new disk. The image is unencrypted at rest except by the host's FileVault, as before, and the user must not mount it by hand: its final name has no disk image extension, so a double click doesn't.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="caution" /> with the guest-side controls above. Formatting a blank image that no guest has booted with is outside the scope of the I44 rule.

</div>
<div class="wb-option">

### B. The guest, HFS+

`wb-guestd` formats the blank disk Mac OS Extended. HFS+ has no encryption at rest, and was kept across the swap the same way.

- **Cost:** no clones or snapshots on the data disk, and its speed against NFR02-fs-speed isn't measured (X05-fs-benchmark measured APFS). Decision 2 goes away.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="caution" /> as A. The host never touches a disk.

</div>
<div class="wb-option">

### C. The guest, APFS (as S06 said)

What S06-vm-lifecycle described before this spike.

- **Cost:** not viable. Every system disk swap loses every home, so FR13-claude-state fails on each update. A passphrase volume failed the same way, and without a grant TCC refuses a USB disk.

</div>
</div>

## Decision 2: which host process runs the format?

With option A, some host process runs `diskutil`. `wb-hostd` can't under its self-sandbox, which starts only the fixed `wb-launcher` entries, with no arguments (S04-architecture, "Each host daemon is self-sandboxed").

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. A shim through a fixed `wb-launcher` entry

`wb-diskfmt`, a small program like `wb-git`, gets the VM's bundle as its profile parameter from its launcher entry, never a path from the request, confines itself to that bundle, and runs the steps of option 1A.

- **Cost:** one more program and two launcher entries, `wb-diskfmt-work` and `wb-diskfmt-isolated`, each with its VM's bundle as the profile parameter. S04-architecture and S06-vm-lifecycle are written for it. I218 (one `wb-vmd` per VM) also edits S04-architecture and rebases onto this.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" />, with `wb-hostd`'s profile unchanged.

</div>
<div class="wb-option">

### B. Widen `wb-hostd`'s profile

Let `wb-hostd` run `diskutil` itself.

- **Cost:** none to build.
- **Weakens:** <Badge text="SEC12-least-privilege" variant="danger" /> a compromised `wb-hostd` could attach and format any disk the user can. Needs a spec change.

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> A guest-formatted APFS volume reported "Encrypted at rest", and on a fresh clone of the image (system disk and auxiliary storage) it failed to mount at boot and by hand (`failed to unwrap volume key`). Its own system disk mounted it again. Source: X08-data-disk, "Answer" part 1, `results/boot2.jsonl`.
- <Badge text="inferred" variant="note" /> The key needs the old system disk, the old auxiliary storage, or both. The log names xART, which is on the system disk, but every swap replaced both. S06-vm-lifecycle replaces both on an update, so the design doesn't depend on which.
- <Badge text="verified" variant="success" /> A passphrase APFS volume failed to unlock on another system disk (`xart error: -3`). Source: "Answer" part 2, `results/boot4.jsonl`.
- <Badge text="verified" variant="success" /> Without a grant, TCC refuses a USB data disk to every guest process, including root and a launchd job. Source: "Answer" part 3, `results/boot3.jsonl`.
- <Badge text="verified" variant="success" /> A host-made APFS volume and a guest-made HFS+ volume mounted on three system disks, and after recreating the users with the same IDs on a fresh system disk, a snapshot of every file and every behavior check were identical. Source: "Answer" parts 4 to 6, `results/snap-boot5-*.txt`, `results/snap-boot6-*.txt`.
- <Badge text="verified" variant="success" /> With a new `GeneratedUID` (on g1, a system disk that never had these users), ACL entries that name the user stop applying, and a deny entry then allows. Source: "Answer" part 9, `results/check-boot8-c3a.txt`.
- <Badge text="verified" variant="success" /> Without `nosuid`, a setuid-root file in a home gave a project user root, before the swap and after it. Source: "Answer" part 10, `results/boot1.jsonl` (guest APFS), `results/boot7.jsonl` (HFS+ after the swap).
- <Badge text="verified" variant="success" /> macOS refuses to change a user's `GeneratedUID` or home path once the record has a UID and a group, and setting `GeneratedUID` first works. Source: "Answer" part 11, `results/boot1.jsonl`.
- <Badge text="assumed" variant="caution" /> That the guest never turns encryption on for a volume the host made. It held for four boots. Option 1A rests on it, `wb-guestd` refuses an encrypted volume, and I228 measures it.
- <Badge text="assumed" variant="caution" /> That the host-made volume gives freed space back to the host like a guest-made one. X05-fs-benchmark measured only the guest-made one. I228 measures it.
- <Badge text="assumed" variant="caution" /> That `diskutil` can attach and format the image under `wb-diskfmt`'s profile, which allows only the bundle, `diskutil`, and the DiskImages, Disk Arbitration and disk management services. Not run confined. Decision 2A rests on it, and I228 measures it.
- <Badge text="assumed" variant="caution" /> The formatting steps of option 1A as S06-vm-lifecycle writes them. The spike checked the device by protocol and size with the deprecated `hdiutil attach`, not by backing path.

## What it unblocks

I44 (the data disk settings and the host-mount control), the update path in S06-vm-lifecycle, and the project user code of `wb-guestd` in V1-M2-walking-skeleton.

<details>
<summary>Details and glossary</summary>

**Why the guest's own volume is lost.** On Apple Silicon, macOS encrypts every APFS volume on an internal disk, even with FileVault off, using keys the Secure Enclave guards. In a VM the Secure Enclave is virtual. The data disk looks internal to the guest, so its volume gets such a key. A fresh clone of the image, with its own system disk and auxiliary storage, couldn't open the old volume.

**Why the host's volume is different.** On the host, a disk image is not internal storage, so the APFS volume `diskutil` makes on it isn't encrypted at rest. The guest mounts it as it is, and `wb-guestd` refuses it if that ever changes.

**Why the IDs matter.** Files belong to a numeric UID and GID, so a recreated user with the same numbers owns its home again. ACL entries name a user by its `GeneratedUID` instead, so that has to match too. If another project's user got the same numbers, it would own the old home, so `wb-hostd` never reuses them.

**Why the mount options.** Guest root can leave a setuid-root program in a home. If the data volume allowed setuid, the project user could run it and become root, also on a new system disk. `nosuid` stops that, `nodev` stops device files, and ownership on makes the guest honor the owners on the volume. Guest root can change the flags in place, but gains nothing, because it is already root. `wb-guestd` reads them again before each session.

- **GeneratedUID:** the UUID macOS gives each user and group, used in ACLs.
- **ACL:** access control list, extra allow and deny rules on a file beyond its mode.
- **Auxiliary storage:** a VM's small extra file that holds its firmware settings.
- **Disk Arbitration:** the macOS service that mounts disks at boot.
- **TCC:** macOS's privacy controls, which ask a person or MDM before a process can use protected data such as external disks.
- **HFS+:** the macOS filesystem before APFS, still supported.

</details>

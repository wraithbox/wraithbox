How agents run work that needs a running macOS guest, given that a Mac runs at most two (NFR05-two-macos-vms), and where the conformance suite and benchmarks run. Recommended: **A**, a `needs-vm` label, at most one such issue per wave, a lock file per slot, and one restore image cache per Mac, with a dedicated self-hosted runner decided before V1-M3-network-floor. This decision gates running the VM spikes of V1-M1-spikes-closed in parallel.
</Aside>

## Options

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Label, wave limit, lock, and a dedicated runner

The issue's option 1, with a lock added. A `needs-vm` label in `.github/labels.yml`. `/wave` starts at most one `needs-vm` issue per wave. Spike code takes a slot lock with `lockf` before it starts a VM, so a second VM user waits with a message. Restore images go in one cache directory per Mac, outside worktrees. A dedicated Apple Silicon Mac runs the conformance suite and benchmarks as a self-hosted runner, for `main` and manual runs only.

- **Cost:** a label, a few lines in `orchestration.md` and the wave skill, a lock helper, and a Mac for the runner. The nine VM spikes run one after another on each machine.
- **Keeps:** <Badge text="NFR05-two-macos-vms" variant="success" /> one slot left for the maintainer

</div>
<div class="wb-option">

### B. Rent a bare-metal Mac

Instead of a Mac of your own, rent a bare-metal Apple Silicon Mac by the day, such as Amazon EC2 Mac. It runs the Virtualization framework directly, so no nested virtualization is needed. The label, wave limit and lock from A still apply on development Macs.

- **Cost:** a 24-hour minimum per allocation, cloud account setup, and credentials for it in CI.
- **Keeps:** <Badge text="NFR05-two-macos-vms" variant="success" />

</div>
<div class="wb-option">

### C. By hand until v1 is close

VM tests run only when the maintainer runs them, on the maintainer's Mac. Agents don't take VM issues.

- **Cost:** none in tooling. Every VM spike waits for the maintainer, and 9 of the 17 spikes in V1-M1-spikes-closed need a VM.
- **Keeps:** <Badge text="NFR05-two-macos-vms" variant="success" />

</div>
</div>

<Aside type="note" title="Missing from the issue">
**A wave limit doesn't cover everything.** "At most one `needs-vm` issue per wave" counts one coordinator's agents. It doesn't count a second session, a spike the maintainer runs, or the maintainer's own VMs. A lock file per slot on each Mac covers the first two. The framework's limit error covers the rest, and a builder that hits it should report it, not retry in a loop. `lockf` ships with macOS.

**The runner is needed earlier than "close to v1".** V1-M3-network-floor already has conformance cases for egress, and S11-verification-and-spikes makes the suite a release gate. Decide the runner before V1-M3-network-floor starts.

**A self-hosted runner runs whatever its workflow runs.** On that Mac, a job runs as the runner's user, with the rights of host code. It should be a dedicated machine without the maintainer's credentials, and its workflow should not run on pull requests, which can come from anyone if the repository becomes public. The repository is private today. Its jobs stay out of `mise run ci`, as S02-toolchain already says.

**I43 is the same limit inside the product.** `wb-hostd` admission (I43) only sees VMs that `wb-hostd` starts. Spike code starts VMs directly, so the lock here is the only guard for it. Both should use the same words in their refusals.

**The issue's option 2 looks for nested virtualization.** Bare-metal rental, option B here, doesn't need it.
</Aside>

<details>
<summary>Details and glossary</summary>

**Why one and not two.** Two `needs-vm` issues per wave would take both slots and leave the maintainer none. A lock with two slots lets the maintainer allow two when not using Wraith Box. Some spikes may need both slots at once, for example to test what happens at the limit. Such a spike takes both locks.

**Disk space.** Each VM bundle grows with use, and each restore image is large. A cache per worktree would copy the image for every builder. One cache directory per Mac, outside worktrees, holds each restore image once.

**Glossary**

- **Slot:** one of the two macOS VMs a Mac may run at once.
- **Restore image:** Apple's macOS installer file that a VM is installed from.
- **Self-hosted runner:** a machine you own that runs GitHub Actions jobs for the repository.
- **Nested virtualization:** running a VM inside a VM. The issue notes that most hosted Mac services don't offer it for macOS guests.
- **Bare metal:** a whole physical machine rented to one customer, with no hypervisor of the provider's underneath.
- **Wave:** one batch of up to six issues a coordinator runs builders for (`orchestration.md`).

</details>

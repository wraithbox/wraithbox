**Decided 2026-10-04: A. Boundary plus allowlist filter, for now. Decided 2026-10-06: 1A, reset on exit, and 2C, the full filter on every stream.** The decisions and their reasons are in the I37 comments that start `Decision (2026-10-04):` and `Decision (2026-10-06):`, and the filter's contents in the I30 decision (B30-terminal-filter). The spec change from PR81 is confirmed: T00-index, S05-cli ("Terminal stream") and S11-verification-and-spikes.

<Aside type="tip" title="You are approving">
The spec text for the decided boundary: `wb` filters guest output to your terminal with the allowlist measured in X19-terminal-filter, drops links and lists them in the session summary, sets the window title itself, and resets the terminal before the summary. Decided on 2026-10-06: `wb` resets the terminal on exit (1A), and output that goes to a pipe or a file passes the same full filter (2C). What `wb` itself writes to a terminal (the window title, the reset, and the input drain's sentinel query) happens only when the output is a terminal, and binary output through standard output isn't supported. This unblocks the terminal filter in V1-M4-claude-end-to-end.
</Aside>

## The spec change

What the decisions on I37 and I30 and the security review of PR66 became, and where:

- **T00-index:** boundary 6 is the host terminal stream. A new accepted risk, T09-terminal-fingerprint, records what the guest learns about your terminal: its name and version, colors, window size, and seven environment variables.
- **S05-cli, "Terminal stream":** the allowlist as a table, tightened as PR66's review asked (at most 16 parameters of at most 5 digits, `CSI 3 J` dropped, unrecorded modes dropped, the kitty keyboard stack at most 4 deep per screen, and the guest can't change or pop an entry it didn't push). OSC 52 is dropped, because V1 has no clipboard (V1-08-no-forward-clipboard). Notifications become a bell, at most one per second. OSC 8 links are dropped on screen. `wb` lists up to 100 of them with their text in the session summary and the audit log, and marks those whose name looks host-local or that aren't `https://`, as a heuristic. `wb` sets the window title itself, resets the terminal before the summary, drains late query replies on exit behind a query of its own, and passes exactly `TERM`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `COLORTERM`, `LANG`, `LC_ALL` and `LC_CTYPE` to the guest.
- **One change from the I37 decision:** it says `wb` strips control sequences from guest text outside the stream. The spec has `wb diff`, logs and audit records show them escaped instead, so you see them when you review. Other output removes them.
- **S11-verification-and-spikes:** the filter's fuzz properties, including one that replays the filtered output and the exit reset into a headless emulator and checks it is back in its initial state, and a conformance case that prints every dropped sequence and a fake summary.
- S03-requirements stays as it is, because it points at T00-index for the boundaries.

**Decision 1: how `wb` cleans up the terminal on exit.** Decided 2026-10-06: 1A.

<div class="wb-options">
<div class="wb-option" data-recommended>

### 1A. Reset the terminal on exit

`wb` undoes what the guest may have changed (colors, modes, scroll region, keyboard protocol, tab stops) before it prints the summary. Claude Code's output stays in your scroll-back, as with `claude`.

- **Cost:** the reset list has to cover every state on the allowlist, and a gap lets the guest hide part of the summary. The fuzz and conformance checks in S11-verification-and-spikes look for that.
- **Keeps:** <Badge text="SEC03-no-host-exec" variant="success" /> <Badge text="FR01-drop-in" variant="success" />

</div>
<div class="wb-option">

### 1B. Run the session on `wb`'s own alternate screen

`wb` switches to the alternate screen before the session and back after it, which discards all screen state at once.

- **Cost:** the session's output is gone from the scroll-back when it ends, unlike `claude`.
- **Keeps:** <Badge text="SEC03-no-host-exec" variant="success" /> **Weakens:** <Badge text="FR01-drop-in" variant="caution" />

</div>
</div>

**Decision 2: output to a pipe or a file.** Decided 2026-10-06: 2C. The I37 decision doesn't make an exception for pipes, so this had no recommendation. The filter passes only output that is safe in a terminal, so a later `cat` of the file is as safe as the live session, and one filter keeps one code path and one fuzz target.

<div class="wb-options">
<div class="wb-option">

### 2A. Pass it unchanged

The filter runs only on a stream that goes to a terminal. `wb claude -p … > out.txt` writes Claude Code's bytes exactly.

- **Cost:** `wb claude -p … | cat`, `| tee` or `| less -R` puts unfiltered guest bytes on your terminal: OSC 52, iTerm2 file transfer, links.
- **Keeps:** <Badge text="FR01-drop-in" variant="success" /> **Weakens:** <Badge text="SEC03-no-host-exec, spec change" variant="danger" />

</div>
<div class="wb-option">

### 2B. Drop only escape sequences

On a stream that isn't a terminal, `wb` drops `ESC` and every sequence it starts (CSI, OSC, DCS, APC, PM, SOS) and passes every other byte. Valid JSON can't hold a raw `ESC`, so `--output-format json` stays byte-exact, and plain `-p` text held none in the probe below.

- **Cost:** a second, smaller mode of the filter. Other controls (BEL, backspace, C1 characters) still pass to whatever reads the pipe.
- **Keeps:** <Badge text="SEC03-no-host-exec" variant="caution" /> for terminals that ignore C1 controls <Badge text="FR01-drop-in" variant="success" /> for JSON and plain text

</div>
<div class="wb-option">

### 2C. Full filter on every stream

The allowlist runs whatever the output goes to. This is the decided option.

- **Cost:** JSON keeps working, but a C1 character or `DEL` inside a string is dropped, and a script sees changed bytes. Invalid UTF-8 becomes U+FFFD, so binary output piped out of `wb shell` is corrupted.
- **Keeps:** <Badge text="SEC03-no-host-exec" variant="success" /> <Badge text="FR01-drop-in" variant="caution" /> except rare bytes in scripts

</div>
</div>

## Options for the boundary (decided: A)

The issue proposes A and doesn't list alternatives. B, C and D are the alternatives as this brief sees them.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Boundary plus allowlist filter

T00-index lists the host terminal stream as boundary 6. `wb` passes only escape sequences on an allowlist and drops the rest, for `wb claude` and `wb shell` alike. Every other place `wb` prints guest text (the session summary, `wb diff`, `wb sessions`) strips control sequences, as `wb approve` already does.

- **Cost:** a parser of guest bytes in `wb`, with a fuzz target. Some rendering may break until the list is right. X19-terminal-filter measures that.
- **Keeps:** <Badge text="SEC03-no-host-exec" variant="success" /> <Badge text="SEC14-no-fake-approvals" variant="success" />

</div>
<div class="wb-option">

### B. Boundary plus denylist

The same boundary, but `wb` drops only the sequences known to act on the host: OSC 52, OSC 1337, DCS, and replies to queries.

- **Cost:** a smaller parser, and nothing Claude Code uses breaks.
- **Weakens:** fails open. A sequence that a new emulator release adds passes until someone adds it to the list. <Badge text="SEC03-no-host-exec" variant="caution" />

</div>
<div class="wb-option">

### C. Re-render on the host

`wb` runs a terminal emulator of its own (as `tmux` or `mosh` do), keeps a screen model, and sends the user's terminal only redraws it generates itself.

- **Cost:** the largest parser of the four, and the most visible differences in rendering, scroll-back and mouse handling. FR01-drop-in is at risk.
- **Keeps:** <Badge text="SEC03-no-host-exec" variant="success" />

</div>
<div class="wb-option">

### D. Leave the spec as is

Write it down as an accepted threat in T00-index and point users at their emulator's settings.

- **Cost:** none now. OSC 52 bypasses the approval of FR12-clipboard, and every emulator parser bug becomes a path to the host.
- **Weakens:** <Badge text="SEC03-no-host-exec, spec change" variant="danger" />

</div>
</div>

<Aside type="note" title="Missing from the issue">
- The boundaries are listed in T00-index ("Model"), not in S03-requirements. S03-requirements now only points there. The spec change belongs in T00-index.
- The relay is not the only path. `wb diff`, `wb sessions` and the session summary print commit messages, branch names and paths that the guest wrote. `git` prints a commit subject with an OSC 52 sequence in it byte for byte. The boundary covers every `wb` output of guest text, not only the PTY relay. After `wb land`, the user's own `git log` shows the same bytes. That is outside Wraith Box and is T04-bad-approvals territory.
- V1-M4-claude-end-to-end already lists "the terminal filter" as a deliverable. The milestone assumes this decision.
</Aside>

- <Badge text="verified" variant="success" /> S11-verification-and-spikes requires a fuzz target for every parser of guest bytes ("Test layers"). The filter gets one under A, B, and C.
- <Badge text="verified" variant="success" /> Claude Code 2.1.289 draws the same screens through the allowlist, on replay in a headless emulator, except that links stop being links (X19-terminal-filter, "What the filter changes").
- <Badge text="verified" variant="success" /> The caps in S05-cli sit above what Claude Code sent: in the seven X19-terminal-filter recordings a CSI has at most 5 parameters of at most 4 digits, `J` and `K` take only 2 or none, and the kitty keyboard stack is at most 1 deep (count over the recordings on the spike branch, for this spec change).
- <Badge text="verified" variant="success" /> The X19-terminal-filter recorder gave Claude Code `TERM`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION` and `COLORTERM` per terminal profile, and the host's own locale. Those are the variables S05-cli lets cross (`cmd/record/main.go` on the spike branch).
- <Badge text="verified" variant="success" /> Plain `-p` text doesn't hold escape sequences when standard output is a file. The X19-terminal-filter recordings are all interactive, so this PR ran one probe: Claude Code 2.1.289, `claude -p --model haiku` asked for a heading, a table, bold text, a code block and a Markdown link, with output to a file. It wrote 528 bytes with no `ESC` byte.
- <Badge text="assumed" variant="caution" /> That Ghostty and Terminal.app answer the drain's sentinel query `CSI ? 6 n`. A terminal that doesn't costs 100 ms on exit, and a reply that arrives after that can still reach your shell. I62 can check it.
- <Badge text="assumed" variant="caution" /> That the headless emulator shows what Ghostty and Terminal.app show. I62 checks it by eye.
- <Badge text="assumed" variant="caution" /> Which macOS terminals act on OSC 52 by default. The answer varies per emulator and version. The filter drops it either way.

## What this unblocks

- The terminal filter in V1-M4-claude-end-to-end, once this spec change merges.
- I38, whose clipboard design (B38-port-forward-clipboard) relies on OSC 52 never reaching the host.

<details>
<summary>Details and glossary</summary>

**Why an allowlist.** The filter is a security control on a parser of guest bytes, and the rest of the design fails closed (SEC05-default-deny for the network). A denylist depends on knowing every sequence every emulator acts on, across releases. An allowlist depends only on what Claude Code needs, which X19-terminal-filter measures once.

**Dropped sequences.** The filter removes a sequence that isn't on the list rather than escaping it into visible text, which would shift the screen layout. The session summary reports how many it removed, which explains a broken render (NFR06-explained-refusals).

**Input in the other direction.** Keystrokes and replies from the emulator go into the guest. Those are host data in the guest. Replies to queries (cursor position, device attributes) are harmless, but a sequence that asks the emulator to report the clipboard (OSC 52 with `?`) would send host clipboard content into the guest. Dropping OSC 52 in the output direction removes that too.

**Glossary**

- **Escape sequence:** bytes starting with `ESC` that a terminal emulator treats as a command (move the cursor, change color) rather than text.
- **OSC:** Operating System Command, a family of escape sequences. OSC 52 sets or reads the clipboard. OSC 1337 holds iTerm2's own commands.
- **DCS:** Device Control String, another family, used by multiplexers such as `tmux` and for graphics.
- **PTY:** the pseudo-terminal in the guest that Claude Code writes to, as if it were a real terminal.
- **Raw mode:** the host terminal passes keystrokes straight through, and `wb` passes output straight back.
- **Fuzz target:** a test that feeds random input to a parser to find crashes.

</details>

---
title: How do development builds without a signing identity keep their Keychain items and their CA key?
description: Between updates the access-control list works, but after each update every item asks for a password nobody knows. A permanent Secure Enclave key needs an entitlement, and a wrapped key in a store item works without one. Recommended - sign development builds with the developer's own certificate (after a spike), and keep the CA key as a wrapped Secure Enclave key.
---

**Answered 2026-10-13: yes between updates, no across an update, and no permanent Secure Enclave key. Decided 2026-10-15: 1D (1A until X29-dev-signing) and 2A.** The decisions are in the I23 comment that starts `Decision (2026-10-15):`. The spec changes are I249, and the follow-up spike is X29-dev-signing (I248). Source: I23, X09-keychain-unsigned. Touches S09-policy-credentials-audit, S15-least-privilege, S10-tech-stack and S12-platforms.

<Aside type="tip" title="What we learned">
**No across an update, yes for the CA key.** After an update every Keychain item of an ad-hoc build asks for a password nobody knows. A wrapped Secure Enclave key works without an entitlement. Recommended: **D** for updates (a spike first, A until then), and **A** for the CA key.
</Aside>

## Decision 1: keeping items across an update

<div class="wb-options">
<div class="wb-option" data-recommended>

### D. Sign development builds with the developer's certificate

Drop the keychain file. Development builds are signed with the developer's own Apple Development certificate and a profile with a Keychain access group, as Secretive does, and use the same data protection keychain as release builds.

- **Cost:** a spike first: whether a free personal team can grant `keychain-access-groups` to the helpers in `Wraith Box.app`. Each developer needs an Apple ID in Xcode.
- **Gives:** one Keychain model for all builds, no dialogs after an update, and G2 by code signature.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" /> <Badge text="SEC14-no-fake-approvals" variant="success" />

</div>
<div class="wb-option">

### A. Fail closed

After an update, the binaries read with dialogs turned off, and a read fails at once. `wb` says the store must be set up again, and the user enters each binding again.

- **Cost:** every binding typed again after each update. Generated items are lost, such as `wbadmin/vm/<vm>/<disk>`, which S15-least-privilege keeps for the secure token.
- **Gives:** no dialog, and the strict default. Recommended as the behavior until D is answered.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" /> <Badge text="SEC14-no-fake-approvals" variant="success" />

</div>
<div class="wb-option">

### B. The old build copies the items over

Before an update replaces the binaries, the old ones copy every item into a new keychain file whose lists name the new binaries, already on disk.

- **Cost:** an update step that reads every secret into one process. Not run end to end.
- **Gap:** the copying process must be on every item's list, so one binary can read every item.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="caution" /> one reader of every item during an update <Badge text="SEC14-no-fake-approvals" variant="success" />

</div>
<div class="wb-option">

### C. A keychain password the user knows

The user picks the keychain file's password and answers one dialog per item and binary after each update.

- **Cost:** many dialogs after each update, about one for each pair of item and reader.
- **Gap:** the user learns to type a password into a dialog that a process asks for, and any process of the user can then ask for any item.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="caution" /> any process can ask for an item <Badge text="SEC14-no-fake-approvals" variant="caution" /> routine store dialogs

</div>
</div>

## Decision 2: where the CA signing key is kept

S09-policy-credentials-audit keeps the CA key in the Secure Enclave, with a software key in the store as the fallback. A permanent Secure Enclave key needs an entitlement, so it isn't there for an ad-hoc build.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. A wrapped Secure Enclave key in a store item, for every build

`wb-proxyd` makes a Secure Enclave key that isn't stored in the Keychain, and stores its wrapped form (the token object ID) as the item `ca/<vm>/<ca>`. Later it hands the wrapped key back to the Secure Enclave to sign.

- **Cost:** one symbol, `kSecAttrTokenOID`, that Security.framework exports but its headers don't declare. 5 ms per new leaf certificate.
- **Gives:** one code path for signed and ad-hoc builds. A copied item is useless on another Mac.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" /> the item is declared for `wb-proxyd` only

</div>
<div class="wb-option">

### B. Software key for ad-hoc, permanent key for signed

Ad-hoc builds use the software fallback key of S09-policy-credentials-audit. Signed builds make a permanent Secure Enclave key.

- **Cost:** two code paths.
- **Gap:** in ad-hoc builds a copied item is a working CA key anywhere.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="caution" /> an exportable key in ad-hoc builds

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> The list pins an ad-hoc signed binary by cdhash. A rebuilt binary, another binary and `security find-generic-password` each got a dialog for the keychain file's password. The maintainer saw each one. Source: X09-keychain-unsigned, "Keychain file".
- <Badge text="verified" variant="success" /> No call repaired a list without the dialog: `SecKeychainItemSetAccessWithPassword` with the right password returned -25293. Source: X09-keychain-unsigned, "Keychain file".
- <Badge text="verified" variant="success" /> `SecKeychainSetUserInteractionAllowed(false)` turns the dialog into error -25293, and `kSecUseAuthenticationUIFail` doesn't. Option A depends on the first. Source: X09-keychain-unsigned.
- <Badge text="verified" variant="success" /> A permanent Secure Enclave key fails with -34018 without an entitlement. A wrapped key restores the same key in another process, another binary and a rebuilt binary, and CryptoKit loads it too. Source: X09-keychain-unsigned, "Secure Enclave".
- <Badge text="verified" variant="success" /> Secretive keeps CryptoKit wrapped keys in the data protection keychain behind an access group, and its debug builds are signed with the developer's team. Source: `secretive` `SecureEnclaveStore.swift` (`saveKey`), `CryptoKitMigrator.swift:17`, `Config.xcconfig`.
- <Badge text="assumed" variant="caution" /> That a free personal team can sign the helpers of an app bundle with `keychain-access-groups`. Option D depends on it, and a follow-up spike would settle it.
- <Badge text="assumed" variant="caution" /> That `kSecAttrTokenOID` keeps working. Apple doesn't document it. Secretive reads the same attribute, and CryptoKit's own format matched on macOS 27.0.1.
- <Badge text="inferred" variant="note" /> That option B works: adding an item whose list names other binaries didn't raise a dialog, but the whole copy wasn't run.

## What this unblocks

- I61: the `wb-proxyd` sandbox rules for the Keychain and the Secure Enclave, in X23-sandboxed-daemons.
- The spec text of S15-least-privilege ("Keychain", G2) and S09-policy-credentials-audit ("Key"), in I249.
- I248, X29-dev-signing: whether a free personal team can grant `keychain-access-groups` to the helpers in `Wraith Box.app`. Option D waits for it, and A applies until it answers yes.

<details>
<summary>Details and glossary</summary>

**Why the dialog asks for a password nobody knows.** A Keychain file has its own password. S15-least-privilege gives the file a random one and keeps it in the login keychain, so Wraith Box can unlock the file without asking. When a binary that isn't on an item's list asks for the item, macOS asks the user to confirm with that file's password, not the login password. The user never saw it.

**Why signed builds don't have the problem.** With a Developer ID or Apple Development certificate, items go into the data protection keychain and are shared by an access group, which names the team, not a build. An update signed by the same team keeps access.

**Glossary**

- **Ad-hoc signed:** signed without a certificate. The signature only records the binary's hash.
- **cdhash:** the hash of a binary's code, which changes with every build.
- **Access-control list:** the list of binaries that an item in a keychain file lets in without a dialog.
- **Access group:** an entitlement that lets every binary of one team share Keychain items.
- **Secure Enclave:** the Mac's key hardware. Its keys can't be read out.
- **Wrapped key (token object ID):** a Secure Enclave key encrypted by this Mac's Secure Enclave, which only that Secure Enclave can use.

</details>

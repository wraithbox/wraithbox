<Aside type="tip" title="What we learned">
**Yes, with conditions:** Claude Code ran on placeholder tokens while the proxy held the real login and made every refresh. **No:** refusing `/v1/oauth/hello` doesn't hide the login URL in a guest. Recommended: **not in V1** (decision 1) and **no filter** (decision 2).
</Aside>

## Decision 1: the browser login in V1

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Not in V1

The long-lived token from `claude setup-token` stays the subscription mode (S09-policy-credentials-audit, "Model credential"). A `/login` in the guest can't finish. The profile doesn't allow the token endpoint, and `wb-proxyd` refuses the code exchange. An issue keeps the measured design for after V1.

- **Cost:** nothing new to build. The user runs `claude setup-token` on the host about once a year.
- **Gap:** an organization whose admin turns off `setup-token` has no subscription mode in V1. Whether an admin can do that wasn't checked.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" /> <Badge text="SEC05-default-deny" variant="success" />

</div>
<div class="wb-option">

### B. A host-side login in V1

`wb` signs the user in on the host, either with its own login flow under Claude Code's public client ID, or by running the host's Claude Code and moving the login out of its store, as the spike did. The refresh token goes in the secret store. `wb-proxyd` answers the guest's refresh as in Figure 1, and writes each rotated token back.

- **Cost:** new code in `wb` and `wb-proxyd`: a login command, a binding kind for the pair, and a rewrite of the token endpoint's request and answer bodies. Spec changes in S07-egress-gateway, S09-policy-credentials-audit and S15-least-privilege. A new sign-in about every 30 days.
- **Gap:** using Claude Code's client ID outside Claude Code is what OpenShell waits for Anthropic to approve (X00-index). A leaked refresh token keeps working after rotation, for up to 30 days. The organization's plugins and skills arrive by download, and the profile has to allow or refuse them.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" /> <Badge text="SEC05-default-deny" variant="caution" /> the token endpoint and the organization paths allowed

</div>
<div class="wb-option">

### C. A login in the guest

The guest's Claude Code signs in itself, and the profile allows the login hosts. Not viable: the guest's Claude Code stores the real pair in its Keychain, or in plaintext in `~/.claude/.credentials.json` when no Keychain is unlocked, which the spike saw. It needs a spec change that weakens a control, so it isn't recommended.

- **Weakens:** <Badge text="SEC04-no-guest-secrets" variant="danger" /> real tokens in the guest

</div>
</div>

## Decision 2: the authorize URL in a guest

`/login` in a guest prints a real authorize URL, and refusing `/v1/oauth/hello` doesn't stop it. A user who opens it and pastes the code into the guest gives the guest a code it can't redeem through `wb-proxyd`, but can send out. S14-claude-in-guest has `wb` warn against it.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. The warning stays

The S14-claude-in-guest warning stays as the only control, without a filter, and the text gets the measured answer.

- **Cost:** none.
- **Gap:** the URL shows, and the warning is the only control against a pasted code.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="caution" /> a pasted code can leave the guest

</div>
<div class="wb-option">

### B. The terminal filter hides the URL

S16-terminal-stream removes `claude.com/cai/oauth/authorize` URLs from the guest's output.

- **Cost:** a new filter rule. Claude Code redraws and wraps the URL across lines. A rule matches some forms of it and misses others. The recording of the spike held the URL in fragments.
- **Gap:** the user can still start a login on the host and paste its code.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="caution" /> as A, with fewer URLs shown

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> `-p` answered `pong` after a refresh, `-p --resume` answered `I replied with "pong".` after a second, and the interactive session answered a question, with placeholders in Claude Code's store. Source: X01-model-credential, "Answer (I15)", the run's output.
- <Badge text="verified" variant="success" /> Each refresh returned a new refresh token, and the access token lives 8 hours. Source: the proxy's `REFRESH` lines, "Refresh".
- <Badge text="verified" variant="success" /> The refresh token's deadline is fixed at login, about 29 to 30 days, and a refresh doesn't move it. Source: `refresh_token_expires_in` across three answers and a second login, "Refresh".
- <Badge text="verified" variant="success" /> A refresh token rotated away five minutes before still refreshed. Source: the restore step, "Refresh".
- <Badge text="verified" variant="success" /> The placeholders appeared only where the proxy swaps them, and no real token went to Claude Code. Source: the full-request scan, "Placeholders and the real tokens".
- <Badge text="verified" variant="success" /> With the login Keychain locked, Claude Code stored the login in plaintext in `~/.claude/.credentials.json`, without a message. Source: "Without a Keychain".
- <Badge text="verified" variant="success" /> `/login` printed the authorize URL with every login host refused, and didn't send a request to one. Source: "The authorize URL without a network".
- <Badge text="verified" variant="success" /> The profile doesn't allow a path on `platform.claude.com` other than `/v1/oauth/hello`, so a guest's code exchange to `/v1/oauth/token` is refused. Source: S07-egress-gateway, model API.
- <Badge text="inferred" variant="note" /> Claude Code wraps the URL across lines. The recording held it in three fragments of different lengths, which a terminal width cut would give.
- <Badge text="assumed" variant="caution" /> That a rotated-away refresh token still works after more than five minutes. One check. A rerun of the restore step after a day would show it.
- <Badge text="assumed" variant="caution" /> That a Pro or Max login behaves like the enterprise login measured. A rerun of `login.sh` with such an account would show it.
- <Badge text="assumed" variant="caution" /> That Anthropic allows a tool other than Claude Code to run the login under Claude Code's client ID. OpenShell waits for an approved client identity (X00-index). Option B depends on it.

## What this unblocks

- I15 closes with the decisions. Nothing else is blocked by it.
- I256 writes the decisions into S14-claude-in-guest, S09-policy-credentials-audit and S15-least-privilege.
- I257 keeps the host-side login for after V1.
- I253 keeps API key mode.

<details>
<summary>Details and glossary</summary>

**Why the host must own the refresh.** Each refresh returns a new refresh token. If the guest held the real one, and the host's Claude Code or a second VM had the same login, whichever refreshed second would send a token the other had already used. With the proxy answering every refresh, there is one holder, and Claude Code in the guest only ever sees placeholders.

**A leaked refresh token works for up to 30 days.** Rotation doesn't revoke the old refresh token, at least not within five minutes. A refresh token copied out of the secret store keeps working until the login's deadline, about 30 days, or until someone revokes the login. `/logout` revokes through `platform.claude.com/v1/oauth/token/revoke`.

**What the long-lived token lacks.** The long-lived token from 2026-10-12 reached none of the organization's plugin and skill paths that the browser login reached, so organization plugins and skills aren't in the guest in V1 either way, as S14-claude-in-guest already says for the plugin marketplace.

**Glossary**

- **Access token:** what Claude Code sends with each model request. It lasts 8 hours.
- **Refresh token:** what Claude Code trades for a new access token when the old one expires. It is the long-lived secret of a login.
- **Rotation:** a refresh returns a new refresh token as well.
- **Authorize URL:** the page where the user signs in. It ends with a code that the user pastes back into Claude Code.
- **PKCE:** a check that ties the code to the program that asked for it. Whoever holds both the code and the program's secret verifier can redeem it.

</details>

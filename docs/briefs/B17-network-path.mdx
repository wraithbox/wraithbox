title: Does a macOS guest work on our userspace network stack, reaching only the proxy, and how fast?
description: Yes, with conditions. The guest gets a lease in about 5 s, reaches only allowlisted names through the proxy, and downloads at about 350 MB/s at MTU 1500 and 570 MB/s at larger MTUs, with a link filter in front of the stack. Still open are the MTU and approval noise from the guest OS.

**Answered 2026-10-05: yes, with conditions. Open: the link MTU, and prompts for the guest OS's own names.** Source: X03-network-path (I17). Changes S07-egress-gateway and S11-verification-and-spikes. Follow-up: I93.

<Aside type="tip" title="What we learned">
**Yes, with conditions.** A macOS guest whose only network card is a socket pair to our Go stack (gVisor) got its address from our DHCP server about 5 s after starting. Only allowlisted names resolved, each to a stand-in address. The proxy stand-in was the one thing it could reach, and our stack reset or dropped every other connection, including IPv6 and UDP other than DNS. No permission beyond the virtualization entitlement was needed. A 1 GiB download reached about 350 MB/s at MTU 1500 and 570 MB/s at MTU 65535, and an upload 300 and 950 MB/s. The catch: to accept connections to the stand-in addresses, the stack claims every address on the local network, so the guest saw its own address as taken. So `wb-netd` must filter frames before the stack sees them. **You are deciding** the link MTU (recommended: 65535) and whether the guest OS's own background lookups raise approval prompts (recommended: no, refuse them quietly and log them).
</Aside>

## What changes in the specs without a choice

S07-egress-gateway now states the complete link filter, the DHCP options the gateway never offers (a proxy configuration URL among them), local answers for names under `.arpa` and `.local`, the size and reuse rules of the synthetic address pool, per-VM caps, rate limits on every event the guest can trigger, the same MTU on both ends of the link, and that NTP is dropped, so the guest clock comes from `wb-guestd`. S11-verification-and-spikes adds the filter to the fuzz targets, adds conformance checks for it, and compares the download benchmark with this spike.

**Choices of the builder.** These go beyond what the spike measured, and are yours to overrule:

- One approval event per name per session, with later queries counted on it. This overlaps the approval design of B51-approval-flow.
- `wb-netd` has no host-side listener and never opens a connection to the guest. This commits port forwarding (FR11-port-forward) to a path outside `wb-netd`.

**Not measured:** S07-egress-gateway gives an empty answer to `HTTPS` and `SVCB` queries for allowlisted names, where the spike refused them and the guest connected fine. An empty answer gives the guest no record that could hold an encrypted ClientHello configuration or an HTTP/3 hint the proxy can't honor. The cost: nobody has checked the macOS resolver behaves the same with it, so S11-verification-and-spikes adds a case for that, and until it passes the choice rests on reading, not on a run.

## Decision 1: the link MTU

The MTU is the largest frame between the guest and `wb-netd`. It only exists on that link: `wb-proxyd` opens its own connections upstream, so no packet from the guest ever crosses the internet and a large MTU can't break anything out there. Bigger frames mean fewer frames to handle for the same bytes.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. 65535, the largest

`wb-vmd` sets 65535 on the attachment and the DHCP server offers it.

- **Cost:** a frame can be 64 KiB, so `wb-netd` bounds its queues in bytes, not only in frames. The parsers of guest frames see frames that large, which the link endpoint's fuzz target (S11-verification-and-spikes) has to cover anyway.
- **Gets:** downloads at about 570 MB/s (the proxy stand-in was the limit), uploads at 950 MB/s, and about 4 CPU-seconds per GiB in `wb-netd`.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="caution" /> with queues bounded in bytes.

</div>
<div class="wb-option">

### B. 9000, the usual large size

A common "jumbo frame" size.

- **Cost:** the same queue bound, at a seventh of the size.
- **Gets:** downloads like A. Uploads at 9000 were not measured.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="success" />

</div>
<div class="wb-option">

### C. 1500, the default

What every network uses, and what S07-egress-gateway says until this is decided.

- **Cost:** about 350 MB/s down and 300 MB/s up, and about 7 CPU-seconds per GiB in `wb-netd`, about 2.4 cores busy during a large download. Option A keeps about 2.2 cores busy, but moves 60% more bytes in that time. These figures include the proxy stand-in, which ran in the same process.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="success" />

</div>
</div>

No security control depends on the MTU: the link filter, DNS and the proxy apply the same rules at any size.

## Decision 2: the guest OS's own lookups

An idle guest at the login window, with nothing installed and nobody logged in, looked up 14 host names in its first hour, 109 queries in all, every one under `apple.com` or `icloud.com`: by their names, push, time, software update, location and iCloud services. It also asked for the reverse name of its own address and for `_dns.resolver.arpa`, which S07-egress-gateway now answers locally without a prompt. Under the spec as it stands, each of the 14 host names raises one approval event per session, a prompt on the host for something the user never did.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Refuse quietly, and turn them off in the image

A list of the guest OS's background names gets `NXDOMAIN` and an audit entry, but no prompt. The image (X17-image-build) turns off the services it can. The conditions:

- the list is host-held policy, which the guest can never extend;
- it holds exact names, not suffixes, so `developer.apple.com` doesn't fall under it;
- `wb status` shows the list and counts each name's refusals.

- **Cost:** a list to keep up with macOS releases. A user who wants one of those services allows it by hand. FR09-approve-unknown is amended to exempt the list.
- **Keeps:** <Badge text="SEC05-default-deny" variant="success" /> still refused. <Badge text="SEC10-audit" variant="success" /> logged.

</div>
<div class="wb-option">

### B. Prompt for everything

Keep S07-egress-gateway as it is.

- **Cost:** a burst of prompts when every VM starts, which teaches users to click allow.
- **Keeps:** <Badge text="SEC05-default-deny" variant="caution" /> as long as users keep saying no.

</div>
<div class="wb-option">

### C. Allow them

Put Apple's background services on the default allowlist.

- **Cost:** the guest talks to iCloud and push services, a channel out of the guest that nobody asked for.
- **Weakens:** <Badge text="SEC05-default-deny" variant="danger" /> needs a spec change.

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> Lease 4.7 to 5.7 s after the VM started, median 4.9 s, on 11 cold boots, with only the file-handle attachment. Source: X03-network-path, "Measurements", and the `*-netd.jsonl` logs on the spike branch.
- <Badge text="verified" variant="success" /> Allowlisted `A` queries got a synthetic address, `AAAA` an empty answer, and other names `NXDOMAIN`. DNS to another server timed out or was reset. TCP outside a synthetic address and allowed port was reset. Only the gateway answered ping. UDP other than DNS and IPv6 were dropped. Source: `results/run1-mtu1500-probe.txt`.
- <Badge text="verified" variant="success" /> The `wb-vmd` stand-in had only the virtualization entitlement, the `wb-netd` stand-in none. Source: `results/entitlements.txt`.
- <Badge text="verified" variant="success" /> With the ARP rule of the filter off, the guest declined every lease as an address conflict and never got an address. With the ICMP rule off, gVisor still didn't answer ping to other addresses. Source: `results/run11-*` and `results/run12-*` on the spike branch.
- <Badge text="verified" variant="success" /> Download throughput and CPU time at MTU 1500, 9000 and 65535. Source: X03-network-path, "Measurements".
- <Badge text="verified" variant="success" /> The idle guest's names. Source: `results/run6-idle-hour-netd.jsonl`.
- <Badge text="assumed" variant="caution" /> That `wb-proxyd`, which terminates and re-originates TLS, costs more than the stack, so the stack isn't the limit. X04-tls-inspection measures inspection.
- <Badge text="assumed" variant="caution" /> That the macOS resolver behaves the same when `HTTPS` and `SVCB` get an empty answer as when they were refused, as in the spike. S11-verification-and-spikes checks it.
- <Badge text="assumed" variant="caution" /> That a guest with a logged-in user and tools installed adds names to the idle list but no new kind of traffic.

## What it unblocks

The `wb-netd` work in S07-egress-gateway, and the conformance cases of S11-verification-and-spikes for the packet path. Decision 2 feeds the approval design (B51-approval-flow) and the image (X17-image-build).

<details>
<summary>Details and glossary</summary>

**Why the stack needs a filter.** Each allowlisted name gets its own made-up address from 198.18.0.0/15, so `wb-netd` must accept connections to thousands of addresses it doesn't own. gVisor does that in promiscuous mode, and spoofing mode lets it answer from them. With spoofing on, gVisor also answers "that's me" to an ARP question about any address. The guest asks that question about its own new address, to check nobody else has it, and with the answer it gave the address back and asked again, every 12 s, without end. The filter passes ARP only for the gateway, ping only to the gateway, and UDP only to DNS and DHCP. gVisor didn't answer ping to other addresses even without the filter, so the ping rule is a second layer.

**What Claude Code looked up.** With a placeholder key, `claude -p` looked up only `api.anthropic.com`. Started interactively it also looked up `raw.githubusercontent.com` and `platform.claude.com`. The stub didn't speak TLS, so anything after the first API call is not in the list.

**Not measured.** TLS inspection, a real upstream, more than one VM, and a restored VM.

- **MTU:** maximum transmission unit, the largest packet a link sends in one frame.
- **DHCP:** how a machine gets its address, router and DNS server when it joins a network.
- **ARP:** how a machine on a local network finds which network card has an IP address.
- **Synthetic address:** a made-up address from a reserved range that `wb-netd` hands out for an allowlisted name, so the guest never learns the real one.
- **Promiscuous and spoofing mode:** gVisor settings that let the stack accept and send traffic for addresses that aren't its own.
- **NTP:** the protocol computers use to set their clocks over the network.

</details>

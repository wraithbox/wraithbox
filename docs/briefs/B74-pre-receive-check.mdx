title: Can Wraith Box refuse a bad push before any of it reaches the landing repository, and before it uses up the host's memory?
description: Yes, with conditions. A pre-receive check that Wraith Box ships keeps refused pushes out of the landing repository, and a Go pack scanner in front of git caps object sizes before git allocates memory for them.

**Answered 2026-10-05. Decided 2026-10-06: A, scanner and check, with fixed caps.** The decision and its reasons are in the I74 comment that starts `Decision (2026-10-06):`. Source: X26-pre-receive-check (I74). Changes S08-workspace-and-git and S11-verification-and-spikes. The scanner's scope waits on I102: if `GIT_ALLOC_LIMIT` makes git refuse an oversized delta before it allocates the memory, the per-object bound comes from git.

<Aside type="tip" title="What we learned">
**Yes, with conditions.** A `pre-receive` check that Wraith Box ships refused every bad push tried, and none of their objects reached the landing repository. It runs too late to protect memory: an 8 KiB push made git use 2 GiB first. A small Go scanner in front of git refuses oversized objects before git sees them. The maintainer decided on I74 to add the scanner, with the caps as proposed (100 MiB per object, 1 GiB per push, 1,000,000 objects) and fixed, not configurable, until a real repository needs more. The S08-workspace-and-git changes keep the old cleanup as a fallback.
</Aside>

## Options

The issue asked about the check alone. The spike found that it can't bound memory, so the options are what to combine.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Scanner and check

The Go scanner caps object sizes before git sees them. The check repeats git's late ref checks while the objects are in quarantine. The cleanup stays for the rare late failure.

- **Cost:** two small Go components, one new fuzz target. About 0.02 s on a normal push.
- **Gives:** bounded memory (207 MiB peak in `index-pack` at a 100 MiB cap), a refused push adds nothing to `landing.git`.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="success" /> <Badge text="SEC03-no-host-exec" variant="success" />

</div>
<div class="wb-option">

### B. Check alone

What the issue proposed.

- **Cost:** one small Go program. It reads only git's output, not the pack.
- **Gap:** git still allocates whatever a delta asks for before the check runs: 2 GiB from an 8 KiB pack, and more is possible. macOS refuses a memory limit on the git process.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="danger" /> memory unbounded

</div>
<div class="wb-option">

### C. Scanner alone

Cap sizes, leave the ref checks to git and the cleanup.

- **Cost:** one Go component with a fuzz target.
- **Gap:** refused pushes still leave objects in `landing.git` until the cleanup runs, and three ref clashes that git accepts leave inconsistent refs.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="success" />

</div>
<div class="wb-option">

### D. Scanner and a reftable landing repository

Store refs in git's newer reftable format, which has no file names to clash.

- **Cost:** the user's git needs 2.45 or later for `wb land`.
- **Gap:** stale old IDs and directory/file clashes still fail late, and it applied half of one push.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="success" />

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> Without a check, git refused ten bad pushes only after moving their objects into the landing repository: a ref too long for the file system, a component too long for its lock file, three stale or wrong old IDs, three directory/file clashes, two case clashes. With the check, all were refused and nothing was left. Same results with git 2.56.0 and Apple git 2.54.0. Source: X26-pre-receive-check, "Cases", `results/run1-homebrew.txt` and `run2-apple.txt`.
- <Badge text="verified" variant="success" /> Git accepted three pushes that leave refs inconsistent on a case-insensitive disk (a packed-ref directory clash, `DIR/y` beside `dir/x`, `MAIN` beside a packed `main`). The check refused them. Source: same.
- <Badge text="verified" variant="success" /> Delta results of 256 MiB to 2 GiB from 8 KiB packs took 271 to 2,063 MiB of memory in git, before the hook ran. The scanner refused each in 0.03 s. Source: X26-pre-receive-check, "Memory while git unpacks".
- <Badge text="verified" variant="success" /> `ulimit -v` and `ulimit -d` fail on macOS 27.0.1 with "Invalid argument". Source: same.
- <Badge text="verified" variant="success" /> A leftover lock file still fails a push after the check passed, leaving objects, so the cleanup stays. Source: X26-pre-receive-check, "Cases".
- <Badge text="verified" variant="success" /> A check for objects no ref reaches refused a normal thin push on its second push. It stays out of the recommendation. Source: `results/run3-thin-homebrew.txt` and `run4-thin-apple.txt`.
- <Badge text="verified" variant="success" /> Cost: the check alone 0.01 to 0.02 s on a one-commit push, 1.1 to 1.2 s on the Go repository's whole history. The scanner reads about 0.8 GB of inflated data per second. Source: X26-pre-receive-check, "Cost".
- <Badge text="verified" variant="success" /> The spike's scanner held each entry with no limit on its wire bytes: a blob of size 1 followed by 512 MiB of empty zlib blocks took its heap to 2,055 MiB. S08-workspace-and-git now caps wire bytes per entry and per pack. Source: the code review of PR88, at spike commit `077a8da`.
- <Badge text="inferred" variant="note" /> Without `receive.unpackLimit=1`, small pushes go to `unpack-objects --strict`, which keeps their trees and commits in memory. A pack header declaring 10 million objects costs `index-pack` about 500 MiB, so the count cap is 1,000,000. Source: the security review of PR88, from reading git. Not measured here, and S11-verification-and-spikes adds a case for each.
- <Badge text="assumed" variant="caution" /> That the delta layouts tried cover how git allocates while unpacking. The peak was measured, not derived from git's source. The conformance case in S11-verification-and-spikes checks it again on every release.
- <Badge text="assumed" variant="caution" /> That the `wb-git-receive` sandbox profile (X23-sandboxed-daemons) can allow the check program to run. Not built yet. I67 is the related open issue for the fetch side.

## What this unblocks

- The git gateway in `wb-hostd`, towards V1-M4-claude-end-to-end. S08-workspace-and-git has no open point left on push sizes.
- I41 item 6: the landing size cap must also cover objects that successful pushes leave unreachable.

<details>
<summary>Details and glossary</summary>

**Why the check alone can't bound memory.** A pack stores most objects as deltas: "take that object, copy these ranges". The start of each delta says how big the result will be, and git allocates that much to apply it, while it unpacks. A hook runs only after unpacking. A delta of a few kilobytes of copy instructions can ask for gigabytes. The scanner reads those size fields as the pack streams in and refuses before git sees the entry.

**Why the cleanup stays.** Some failures happen inside git's final ref update, after the objects moved: a lock file left by a crashed process, a disk error. The check can't foresee those, so the existing repack-and-prune after a refused push remains.

**Glossary**

- **Quarantine:** a temporary directory git unpacks a push into. Git deletes it if a `pre-receive` hook refuses the push.
- **`pre-receive` hook:** a program git runs once per push after unpacking, before updating refs. Here it comes from a directory Wraith Box owns, never from the repository.
- **Delta:** an object stored as copy instructions against another object.
- **Thin pack:** a push whose deltas use objects the receiver already has.
- **Reftable:** a newer git format that stores refs in one file instead of one file per ref.

</details>

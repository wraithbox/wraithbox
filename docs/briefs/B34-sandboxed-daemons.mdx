title: Can the Go daemons confine themselves on macOS?
description: Yes, with conditions. Each daemon applies its own Seatbelt profile in process, and wb-hostd starts the other daemons through an unconfined launcher, because a confined process can't confine its children further.
---

**Answered 2026-10-04. Decided 2026-10-04: A, the `wb-launcher`, with the `wb-git` shim.** Source: X23-sandboxed-daemons, I34. Affects S04-architecture and S12-platforms. The `wb-proxyd` Keychain part is I61.

<Aside type="tip" title="What we learned">
**Yes, with conditions.** Each Go daemon can confine itself, but its children can't confine themselves any further. You choose how `wb-hostd` starts the other daemons. Recommended: a small unconfined launcher under strict conditions (option A), which also starts git with its own profile. Accepting merges the S04-architecture and S12-platforms changes here.
</Aside>

## Options

The spike settled the mechanism: an in-process profile, without cgo. The real choice is how `wb-hostd` starts the other daemons.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. A launcher started before wb-hostd confines itself

`wb-hostd` starts a launcher, `wb-launcher`, first, then confines itself. Later it asks `wb-launcher` for each daemon (`wb-vmd`, one `wb-netd` per VM, `wb-proxyd`) and hands it their descriptors. `wb-launcher` starts only those programs, and each confines itself first thing. It must hold to these conditions, which the spike's looser launcher didn't:

- a separate standard-library-only program, not `wb-hostd` started in another mode;
- requests over a `SOCK_SEQPACKET` or `SOCK_DGRAM` socketpair inherited at start, one fixed-format request per message, with unexpected descriptors closed and the request refused;
- no arguments and a fixed environment for each program, with one bounded exception for `wb-git` (below);
- profiles and their parameters compiled into each program, or taken from configuration `wb-hostd` read before it confined itself, never from a request;
- a table of absolute paths in the installed bundle, never under `<config>`, `<data>` or `<logs>`, which the launcher checks;
- an instance cap per program.

git starts the same way, as a `wb-git` shim that applies a profile for one repository and then runs git (recommended, not tried). The table has two fixed entries, `wb-git-receive` and `wb-git-upload`, so the git subcommand is never a free string. Besides its program, the request holds one field, the repository. `wb-launcher` accepts it only if it equals, after cleaning, `<real path of the projects root>/<id>/<basename>`, with a valid `<id>` and `<basename>` either `landing.git` or `export.git`. The launcher takes the root's real path once, at start, and never resolves the request string, which could follow a planted symbolic link. The shim repeats the check before it confines itself. Seatbelt matches resolved paths, so a link swapped in after the check is denied (reproduced in the security review on PR65). Instead of a path, `wb-hostd` could hand over a directory descriptor that the launcher checks with `F_GETPATH`.

The fallback is git as a child of `wb-hostd` under its profile, as the spike ran it. A git bug then reaches every project's policy, the approvals in `state.db`, other projects' landing repositories, and the audit log. If you choose it, that goes into T00-index as an accepted residual risk.

- **Cost:** one small process with no profile (the spike's was 165 lines, test code included), plus the `wb-git` shim. The launcher becomes the parent that sees the daemons exit, which the I48 supervision change must cover, including what happens when `wb-hostd` restarts.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" />

</div>
<div class="wb-option">

### B. Children inherit the wb-hostd profile

`wb-hostd` starts the daemons directly. Each runs under the `wb-hostd` profile, which must then allow what every daemon needs.

- **Cost:** no launcher. `wb-netd`, which parses raw guest frames, gets the `wb-hostd` directories and the `wb-proxyd` network rules. That breaks the S04-architecture promise of "no filesystem and no network" for `wb-netd`.
- **Weakens:** <Badge text="SEC12-least-privilege" variant="danger" />

</div>
<div class="wb-option">

### C. wb-hostd stays unconfined

Only `wb-netd`, `wb-proxyd` and `wb-vmd` confine themselves. `wb-hostd` starts them directly, as now.

- **Cost:** no launcher. `wb-hostd` terminates the host-guest socket and runs git on guest pushes, and a bug there reaches every file of the user. S04-architecture says `wb-hostd` gets only its state directories, so this needs a spec change.
- **Weakens:** <Badge text="SEC12-least-privilege" variant="danger" />

</div>
<div class="wb-option">

### D. Each daemon as its own launchd job

`wb-hostd` asks launchd to start each daemon. They aren't its children, so each can confine itself.

- **Cost:** launchd can't pass the guest socket and network descriptors to a job. Each daemon connects back to `wb-hostd` to get them, `wb-netd` needs a launchd job per VM, and the confined `wb-hostd` needs rules to talk to launchd. The spike didn't try this option.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="caution" />

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> A Go program that calls `sandbox_init_with_parameters` in `main`, without cgo, keeps goroutines, garbage collection, preemption, timers, `crypto/rand` and ECDSA working under `(deny default)`, and is denied every file open, `stat`, connect, listen, DNS lookup, and program start. The profile covers all 32 OS threads tried (X23-sandboxed-daemons, "What a confined Go program can still do").
- <Badge text="verified" variant="success" /> A `wb-netd` stand-in on gVisor moves 4 streams of 64 MiB each way over an inherited socket and hands each stream to a proxy with `SCM_RIGHTS`, at the same throughput confined as unconfined: 438 against 420 MiB/s, medians of 5 (X23-sandboxed-daemons, "wb-netd: gVisor over inherited descriptors").
- <Badge text="verified" variant="success" /> Denying the `hw.ncpu` read makes Go 1.27 set `GOMAXPROCS` to 1 within seconds and cuts that throughput to 258 MiB/s. The runtime re-reads the CPU count every second (`runtime/cgroup_stubs.go`, `sysmonUpdateGOMAXPROCS` in `runtime/proc.go`). An explicit `runtime.GOMAXPROCS` call before confining turns that off: it stays at 8 under a bare `(deny default)` (437 MiB/s, median of 3). The security review on PR65 found this.
- <Badge text="verified" variant="success" /> Paths pasted into generated profile text let a crafted path turn the profile off (reproduced in the security review on PR65). Paths go in as parameters instead.
- <Badge text="verified" variant="success" /> A child of a confined process can't apply its own profile. The kernel logs `deny(1) forbidden-sandbox-reinit` and the call fails with "Operation not permitted". Through a launcher started before confinement, the child's profile applies.
- <Badge text="verified" variant="success" /> Under its profile, a `wb-hostd` stand-in reads its configuration, writes and locks its state file, appends to its log, serves its Unix socket, and runs a git push and clone into a landing repository with Homebrew git and with the Xcode git binary. Writes to its configuration, files outside its directories, and network connections are denied.
- <Badge text="verified" variant="success" /> `sandbox-exec` needs extra rules to start a Go binary at all: running and reading it, `/usr/lib`, the dyld cache, and the `sysctl` values the runtime reads at start.
- <Badge text="verified" variant="success" /> Apple's SDK header marks `sandbox_init` "No longer supported" since macOS 10.8, and the `sandbox-exec` man page says "DEPRECATED". Both work on macOS 27.0.1.
- <Badge text="inferred" variant="note" /> The launcher doesn't give an attacker in `wb-hostd` any right it lacks today, but only while the conditions under option A hold. `wb-hostd` already starts these programs, and each one confines itself before it reads anything `wb-hostd` sends. The spike's launcher didn't meet them: it passed on arguments and the profile from `wb-hostd`, so a compromised `wb-hostd` could have started an unconfined `wb-netd` (code review on PR65).
- <Badge text="assumed" variant="caution" /> That the `wb-git` shim works with a profile for one repository. Not built in the spike.
- <Badge text="assumed" variant="caution" /> That Apple keeps `sandbox_init_with_parameters` working in later macOS versions. Apple doesn't promise it.
- <Badge text="assumed" variant="caution" /> That `wb-vmd` can confine itself with the Virtualization framework running. Not tested: I64.

<details>
<summary>Details and glossary</summary>

**Why in process, not `sandbox-exec`.** With `sandbox-exec`, the profile is in force before the program is loaded. It must then also let the process read the system libraries and run its own binary, until the process exits. In process, the call comes after loading, and the profile only allows what the daemon does from then on. It also keeps the profile inside the binary, so the parent can't swap it. That last point follows from the design and was not tested.

**Why no cgo.** cgo would make each macOS build need a C toolchain for macOS and stop cross-compiling from Linux or Windows. The spike calls the function through a few lines of Go assembly, the way the standard `golang.org/x/sys/unix` package calls the C library on macOS. That links to a function in package `syscall` (`syscall6`) which Go keeps for `golang.org/x/sys` and lets other packages use (`syscall/syscall_darwin.go` in Go 1.27, go.dev/issue/67401). A later Go release could restrict that, and the build would then fail rather than run unconfined.

**Why git gets its own profile.** The git gateway runs `git upload-pack` and `git receive-pack` on data the guest sends. Under the `wb-hostd` profile, a bug in git reaches everything in the `wb-hostd` directories: policy, approvals, every landing repository, the audit log. A `wb-git` shim with a profile for one repository limits it to that repository. Either way, git runs without the user's git configuration, and the profile allows only the git installation (`bin/git`, `libexec/git-core/`, `share/git-core/` and the libraries git links), not all of `/opt/homebrew`.

**A gap this found.** `wb-hostd` can't read the user's repository under its profile, which S08-workspace-and-git needs for the project clone. I67 has the options.

**Glossary**

- **Seatbelt:** the macOS kernel sandbox. A profile is a list of rules ("deny everything, allow reading this directory") in a small Lisp-like language.
- **`sandbox_init_with_parameters`:** the C function that applies a profile to the calling process. Nothing can remove it afterward. `sandbox-exec` is the command-line tool that applies one and then starts a program.
- **cgo:** Go's way of calling C code. It needs a C compiler for the target platform at build time.
- **`GOMAXPROCS`:** how many CPU cores the Go runtime uses at once.
- **Descriptor, `SCM_RIGHTS`:** a handle to an open socket or file, and the Unix mechanism that passes one to another process.
- **gVisor:** the userspace network stack `wb-netd` runs (S07-egress-gateway).

</details>

## What changed since I145 and I146

The design in this pull request differs from what those issues say today:

- **The host keeps the password.** I145 option 4 had `wb-guestd` set a random password at first contact that nobody keeps, and accepted a dead secure token as better for SEC11-root-gains-nothing. Now the host keeps that password, and the token keeps working. The argument changed: the host already has guest root through `wb-guestd`, so a guest admin password it holds is no escalation, and SEC11-root-gains-nothing is about guest root reaching the host.
- **One password per VM, not per image.** Every VM is a clone of the image, so `wb-guestd` rotates the password at each VM's first contact. The build's provisioning password is the first one, retired by the build VM's rotation.
- **Break-glass.** The password also serves a console login when `wb-guestd` is dead or wedged. Piping it into a guest that has run project code burns it.
- **I146 option 1B is dropped.** A second admin created to delete the first only renames the token holder. `wbprov` stays in the image as a host-administered account. Whether it stays in `admin` is open question 3.
- **I142 narrows.** It no longer has to prove the token dead. It has to show that guest root can't extract the host-held password, or reset its way into the token.

## Options

### Decision 1: how SEC12 treats a credential that must be shared

<div class="wb-options">
<div class="wb-option" data-recommended>

#### A. One nominal holder, named sharing paths

SEC12-least-privilege says each credential is nominally held by one process and reaches others only along paths S15-least-privilege names, with recipients, channel, and lifetime. The guest admin password is the worked example, kept by the host per VM.

- **Cost:** a crossing table to keep current. Each new path is a spec change.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" /> <Badge text="SEC11-root-gains-nothing" variant="success" /> <Badge text="SEC04-no-guest-secrets" variant="caution" />

</div>
<div class="wb-option">

#### B. Keep "exactly one", with named exceptions

I145 options 1 to 3: the wording stays, and the build password becomes a written exception in SEC00-index and S04-architecture.

- **Cost:** every later case (`wb cred set`, OAuth refresh, break-glass) needs an exception of its own, and the rule stops describing what the code does.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="caution" />

</div>
<div class="wb-option">

#### C. Discard the password, dead token

I145 option 4 as first written: nobody keeps the password, and the secure token stops working.

- **Cost:** no break-glass login. No volume owner is left, so nothing can authorize a change that needs one.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" /> <Badge text="SEC11-root-gains-nothing" variant="success" />

### The open questions in S15-least-privilege

Each has a leaning. Approving the spec accepts the leanings unless you say otherwise.

1. **Build pipes.** `wb-hostd` creates a pipe each for the build's `wb-vmd` and SSH client, and `wb-launcher` hands the read ends over at spawn. The alternative, a gRPC field, breaks rule 3. Needs X25-vmd-sandbox decision 2 and I139.
2. **After break-glass.** Leaning: replace the VM's system disk with a fresh clone at its next stop, which keeps the data disk and rotates at first contact. Rotating in place gives the new password to a guest that may be rooted.
3. **Break-glass delivery, and `admin`.** Leaning: `wb vm console` shows the password once, and the user types it. Is `wbprov` kept in `admin`, enabled, and with a shell? A console login may need all three. Today's sealing scan requires it disabled, hidden, without a shell and out of `admin`.
4. **`wb cred set`.** Leaning: `wb` passes the value to `wb-proxyd` on a descriptor, and `wb-proxyd` writes the secret store item, so `wb-hostd` never sees it. Bindings name their OAuth token endpoint.
5. **Passwords in host remote URLs.** Leaning: remove user name and password from withheld URLs too, before their audit record.

### Questions for you

- **S01-spec-based-development.** Should it record the "one spec per security requirement" approach now, or after you have reviewed this first one? This pull request doesn't change S01.
- **SEC04-no-guest-secrets.** The guest admin password enters its own guest at first contact and at break-glass. Should SEC04 say that a credential which opens nothing outside its own VM is outside its scope, or is S15-least-privilege rule 6 enough?
- **Length.** S15-least-privilege is about 270 lines, against the 100-line aim of S01-spec-based-development. Is that the right size for a spec per security requirement, or should the crossing table move to its own page?
- **I142 and I146.** Should their bodies be updated to the narrowed question and the dropped option, or closed and filed again?

<summary>Details and glossary</summary>

**Why "nominally".** A credential always spends some time somewhere else: in the OS service that stores it, in the TLS connection that sends it, or in the guest that has to check it. "Held by exactly one process" can't be true of any of them. S15-least-privilege keeps one process responsible for each credential and makes every other place it goes a named path with a channel and an end.

**The rules, short.** Named in advance, random and narrow, descriptors or standard input only, audited without the value, dropped or burned and replaced, and into a guest only before project code or as a burn.

**Why the host may keep the guest's admin password.** `wb-guestd` runs as root in the guest and does what the host asks, so the host is already the guest's administrator. The password adds the secure token, which lets a volume owner approve changes such as turning off System Integrity Protection. Only the host can use it, and a password burned in one VM opens nothing in another.

**Crossings still open.** How `wb cred set` hands a value to `wb-proxyd` (question 4), passwords in withheld remote URLs (question 5), and the Claude subscription login (X01-model-credential).

**Glossary**

- **Nominal holder:** the one process responsible for a credential, which reads it, uses it, and decides who else may see it.
- **Secure token:** a macOS account property that lets the account unlock the disk and approve changes to it. The first account on a volume gets it.
- **Volume owner:** an account with a secure token, which macOS asks before changes to the startup disk's security.
- **Break-glass:** an emergency way in, used when the normal one (`wb-guestd`) is broken, and treated as compromising the password.
- **Descriptor:** a handle to an open pipe or socket that one process can pass to another. The data then goes straight between them.
- **Burned:** a credential that reached a place that may be hostile, and is replaced before it is used again.

</details>

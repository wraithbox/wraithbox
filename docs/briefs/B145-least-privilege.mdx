## What changed since the first draft

Four rounds of changes, all from you on 2026-10-07. The design differs from what I145 and I146 say today.

- **The host keeps the guest admin password.** I145 option 4 had nobody keep it, and accepted a dead secure token. Now the host keeps it, and the token keeps working. The host already has guest root through `wb-guestd`, so that is no escalation, and SEC11-root-gains-nothing is about guest root reaching the host. One password per VM: every VM is a clone of the image, so the password is rotated at each VM's first contact, and a password burned in one VM opens nothing elsewhere. I146 option 1B is dropped, because a second admin only renames the token holder.
- **The store is the holder, not a Wraith Box process.** The first draft made `wb-proxyd` the nominal holder of every credential, which gives the process that faces guest streams every secret. Now the configured secret store holds them, the macOS Keychain first, 1Password next, other backends later. `wb-proxyd` fetches only what proxying needs. The guest admin user is renamed `wbadmin`, and a short-lived `wb-guestadmin` generates, writes and rotates its passwords, without `wb-proxyd`.
- **I142 narrows.** It has to show that guest root can't extract the host-held password or reset its way into the token.
- **Specs carry no review material.** On review, you set the rule that a spec states only the design. S15-least-privilege lost its "For review" and "Open questions" sections, each leaning became its design, and this brief and I151 to I156 carry the rest. S01-spec-based-development's template, the `spec-draft` and `brief` skills, `review-briefs.md` and `planning.md` follow. `wb-guestadmin` became a process of its own in S04-architecture.
- **Break-glass replaces the disk.** You decided I156 as option C. In v1, break-glass replaces the VM's system disk, nobody logs in, and `wbadmin` stays disabled, hidden, without a shell and out of `admin`, so the sealing scan is unchanged. The host still keeps the per-VM password, for rotation and a later diagnostics path. Developer break-glass through recoveryOS is I158.

## Options

### Decision 1: where credentials are held

<div class="wb-options">
<div class="wb-option" data-recommended>

#### A. The store, with declared access per process

Each process has a declared set of store items and an access kind for each. A backend must keep Wraith Box items apart and scope them per process. It fails closed when locked. A weaker backend runs only when you turn it on by name.

- **Cost:** a store access shim in each declared process, and a table to keep current.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" /> <Badge text="SEC11-root-gains-nothing" variant="success" /> <Badge text="SEC04-no-guest-secrets" variant="caution" />

</div>
<div class="wb-option">

#### B. wb-proxyd holds every credential

The first draft, and S04-architecture as written. Other processes get their secrets through `wb-proxyd`.

- **Cost:** a compromise of `wb-proxyd` through a guest stream reaches every secret, the guest admin passwords included.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="caution" />

</div>
<div class="wb-option">

#### C. Discard the guest admin password

I145 option 4 as first written: nobody keeps it, and the secure token stops working.

- **Cost:** no volume owner left, and no later diagnostics or recovery path (I158).
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" /> <Badge text="SEC11-root-gains-nothing" variant="success" />

</div>
</div>

### Open points and their issues

S15-least-privilege states each leaning below as its design, because a spec carries no open questions (S01-spec-based-development, "Spec template"). The points and what each relies on are listed here instead, with the issue that tracks each one that still needs work.

1. **Who builds and rotates.** `wb-guestadmin`, a short-lived program started through `wb-launcher`, with access to `wbadmin/*` items only, now a process of its own in S04-architecture. The alternative, `wb-hostd`, would give store access to the process that runs the host-guest socket handlers.
2. **The build's `ssh`.** `wb-guestadmin` pipes the password, through an askpass program that reads an inherited descriptor, and to `sudo -S` on the session's standard input. The alternative is a `wb-askpass` helper that reads the store itself, which adds a store reader. Which network carries the session stays with I139.
3. **Break-glass.** When `wb-guestd` is dead or wedged, `wb-hostd` replaces the VM's system disk with a fresh clone. The data disk stays, and first contact rotates again.
4. **Break-glass login, and `admin`.** Decided on I156, option C: in v1 nobody logs in, no password is fetched, and `wbadmin` stays disabled, hidden, without a shell and out of `admin`. Developer break-glass through recoveryOS with the volume owner's password is I158.
5. **Unlocking the dedicated keychain.** With signed builds, the data protection keychain with an access group per role. Until then, a dedicated keychain file whose password is the one Wraith Box item in the login keychain. G2 on the Keychain waits for X09-keychain-unsigned and I61.
6. **1Password.** The desktop app integration, with a vault per role, and a license check of the client first: I151.
7. **Passwords in host remote URLs.** Removed from withheld URLs too, before the audit record: I152.
8. **OAuth token endpoint.** A binding names its token endpoint, so the refresh token goes only to a declared recipient: I153.
9. **`wbadmin` rotation on standard input.** Relies on `sysadminctl` reading both passwords from standard input, and on a disabled account authorizing its own reset: I154.
10. **The provisioning password in the bundle.** Relies on Virtualization not writing it into the build bundle, which the build's test checks: I155.
11. **Guest root and the secure token.** Relies on guest root being unable to extract the host-held password or reset its way into the token: I142.
12. **The Claude subscription login** stays with X01-model-credential.

<summary>Details and glossary</summary>

**Why "nominally".** A credential always spends some time somewhere else: in the process that injects it, in the TLS connection that sends it, or in the guest that checks it. S15-least-privilege keeps the store as the one place a credential lives, and makes each other place a declared access with a kind, a channel, and an end.

**Fetch and use.** A fetch brings the value into the process. With a use, the store signs or decrypts in place and keeps the value. The Secure Enclave CA key and 1Password's SSH agent work that way, and S15-least-privilege prefers use wherever the store allows it.

**Why the host may keep the guest's admin password.** `wb-guestd` runs as root in the guest and does what the host asks, so the host is already the guest's administrator. The password adds the secure token, which lets a volume owner approve changes such as turning off System Integrity Protection.

**Glossary**

- **Secret store:** the place credentials are kept, for example the macOS Keychain, or a 1Password vault.
- **Declared access:** an entry in S15-least-privilege that lets one process write, fetch or use one kind of store item.
- **Secure token:** a macOS account property that lets the account unlock the disk and approve changes to it.
- **Break-glass:** the emergency path when `wb-guestd` is broken. In v1 it replaces the VM's system disk, and nobody logs in.
- **Descriptor:** a handle to an open pipe or socket that one process can pass to another. The data then goes straight between them.
- **Burned:** a credential that reached a place that may be hostile, and is replaced before it is used again.

</details>

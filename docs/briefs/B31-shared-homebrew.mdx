**Answered 2026-10-07: yes, with conditions. Awaiting decision.** Source: X20-shared-homebrew (I31). Changes S06-vm-lifecycle ("Images" only), S11-verification-and-spikes and T00-index (T15-shared-toolchain). Confirms I144 for how projects add packages, and builds on I150. Follow-up: I180 (the three untested conditions, in a guest).

<Aside type="tip" title="What we learned">
**Yes, with conditions.** One Homebrew prefix, `/opt/homebrew`, that belongs to the toolchain user works. `wb-guestd` installs every project's declared packages into it as that user. A project user can run them but couldn't change any file or install anything, and the agent runs as that project user. The catch is the Brewfile, which is a Ruby program. Run by `brew bundle` as the toolchain user, a Brewfile planted a file in the prefix every project runs from. So the host reads the manifest as a list of package names and refuses anything else. Installing a realistic project took 3 minutes. A prefix in each project's home doesn't work in practice: Homebrew set out to build nine of the project's packages and LLVM from source there, and was still going after 51 minutes. The decisions are whether a project may have a prefix of its own anyway, and whether to refuse packages without a prebuilt bottle.
</Aside>

## Decision: may a project have a prefix of its own?

The shared prefix covers what projects declare. A prefix per project would let the agent run `brew install` itself, and would keep one project's versions out of another's way.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Shared prefix only

Every project's declared packages go into `/opt/homebrew` through `wb-guestd`. Projects with conflicting packages use `--isolated`.

- **Cost:** the agent can't install Homebrew packages, only language packages in its home (`pip --user`, `uv tool`, `go install`, `npm` with a home prefix). A conflicting project needs the isolated VM.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="caution" /> with the manifest read as names.

</div>
<div class="wb-option">

### B. Also a short per-project prefix

Root makes `/opt/<id>`, at most 13 characters long, for the project and gives it to the project user. The agent can then install into it. All 59 packages of the test project poured in 230 s.

- **Cost:** a second Homebrew per project, 1.7 GB each, where A shares one copy of each package. Both are on the system disk, so after a new system disk each project's own packages are installed again in either option, and B has no packages from the image to start from. Homebrew failed to sign 8 static library files and carried on.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="success" />, since a project writes only its own prefix.

</div>
<div class="wb-option">

### C. A prefix in each home

`~/homebrew`, owned by the project user, with no help from root.

- **Cost:** 9 of the test project's 59 packages, plus LLVM, are built from source. Stopped after 51 minutes, unfinished.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="success" />, but isn't usable.

</div>
</div>

## Decision: refuse packages without a bottle?

A bottle is a prebuilt package. When a declared package has none for the guest, Homebrew builds it from source as the toolchain user, which runs more of the package's code and can take hours (LLVM above).

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Bottles only

`wb-guestd` checks that every package the names need has a bottle for the guest, names them all on the command line with `--force-bottle`, because Homebrew doesn't apply it to dependencies, and otherwise refuses the session with the package's name before anything is installed. The spec says this now.

- **Cost:** a package without a bottle for the guest's macOS can't be declared. A project that needs one installs it into its home with another tool, or waits for the bottle.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="success" /> <Badge text="SEC13-bounded-resources" variant="success" />

</div>
<div class="wb-option">

### B. Build from source

Homebrew builds what has no bottle, within the session start deadline, after which `wb-guestd` kills the build.

- **Cost:** slow starts, builds that fail at the deadline, and more code from `homebrew/core` run as the toolchain user (T15-shared-toolchain).
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="caution" /> on more trust in `homebrew/core`.

</div>
</div>

Not adopted: `HOMEBREW_VERIFY_ATTESTATIONS`, which has Homebrew check GitHub's build attestation of each bottle. It would bind bottles to Homebrew's own build workflow, and needs the `gh` command and more allowed hosts. The spike didn't try it, and it stays an option for later hardening of T15-shared-toolchain.

## Evidence

- <Badge text="verified" variant="success" /> The toolchain user (uid 440, shell `/usr/bin/false`, password `*`, outside the admin group) installed Homebrew 7.0.8 into the `/opt/homebrew` root made for it, with Homebrew's own installer and no `sudo`. Source: X20-shared-homebrew, "Answer" part 1.
- <Badge text="verified" variant="success" /> As a project user, every write to the prefix and `brew install`, `uninstall`, `link` and `update` failed, and `su` to the toolchain user failed. Only the toolchain user and its own group can write the prefix's files, and none is set-user-ID. Source: "Answer" part 2, `probe-shared.sh`, and `probe-shared-2.sh` for the `Cellar` write and `brew install tree`.
- <Badge text="verified" variant="success" /> `sudo -n -u _wbtool` was refused. That rules out a rule without a password only, and the S11-verification-and-spikes check `sudo -l -U` covers the rest. Source: "Answer" part 2.
- <Badge text="verified" variant="success" /> A Brewfile with a `system` line, run by `brew bundle` as the toolchain user, created a file in `/opt/homebrew/bin`. Source: "Answer" part 4.
- <Badge text="verified" variant="success" /> Older versions of the same packages installed side by side and ran from their own folders. `mysql` was refused while `mariadb` was installed. `python3` in the shared `bin` was 3.14 for a project that declared 3.13. Source: "Answer" part 5.
- <Badge text="verified" variant="success" /> Times: 179 s for the test project in the shared prefix, 66 s for a second project after it, under a second when nothing is new, 230 s in a short per-project prefix, unfinished after 51 minutes in a home prefix. Source: "Measurements".
- <Badge text="verified" variant="success" /> A symbolic link from a short path to the home doesn't help: Homebrew followed it and started building from source. Source: "Answer" part 7.
- <Badge text="assumed" variant="caution" /> That a reconcile never changes what another running session uses. `HOMEBREW_NO_INSTALL_UPGRADE` covers only the packages on the command line, so the control is the formula data pinned at image build. The spike didn't try it (condition 4, I180).
- <Badge text="assumed" variant="caution" /> That a session `PATH` with only the declared packages' folders, and not the shared `bin`, is enough for common tools, which the spike didn't try (condition 5, I180).
- <Badge text="assumed" variant="caution" /> That Homebrew keeps its temporary and cache files in the toolchain user's mode-700 home when told to, and not in the shared `/private/tmp`, which the spike didn't try (condition 7, I180).

## What it unblocks

I144 and I150 can write the toolchain user and the derived images into S06-vm-lifecycle with the shared prefix confirmed. The `wb-guestd` user and package work of the walking skeleton (V1-M2-walking-skeleton) can build on S06-vm-lifecycle, "Toolchain prefix".

<details>
<summary>Details and glossary</summary>

**Why a shared prefix is a risk at all.** Every project runs tools like `git` from the prefix. If project A could replace `/opt/homebrew/bin/git`, project B would run A's program the next time it commits, with B's files and B's network grants. That is persistence from one project into another without root, which SEC08-proj-isolation forbids.

**Why the Brewfile matters.** A Brewfile looks like a list, but Homebrew evaluates it as Ruby. Run as the user the prefix belongs to, any line can write anywhere in the prefix. Reading it on the host as `brew "<name>"` lines only keeps the common Brewfile working and drops the rest. Third-party taps are refused for the same reason: their package recipes are Ruby too.

**Why a home prefix builds from source.** Homebrew's prebuilt packages (bottles) are built for `/opt/homebrew`. Homebrew 7 can move most of them, but some have the path compiled in, and it can only rewrite that path into one of at most 13 characters, the length of `/opt/homebrew`. `/Users/wbp-b/homebrew` is 21. Those packages, Python, Node.js, OpenSSL, git and PostgreSQL among them, are then compiled, and Node.js needs Rust, which needs LLVM.

- **Prefix:** the folder Homebrew installs into, with `bin`, `Cellar` (one folder per package version) and `opt` (a stable link per package).
- **Bottle:** a prebuilt Homebrew package.
- **Keg-only:** a package Homebrew installs but doesn't link into the shared `bin`, for example an older version.
- **Tap:** a third-party collection of Homebrew package recipes.
- **Toolchain user:** the non-admin account of I144 that the prefix belongs to. The spike called it `_wbtool`, and the name is still open.

</details>

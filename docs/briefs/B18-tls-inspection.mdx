<Aside type="tip" title="What we learned">
**No.** In a macOS 27 guest, behind a stand-in for `wb-proxyd`, every tool that can be pointed at a CA file accepted the per-VM CA: curl, git, `gh`, Go, Node and `npm`, Python, `pip`, `uv`, Ruby, cargo, Java, Claude Code, and SwiftPM's git clones. None pins. But `wb-guestd` can't put the CA in the guest's system trust store: macOS refuses every way the spike tried without a user to click "allow". So URLSession clients, which read only that store, reject every inspected host: Swift programs, SwiftPM's binary target downloads, and Xcode's own requests. Of the clients tested, only Python's `requests` rereads trust while it runs, so the 28-day CA overlap stands. You decide how to treat URLSession clients (I185).
</Aside>

## Decision: URLSession clients on a macOS guest (I185)

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Accept it, and test B in a VM

URLSession clients reach only pass hosts. A host with a credential binding or a built-in profile, such as `github.com` or the model API, can't be a pass host, so they can't reach it. FR08-no-proxy-config is then amended to leave out URLSession clients on inspected hosts. Then test option B in a VM before deciding on it.

- **Cost:** Swift programs that call inspected hosts fail, and so do SwiftPM binary targets hosted on GitHub. It needs no code, but a requirement change.
- **Keeps:** <Badge text="SEC05-default-deny" variant="success" /> <Badge text="SEC06-repo-writes" variant="success" />, fails closed.

</div>
<div class="wb-option">

### B. Let guest root set trust

At image build, add `is-root` to the authorization right `com.apple.trust-settings.admin`, so root may set admin trust without a user. Guest root then gets admin trust over trustd and URLSession for every user in the guest. T05-cross-proj-clones already concedes that guest root reaches every project, and the CA has no name constraints (I39), so a root-made CA could vouch for any name. The whole control is the gap between `is-root` and `allow`: with `allow`, any user could change admin trust. The sealing scan compares the full rule and the rights next to it, at every seal and at first contact, because authd may rewrite its database on a macOS update.

- **Cost:** the supported tool refuses the change. The build would edit authd's database directly, which nobody has tried yet, and needs a VM test. trustd's own entitlement check may still refuse it.
- **Keeps:** <Badge text="SEC11-root-gains-nothing" variant="caution" /> changes one guest security setting, the maintainer's call.

</div>
<div class="wb-option">

### C. A profile through MDM

Deliver the CA as a configuration profile through MDM, which installs without a click.

- **Cost:** the guest must be enrolled, which needs a user's approval or Apple Business Manager. Not viable for local VMs (inferred).
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="caution" /> an enrollment identity in the guest.

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> `security add-trusted-cert -d`, `security authorizationdb write`, `trust-settings-import`, user domain trust and `profiles install` are all refused as root without a user, on macOS 27.0.1. Spike branch, `results/g1-requests.jsonl` (`trust.sh`, `trust-probe.sh`, `trust-supported.sh`).
- <Badge text="verified" variant="success" /> With every variable set, the Swift URLSession client and a SwiftPM binary target download reject the leaf, and every other client accepts it. `results/matrix-vars.jsonl`, `results/extras.txt`.
- <Badge text="verified" variant="success" /> Which single variable each client needs. `results/matrix-only-*.jsonl`, X04-tls-inspection, table.
- <Badge text="verified" variant="success" /> A bundle without the public roots breaks pass hosts for curl, Go, and Python. `results/extras.txt`.
- <Badge text="verified" variant="success" /> Only Python's `requests` accepted the successor CA in a process started before its install. Go, Node, `urllib`, Ruby and Java didn't. `results/reread.txt`.
- <Badge text="verified" variant="success" /> None of the clients that could be tested pins. URLSession and Xcode couldn't be tested for pinning. `results/matrix-vars.jsonl`.
- <Badge text="inferred" variant="note" /> Apple pins its own hosts: trustd's pinning rules in the guest list software update, `xcode-cdn.apple.com`, `mesu.apple.com` and others, so they would refuse an inspected leaf even with the CA in the system store. The spike couldn't put it there. `results/pinning-rules.txt`.
- <Badge text="inferred" variant="note" /> The six variables S09-policy-credentials-audit names work as a set. The spike ran eight together and each one alone, never these six alone.
- <Badge text="assumed" variant="caution" /> Option B works: that `add-trusted-cert` succeeds once the rule allows root, that trustd's entitlement check doesn't refuse it, that the rule is still there after a reboot and a macOS update, and that other users still need an admin. Untried, it needs a VM test (I185).
- <Badge text="assumed" variant="caution" /> Claude Code reads its trust once at start, like Node. It couldn't be run in a loop without an API key.
- <Badge text="assumed" variant="caution" /> The Java trust store of S09-policy-credentials-audit works: built by `wb-guestd` from the bundle, without a password. The spike tested the JDK's own roots plus the CA, built with `keytool`, with a password.

## What it unblocks

- `wb-guestd`'s CA install and the trust variables (S09-policy-credentials-audit, "Guest trust").
- `wb-proxyd` leaf issuing, which X04-tls-inspection blocked in `docs/implementation-plan.md`.
- I185, which decides URLSession clients on macOS guests.

<details>
<summary>Details and glossary</summary>

**How the spike ran.** A macOS 27 guest from the X17-image-build image, with the Xcode command line tools, Xcode 27.0 and Homebrew. A Go relay in the guest took the place of `wb-proxyd`, and pf in the guest sent every process's port 443 to it, so no tool had proxy settings. The relay signed a 24-hour leaf for each name with a CA of the S09-policy-credentials-audit profile, without name constraints. Each client ran three ways: without the CA anywhere, with all variables set, and with one variable at a time.

**Why "no".** The question names Swift-based and Xcode clients. Xcode's package resolution passes, because it clones over git. URLSession, the HTTP client of Apple's frameworks, reads only the system trust store, and nothing could put the CA there.

**Glossary.**

- *CA (certificate authority):* the certificate that signs others. A client accepts a server's certificate when a CA it trusts signed it.
- *Leaf:* the certificate a server shows. `wb-proxyd` signs one per inspected host name.
- *Trust store:* the list of CAs a client accepts. macOS keeps one for the system, and many tools read their own file instead.
- *Trust variable:* an environment variable that points a tool at a CA file, such as `SSL_CERT_FILE`.
- *Pinning:* a client accepts only the certificates it expects for a host, whatever CAs it trusts.
- *URLSession:* Apple's HTTP client, used by Swift programs and Apple's tools.
- *Authorization right:* a rule in macOS's authorization database that says who may do a protected action, here change trust settings.
- *MDM:* mobile device management, Apple's remote management of devices, which can install profiles without a click.

</details>

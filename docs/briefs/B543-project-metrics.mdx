## Wraith Box in brief

Wraith Box runs Claude Code, an AI coding agent, inside an isolated macOS virtual machine, with one command: `wb claude`. The controls run on the host, out of the agent's reach. The VM sees only its own disk and reaches only the destinations that a rule allows, and secrets stay on the host (S03-requirements). V1-initial is the first usable version, for macOS hosts and macOS guests.

One maintainer builds it part-time, in evenings and at weekends. Claude agents write nearly all the specs, code and tests, many of them at once. The maintainer sets the scope, approves each design decision, and runs the tests that need a real VM on their own Mac. The project started on 2026-10-03.

## What V1 is likely to be

**To spec: probably good.** The code that exists scores well on the usual leading indicators:

| Measure | Value | Reading |
|---|---|---|
| Test coverage | Go 82%, Swift 72% | Go is above Google's "commendable" 75%. Coverage is a floor, not proof |
| Fuzz targets on input from the VM | 41, on every host-side parser of guest bytes that exists | Wide, but shallow: one seed file, 10 seconds per target |
| Complexity | 0 functions over the limit of 15, out of about 2,500 | Enforced by CI |
| Rework | 95% to 97% of the lines added each build week are still there | Little churn so far |
| Follow-ups | about one bug or follow-up for every two items closed | Expect the same after the release |
| Flaky CI runs | under 2.5% a week, then 7.4% in the last week | The last week needs a look |

The weak spots are where defects are most likely. The network and policy code has the most input from the VM to parse, and none of it is written yet. Only the maintainer runs the tests that need a real VM, by hand, and the runs aren't recorded. And the same model writes the code and its tests, so a shared misreading of the spec passes CI.

**In use: uncertain, and nothing in the plan measures it.** V1's exit criteria cite requirements, and none of them is a person using it. Start time (NFR01-startup) and file speed (NFR02-fs-speed), the two things a user feels, were demoted from requirements to goals. The design changes the daily loop of working with an agent, on purpose:

- The editor on the host can't see the files during a session, because nothing is shared. Work comes back through `wb diff` and `wb land`.
- Each session starts in a new checkout of the repository, with your uncommitted changes but without ignored files such as installed dependencies.
- A website the rules don't yet allow waits for the user's approval. The first try fails unless the user approves within 4 seconds.
- A check of 10 real package installs refused 4, for package age or a known vulnerability (X21-dep-gate-registries).
- Starting a VM took 14 to 19 seconds against a 10-second goal (C11-host-daemons).
- `gh pr create` is refused inside the VM until its GitHub API call is added to an allowlist that starts empty (I502). So the way this project is itself built can't run inside V1 as planned. That list is cheap to change.

An agent that walked the first-run journey through the specs judged it about 80% likely that a plain session works end to end on day one, and 30% to 40% likely that the maintainer runs most Claude sessions through `wb` in the first month. Nobody has compared V1 with the real alternatives: Claude Code on the host with its own permission prompts, or a dev container.

## What it unblocks

The pace decides how many agent runs to plan each week and when to book the attended sessions. Record it as a comment on I543. The measurement itself is the answer of X32-project-metrics: it can be repeated, with conditions. Cost totals come from Claude Code's own cost records, because the transcripts miss about 30% of the calls. The maintainer's hours stay a range until a time log calibrates them. <details>
<summary>How the figures were made, and a glossary</summary>

**Method.** Agents measured the project in parallel, from git history, GitHub, the Claude Code transcripts on the maintainer's Mac, the source tree, the open issues and the specs. They published only aggregates, such as weekly totals and coverage. The transcripts, the raw GitHub data and the prompt text stay on the Mac, and no other project of the maintainer's is named. R09-v1-progress-and-quality has the details, and X32-project-metrics says how well each measurement worked.

**The maintainer's time** comes from the transcripts. The assumptions came from the maintainer: no effort on days without agent activity, more effort on days with more activity or bigger decisions, and little during weekday working hours. METR's method counts the 10-minute windows that hold a prompt (59 hours). A model adds reading time, pauses before long prompts and time per decision (27, 63 and 117 hours as low, mid and high). Neither sees thinking done away from the keyboard.

**The forecast** has two layers. The first replays the build phase's active days on two lanes, the serial VM lane and the parallel rest, until both are empty. The second turns active days into calendar dates, by drawing weeks from three attention patterns: faster (6 or 7 days), as before (the measured weeks, 5 to 7 days) and half (0 to 4 days, 2.4 on average). It starts on 2026-11-03.

**Glossary**

- **Active day:** a day with any agent activity. Every such day also had a prompt from the maintainer.
- **Agent-hour:** one agent working for one hour. Thirteen agents in parallel for an hour make thirteen agent-hours.
- **API list price:** what the tokens would cost when bought per token from the vendor's price list. A subscription costs a different amount.
- **Attended step:** a step that needs the maintainer at the Mac, such as running a VM test or setting up the host.
- **Fuzz target:** a test that passes random and malformed input to a parser, looking for crashes.
- **Line survival:** the share of the lines added in a week that are still there today.
- **METR method:** count the 10-minute windows that hold at least one human prompt, once across parallel sessions.
- **P50, P85, P95:** the dates by which 50%, 85% and 95% of the simulated runs finish.
- **Spike:** a small experiment that answers one design question, with a written result.
- **Token:** the unit that language models read and write, and are billed by.
- **VM lane:** the work that needs a running macOS VM. One builder at a time does it, so it runs in series.
- **Work unit:** the size of one finished package issue from V1-M2-walking-skeleton or V1-M3-network-floor, about 2,700 changed lines at the median. A small issue counts 0.3.

<Aside type="tip" title="What we learned">
**Yes, with conditions.** Git, GitHub, the Claude Code transcripts and the tree measure the project well enough to answer how far V1 is, what it costs, when it will be done and how good it is. The measuring agents ran in parallel and needed about a quarter of an hour. Their scripts run again on new data. The first report found that V1 is about 28% implemented. Its P50 is January 2027 at the current attention and April 2027 at half. It is likely good to spec, and nothing in the plan measures whether it's good in use. Conditions: cost totals come from Claude Code's `cost-state` records, human effort stays a range until a time log calibrates it, and raw data stays on your Mac. Recommended: do I544 and repeat the measurement at each milestone close.
</Aside>

## Options

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. At each milestone close

Do I544: an agent file, a `mise` task and a time log. Run the measurement when a V1 milestone closes, and add a short R note each time, or update R09-v1-progress-and-quality.

- **Cost:** I544 itself, then about 1 M agent tokens and an hour of coordinator time per run. You keep a time log of a line per sitting.
- **Gives:** a forecast that tightens as milestones close, a check on the plan's estimates at the point where the next milestone is cut, and calibrated human numbers.

</div>
<div class="wb-option">

### B. Monthly

The same as A, on the first weekend of each month.

- **Cost:** the same per run. Runs may fall mid-milestone, when the numbers say less.
- **Gives:** a steady series, independent of how milestones are cut.

</div>
<div class="wb-option">

### C. Only when asked

Skip I544. Keep the spike scripts, and run them by hand when you want a report.

- **Cost:** nothing now. Each run fixes paths and re-learns the traps: units, lane names, the 30% of cost that the transcripts miss.
- **Gives:** a report when you think to ask for one.

</div>
<div class="wb-option">

### D. Not again

Close I544 as not planned. R09-v1-progress-and-quality stays as a one-time snapshot.

- **Cost:** none.
- **Gives:** nothing more. The forecast ages within weeks.

</div>
</div>

**The case for C.** This is a hobby project, and a report costs about as much as one small issue. Most of its value came from findings, not numbers: the empty GraphQL allowlist, the missing use criterion and the plan's drift. A careful review at each milestone might find those without any measurement. A run on request keeps that option open without building anything.

Confidence in A: medium. A second run will show whether the forecast narrows and whether the findings keep coming. If the second report doesn't add anything new, drop to C.

## What it unblocks

I544, and the recommendations of R09-v1-progress-and-quality. Each of those recommendations is the maintainer's to file.

<details>
<summary>Details and glossary</summary>

**The report's recommendations:**

1. A use criterion for V1: a timed first run and a week of real use at V1-M4-claude-end-to-end or V1-M5-approvals.
2. Count approval prompts now by replaying a week of host transcripts against the built-in profiles.
3. Decide the GraphQL allowlist for `gh` before V1-M4-claude-end-to-end (I502).
4. Repair the plan: its status, the package sizes, a stale dependency, the missing secret scanner package and the dependencies of V1-M6-release-gate.
5. Batch the attended steps and decisions, starting with I253.
6. Record manual VM test runs, and add mutation testing and deeper fuzz corpora for `wb-netd` and `wb-proxyd`.
7. Look at the 7.4% flaky CI runs of the last week.

**Glossary**

- **Active day:** a day with any agent activity. Every such day also had a prompt from the maintainer.
- **Work unit:** one closed package issue of V1-M2-walking-skeleton or V1-M3-network-floor, about 2,700 changed lines at the median. A small issue counts 0.3.
- **Monte Carlo forecast:** replay randomly chosen past days until the remaining work is done, many thousands of times. Report the spread.
- **P50, P85:** half of the simulated runs finish by the P50 date, 85% by the P85 date.
- **VM lane:** the work that needs a running macOS guest. One builder at a time does it, so it runs in series.
- **`cost-state`:** Claude Code's own record of what a session cost at list prices.
- **METR method:** count the 10-minute windows that hold at least one human prompt, once across parallel sessions.
- **Line survival:** the share of lines added in a week that are still there today. The rest were rewritten or removed.

</details>

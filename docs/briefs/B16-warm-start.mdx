**Answered 2026-10-04: yes, with conditions. Awaiting decision on idle-while-locked.** Source: X02-warm-start (I16). Changes S06-vm-lifecycle and S11-verification-and-spikes. Feeds X18-vsock-handoff (I29) and X17-image-build (I28).

<Aside type="tip" title="What we learned">
**Yes, with conditions.** A macOS guest with a vsock device and the file-handle network attachment saves in about 3 s and restores in 3.7 s (p50) to 3.9 s (p95) at 4 GiB, or 4.1 s to 4.6 s at 8 GiB, measured to the guest kernel answering on the network. For an idle guest that fits the 7 s budget of NFR01-startup for a suspended VM, with about 2.5 s left for the session. Whether it fits for a working guest, with more memory in use, waits on X18-vsock-handoff (I29) and the time-to-prompt benchmark of S11-verification-and-spikes. One saved state restored 30 times from fresh APFS clones. The catches: every restore needs a fresh clone, the same machine identifier and MAC address, no other running VM with that identifier, and the host unlocked at save time. One decision is left for you: what an idle VM does when the host is locked.
</Aside>

## The decision left: an idle VM while the host is locked

Saving encrypts the state with a key that macOS keeps in the Secure Enclave, and the key can only be made while your session is unlocked. With the screen locked the save fails. S06-vm-lifecycle saves a VM after an idle period, which often ends while you are away.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Keep running, save after unlock

The VM stays up while the host is locked and is saved at the next unlock if it is still idle.

- **Cost:** guest memory stays in use while you are away.
- **Keeps:** detached sessions keep running (B46-session-lifecycle). <Badge text="NFR03-footprint" variant="caution" /> idle VMs suspend, later than set.

</div>
<div class="wb-option">

### B. Shut down instead

The guest shuts down when the idle period ends while locked. The next session cold boots.

- **Cost:** a cold boot (about 5 s to the network, then the rest of startup) instead of a restore, and detached sessions end.
- **Keeps:** <Badge text="NFR03-footprint" variant="success" /> memory freed on time.

</div>
<div class="wb-option">

### C. Save before the lock

Save every idle VM when the screen is about to lock.

- **Cost:** a save of 3 to 5 s per VM on every lock, racing the lock itself. Untested whether the key is still available then.
- **Keeps:** <Badge text="NFR03-footprint" variant="success" />, if it works.

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> The configuration with `VZVirtioSocketDevice` and `VZFileHandleNetworkDeviceAttachment` passes `validateSaveRestoreSupport`, and saves and restores. Source: X02-warm-start, "Answer".
- <Badge text="verified" variant="success" /> Restore from a fresh clone to the guest answering on the network: 3.71 s p50, 3.92 s p95 at 4 GiB, and 4.11 s and 4.58 s at 8 GiB, 20 runs each. Cold boot from a fresh clone: 5.04 s and 5.38 s. Save: 2.94 s and 3.20 s at 4 GiB. Source: X02-warm-start, "Measurements", and `results/stats.txt` on the spike branch.
- <Badge text="verified" variant="success" /> A restore with a new machine identifier or a new MAC address fails with "invalid argument". A restore fails while another VM with the same identifier runs: 4 failures in 4 tries. Three of the tries were pairs of concurrent restores of one state, where one restore of each pair failed. The fourth was a restore next to a cold-booted VM with the same identifier. Clones of two states with different identifiers restored side by side. Source: X02-warm-start, "Answer", conditions 2 and 3.
- <Badge text="verified" variant="success" /> A restore onto disks the guest had run from for 10 s gave no error. Source: X02-warm-start, condition 1.
- <Badge text="verified" variant="success" /> Save failed with the screen locked: the log shows the Secure Enclave refusing the key (`errSecInteractionNotAllowed`), `ioreg` showed the console locked, and the login window process logged the key store as locked just before the unlock. After the unlock, the same binary on the same bundle saved 21 times without an error. Source: `results/save-locked.log`, `results/save-locked-run.md` and `results/cycle-4g.jsonl` on the spike branch. The "permission denied" text in `save-locked-run.md` is transcribed from the session, because the next run overwrote that run's output file.
- <Badge text="assumed" variant="caution" /> That a working guest restores within the budget too. All states came from a guest idle at Setup Assistant (1.41 GB in use), and reading the state file is most of the restore time (2.0 s from the host's memory, 3.7 s from disk).
- <Badge text="assumed" variant="caution" /> That restore also fails while the host is locked, which no run tried. It doesn't change the recommendation, because under option A, a locked host leaves the VM running.
- <Badge text="assumed" variant="caution" /> That `wb-guestd` answers on vsock the moment the guest kernel answers on the network. No process of ours ran in the guest. X18-vsock-handoff measures it.

## What it unblocks

X18-vsock-handoff (I29) step 4, X03-network-path (I17) and X05-fs-benchmark (I19), which build on this VM prototype, and the warm start work in S06-vm-lifecycle.

<details>
<summary>Details and glossary</summary>

**The numbers stop at the guest kernel.** A freshly installed macOS guest runs nothing of ours, and the host may not write into a guest disk after its first boot (B44-data-disk-durability). So the spike timed the guest's network stack answering a ping on the file-handle attachment. A vsock connect is no signal: the host side of the device refuses connections to closed ports within 30 ms of start, before the guest kernel runs.

**Fresh clones are the honest case.** Restoring a state just after saving it took 2.0 s, because the file was still in the host's memory. After an idle period it isn't, and a fresh APFS clone behaves the same way: 3.7 s.

**A cold boot comes close.** The guest answers the network 5 s after a cold boot, but the rest of its startup is still running then. The restored guest has finished starting up.

**Bound to this Mac.** Apple's header says a saved state only restores on the host that wrote it, and can stop working after a macOS update. A saved state can't be shipped in an image. A restore that fails for one of these reasons deletes the state and cold boots. One that fails because the identifier is in use or the host is locked keeps the state.

- **Saved state:** a file with a paused VM's memory and device state, which restores the VM where it left off.
- **APFS clone:** a copy that shares disk blocks with its original until either one changes, so it takes no time or space to make.
- **Machine identifier:** the identity Virtualization gives a macOS VM, stored in the VM bundle.
- **vsock:** the host-guest socket, a direct channel between host processes and the guest that doesn't go through the network.
- **p50, p95:** the median, and the value 95% of runs stay under.

</details>

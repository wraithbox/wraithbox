---
title: Does the checksum database work as Go's clock for the dependency gate?
description: Yes. Record numbers in sum.golang.org order Go module versions by when they first appeared, and real installs pass with them as the clock. Without a calibration point the gate refuses every Go request.
---

**Answered 2026-10-08: yes. Awaiting decision.** Source: I76, X21-dep-gate-registries ("The Go clock end to end"). Changes S07-egress-gateway, S04-architecture ("Host work the guest can cause", "Accounting and event channels", "Host state"), S05-cli (`wb gate reset go-clock`) and S11-verification-and-spikes. Follows B32-dep-gate-registries. Follow-up: I193 (branch and commit queries).

<Aside type="tip" title="What we learned">
**Yes.** The gate reads each Go module version's record number in the public checksum database and compares it with the record number of 7 days ago, found from `index.golang.org`. In 320 samples over 16 days, every version fell on the side of that line its first-seen time puts it on. Lockfile installs of cli/cli, fzf, caddy, node_exporter and hugo passed, and a fresh `go get` of fast-moving modules passed by picking an older version. The samples were 6 hours apart and the nearest was about 2 hours from the cutoff, so the claim that the line is on the safe side rests on how far apart out-of-order records were (3.8 s at most) against the 1-minute margin. With `index.golang.org` unreachable from the start, the gate refused every Go download, as required. One open choice is what happens when the index goes away **after** the gate has a point. Recommended: **A**, keep the last point, which only refuses more. The values of the new limits are open too ("Values" below), and so is the recovery command after a fork of the checksum database ("Recovery" below). Approving puts the calibration rules, the lookup limits and the check of each lookup against the signed log in S07-egress-gateway, already in this pull request.
</Aside>

## Options

The choice is only about a point that exists but can't be refreshed. Without any point, every option refuses all Go downloads and lists with the rule `go-clock-uncalibrated`.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Keep the last point

When the hourly refresh fails, the gate keeps using the point it has, retries every minute, and logs `go-clock-stale` with the point's age. `wb status` shows the age, and a refusal gives it too. After a restart the gate computes a point before it decides: the stored point is only shown in `wb status`, so requests wait up to 30 s for the first computation, as on a new install.

- **Cost:** none for the user while the outage is short. The longer it lasts, the more versions are refused: after a day, versions 7 to 8 days old are refused too.
- **Safety:** each point is at or below the true record number at its own cutoff, which is at or below the true record number at any later cutoff. Every version an old point allows, a fresh point would allow too.
- **Keeps:** <Badge text="SEC07-dep-gate" variant="success" />

</div>
<div class="wb-option">

### B. Refuse when the refresh fails

When the hourly refresh fails, the gate drops its point and refuses every Go request until the index answers again.

- **Cost:** every Go install in every VM stops during an outage of `index.golang.org`, though the gate could still decide correctly.
- **Gives:** the outage shows up at once in `wb status` instead of as a slow drift.
- **Keeps:** <Badge text="SEC07-dep-gate" variant="success" />

</div>
</div>

### Values

S07-egress-gateway now sets these. Each is open for the maintainer to change, and the spike's data supports them only as far as stated.

- **4 lookups in flight per VM, 8 requests in flight per `wb-proxyd`, one of them kept for calibration.** The strict choice: 8 at once ran clean. At 16 at once, the full list-filter run (4,074 lookups) and the fresh `go get` with filtering (3,423) ran clean, and one other run, next to an install, got a connection reset. More was never tried. **What it costs:** every timing was measured at 16 at once, and at 4 the lookups take about 4 times as long. That is inferred, not measured: filtering the 1,865 versions of `aws-sdk-go` cold goes from 5.6 s to about 22 s, the fresh `go get` from 9.2 s to about 45 s, and a lockfile install of 179 modules gains up to about 4 s.
- **6,000 uncached lookups a minute per VM.** At 4 in flight and the 87 ms median, a VM makes about 2,760 lookups a minute, so this cap isn't reached. It only matters if lookups get faster than about 40 ms. The fresh `go get` with filtering made 3,423 lookups, calibration included.
- **One retry after 1 second, and 10 seconds per lookup.** The spike measured a median of 87 ms and a p95 of 176 ms per lookup, and no retry or timeout.
- **A deadline per request of 10 s plus 250 ms per 4 uncached lookups, at most 5 minutes, and 4,500 versions per `@v/list` and per queue.** 250 ms per round of 4 is above the 176 ms p95. 4,500 is the most the 5-minute maximum covers. The longest list measured had 1,865, which gets about 2 minutes, and the spike didn't search for longer ones. The 30 s wait for the first point doesn't count toward it.
- **100,000 cached records per VM, least recently used evicted.** The spike didn't measure a cache, and an eviction only costs a lookup. A cache per VM, not one shared, closes a timing channel between VMs (SEC08-proj-isolation). At a guessed 150 bytes an entry, that's about 15 MiB per VM.
- **30 seconds of waiting for the first point after each start, and a retry every minute.** The spike didn't measure either. Its first list request, calibration included, took 1.1 to 1.5 s.
- **8 days of verified tree heads, one an hour, at most 192 stored heads of 1 KiB each,** for the tree bound on a fresh point. Not measured: the spike didn't keep heads.

### Recovery

When a tree head contradicts one the gate accepted in the same run, the checksum database has forked or someone is answering in its place. The gate then refuses every Go download, across restarts too, until the operator runs `wb gate reset go-clock`, a new command in S05-cli that deletes the finding and the stored heads. Open: the command's name, and whether it should also ask the operator to confirm they checked the finding. Recommended: the name above, with a confirmation prompt.

## Evidence

- <Badge text="verified" variant="success" /> 320 index entries sampled every 6 hours over 16 days all had a record already, and their record numbers follow first-seen time except for 4 pairs at most 3.8 s apart. Against the point, none was on the wrong side of the 7-day line. Source: X21-dep-gate-registries, "The Go clock end to end".
- <Badge text="inferred" variant="note" /> The point is on the safe side of the cutoff. The nearest sample was about 2 hours from the cutoff, so the samples don't show the boundary. The claim rests on the inversion width, 3.8 s at most, against the 1-minute margin. Source: same.
- <Badge text="inferred" variant="note" /> The spike's point was about 8 minutes before the cutoff, not 1. It read one page of 400 index entries from 10 minutes before the cutoff, which at 3.3 records a second covers about 2 minutes. That is on the safe side. S07-egress-gateway now pages until 1 minute before the cutoff. The 20 records of one window spread over 22 numbers. Source: same.
- <Badge text="assumed" variant="caution" /> That the checksum database adds a version's record when the module proxy first serves it. All 320 sampled versions had one, but nothing in the database's design promises it. A point larger than the earliest verified tree head fetched at or after its cutoff is rejected (`go-clock-implausible`). New records only raise a head, so a burst of new records that a guest causes can't make a correct point fail that check.
- <Badge text="verified" variant="success" /> Lockfile installs of cli/cli, fzf, caddy, node_exporter and hugo (589 module versions) passed through the gate, with no young version, in 3.4 to 32.4 s against 2.6 to 31.3 s without the spike's proxy. Source: same.
- <Badge text="verified" variant="success" /> A fresh `go get` of five modules `@latest` failed with refuse on one young version and passed with filter. Source: same.
- <Badge text="verified" variant="success" /> Filtering `@v/list` with one lookup per version, 16 at once, took 5.6 s for the 1,865 versions of `aws-sdk-go` on a cold cache. Checking from the highest version down was cheaper but missed a young patch release, so S07-egress-gateway keeps one lookup per version. Source: same.
- <Badge text="verified" variant="success" /> With `index.golang.org` unreachable from the start, all 179 downloads of a lockfile install and every list of a fresh install were refused with `go-clock-uncalibrated`. With the index taken away after the first point, both installs passed on the kept point (option A). Source: same.
- <Badge text="verified" variant="success" /> Of 15 pseudo-versions of commits from before 2022, 14 were already in the checksum database. One got its first record from the gate's lookup and was refused as young. Source: same.
- <Badge text="inferred" variant="note" /> A kept point never allows a version a fresh point would refuse. Each point is at or below the true record number at its own cutoff, and the database only appends. Follows from the order measured above.
- <Badge text="inferred" variant="note" /> In the spike, `wb-proxyd`'s stand-in took each record number over TLS without checking them against the signed log. S07-egress-gateway now has `wb-proxyd` verify each lookup the way `golang.org/x/mod/sumdb` does, and counts a reply that fails as a failed lookup (`go-clock-lookup-failed`). That library is how the go command checks the same log.

## What this unblocks

- The Go part of the dependency gate in `wb-proxyd` (SEC07-dep-gate), towards V1-M5-approvals.
- The conformance case for the gate in S11-verification-and-spikes, which now covers an unreachable `index.golang.org`.

<details>
<summary>Details and glossary</summary>

**Why not the time the module proxy reports.** The `.info` file of a Go module version gives the time of the commit the version points at. Whoever tags a version picks the commit, so a version published today can look years old. In the first X21 run, 173 of 200 versions that the module proxy first saw that week claimed to be more than 7 days old.

**Why the record number works.** The checksum database adds a record the first time anyone asks for a version, and numbers the records in order. A version published today can only get today's number. The gate doesn't need the database to know any dates: it needs one number from 7 days ago, which it reads off versions that the module index lists as first seen then.

**What a never-seen version means.** When nobody has asked for a version before, the gate's own lookup creates its record. The version then counts as published at that moment and is allowed 7 days later. That happened to one of 15 old commits tried.

**Glossary**

- **Checksum database (`sum.golang.org`):** a public, append-only log of the hash of every Go module version. The go command checks downloads against it.
- **Module index (`index.golang.org`):** a public feed of module versions in the order the module proxy first saw them, with times.
- **Record number:** the position of a version in the checksum database.
- **Calibration point:** the record number current 7 days ago.
- **Pseudo-version:** a version name the go command makes up for a commit that has no tag.

</details>

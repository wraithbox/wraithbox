## Sub-decisions

The issue raises four points. Point 1 hides the one real fork, the default VM, with options below.

| Point | Recommendation | Source |
|---|---|---|
| Meanings of "trusted" | Separate, named project settings. `config_trust` (set by `wb trust`) decides whether `.wraithbox/` in the repository is read (SEC09-host-policy). `placement` (`work` or `isolated`) decides the VM. `--isolated` overrides it for one session. The word "trusted" alone leaves the specs. | issue |
| 1. Default VM for a new project | **A** below: `isolated`, until the user runs `wb project place work`. | this brief |
| 2. Untrusted projects share one VM | A new accepted threat in T00-index next to T05-cross-proj-clones: after guest root, one isolated project can read and write another's clone. | issue, but in T00-index |
| 3. Learn mode | Needs `placement = work`, the setting that says the user vouches for the repository. `config_trust` is about reading `.wraithbox/` and says nothing about the content the agent reads. Whether learn mode stays at all is I40. | this brief |
| 4. Project identity | Key on the host realm and the path of the repository's git directory (`git rev-parse --git-common-dir`), so every `git worktree` of one repository is one project. Record the cleaned remote URL. If it changes, stop and ask the user to confirm with `wb project`. `wb project show/move/rename` handle moves explicitly. | issue, amended |

## Options for the default VM

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. New projects start isolated

A newly registered project runs in the isolated VM. One command moves it to the work VM, and from then on it shares grants with your other projects.

- **Cost:** the isolated VM starts for most first runs, which uses memory and a second VM slot (NFR05-two-macos-vms). One command per project you keep.
- **Keeps:** <Badge text="SEC06-repo-writes" variant="success" /> <Badge text="SEC08-proj-isolation" variant="success" />

</div>
<div class="wb-option">

### B. New projects start in the work VM

The issue's recommendation. The user adds `--isolated`, or sets `placement`, for a repository they don't trust.

- **Cost:** none for the user, one VM in daily use.
- **Weakens:** under I36's option A, every new clone gets the network grants and credentials of every work-VM project. <Badge text="SEC06-repo-writes" variant="caution" /> <Badge text="SEC08-proj-isolation" variant="caution" />

</div>
<div class="wb-option">

### C. Ask on first run

`wb` asks once, before the session starts and before any guest output, which VM to use.

- **Cost:** a question per new project, and no answer in non-interactive use (`wb claude -p`), which then needs a default anyway. FR02-any-repo says no setup step per project.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="success" />

</div>
</div>

<Aside type="note" title="Missing from the issue">
- **The default depends on I36.** If I36 makes the VM the enforced unit (its option A), a project in the work VM can use every other work-VM project's grants without guest root. A freshly cloned repository is the most likely place for a prompt injection, so B hands it your tokens by default. If I36 keeps project secrets in a VM of their own (its option B), B is reasonable again.
- **The threats are in T00-index.** The issue says to record the shared isolated VM in S03-requirements, but the accepted threats are in T00-index.
- **The remote URL is a weak identity.** "First remote" is alphabetical, so adding a remote can change the project. A token in the URL (I41, item 3) changes it when the token rotates. Dropping the URL from the key needs a guard, because a different repository cloned into the same directory would then inherit the old project's approvals. That is why point 4 stops on a URL change.
</Aside>

## Evidence

- <Badge text="verified" variant="success" /> S06-vm-lifecycle sends "untrusted repositories" to the isolated VM, by `--isolated` or "a project marked untrusted" ("VMs"). S05-cli has `wb trust` and `wb untrust` for repository configuration only, and no command that marks a project untrusted ("Management commands").
- <Badge text="verified" variant="success" /> `--learn` is "refused unless the project is trusted" (S05-cli, "Session flags"), and FR10-learn-mode says "trusted repositories", without saying which trust.
- <Badge text="verified" variant="success" /> S09-policy-credentials-audit already lists the VM slot (work or isolated) among the project settings ("Settings contents").
- <Badge text="verified" variant="success" /> T05-cross-proj-clones accepts cross-project access in the work VM because "untrusted repositories use the isolated VM", and says nothing about projects sharing the isolated VM (T00-index).
- <Badge text="verified" variant="success" /> Project identity is a hash of the repository's location and the URL of its first remote (S05-cli, "Naming"). `git remote` lists remotes alphabetically (local test, git 2.56.0).
- <Badge text="verified" variant="success" /> In a `git worktree`, `git rev-parse --git-common-dir` returns the main repository's `.git` directory, while `--show-toplevel` returns the worktree's own path (local test).
- <Badge text="inferred" variant="note" /> So today each worktree of one repository is its own project, and keying on the common directory makes them one.
- <Badge text="assumed" variant="caution" /> That I36 is decided as its brief recommends (B36-flow-attribution). The case for A over B rests on it.
- <Badge text="assumed" variant="caution" /> That the isolated VM can host more than one project user at once, as the work VM does. S06-vm-lifecycle implies it, and X06-guest-xcode and I43 may give that slot other work too.

<details>
<summary>Details and glossary</summary>

**The default decides for most repositories.** Few users pass `--isolated` by habit. The default then places nearly every repository, including the ones cloned to try out once. Those are the likeliest to contain a prompt injection.

**Moving a project.** `wb project move` points a project at a new directory, keeping its id, Claude Code state (FR13-claude-state), approvals and policy. `wb project place` moves it between VMs. Moving between VMs copies the project user's home, which needs the data-disk design of I44.

**Glossary**

- **Project:** a repository that Wraith Box knows, with its own guest user, state, policy and landing repository.
- **Work VM / isolated VM:** the two VM slots per guest OS (S06-vm-lifecycle).
- **Configuration trust:** reading the repository's own `.wraithbox/` settings, which can add hosts but never credentials (SEC09-host-policy).
- **Placement:** which of the two VMs a project runs in.
- **Host realm:** the native host, or a WSL distribution on Windows (S12-platforms).
- **Git common directory:** the `.git` directory that all worktrees of one repository share.
- **Learn mode:** a session that allows every destination and records them as a suggested allowlist (FR10-learn-mode).

</details>

title: Can wb-vmd hand guest connections to our Go daemons as descriptors, also across a restore?
description: Yes, with conditions. Go uses vsock in a macOS guest without cgo, passed descriptors keep working without wb-vmd, and every connection ends at a restore, after which wb-guestd answers 4.1 s after the restore starts.

**Answered 2026-10-05: yes, with conditions.** Source: X18-vsock-handoff (I29). Changes S04-architecture, S06-vm-lifecycle, S11-verification-and-spikes and S12-platforms. Follow-up: I86.

<Aside type="tip" title="What we learned">
**Yes, with conditions.** A Go daemon in a macOS guest listens and dials on vsock through `golang.org/x/sys/unix`, with no C code. `wb-vmd` can pass each guest connection and the network endpoint to a Go process and close its own copy: the Go side kept working even with `wb-vmd` frozen. A restore ends every connection, so `wb-hostd` reconnects after each one. From a fresh clone, `wb-guestd` answers 4.1 s (p50) after the restore starts, which leaves about 2.9 s of the 7 s in NFR01-startup. Approving accepts the spec text in this pull request.
</Aside>

## Evidence

- <Badge text="verified" variant="success" /> `golang.org/x/sys/unix` has `AF_VSOCK` and `SockaddrVM` for darwin. A Go LaunchDaemon in the guest listened, accepted, dialed the host, and served gRPC. Source: X18-vsock-handoff, "Answer" part 1, `results/handoff-run2.jsonl` on the spike branch.
- <Badge text="verified" variant="success" /> The descriptor of a vsock connection is a Unix stream socket. It kept working in a Go process after `wb-vmd` closed or dropped its copy, and while `wb-vmd` was stopped with `SIGSTOP`. Source: "Answer" part 2, `results/handoff-run2.jsonl`.
- <Badge text="verified" variant="success" /> Half-close works in both directions, as X07-git-round-trip assumed. Source: `results/halfclose.jsonl`.
- <Badge text="verified" variant="success" /> After a save and a restore into a new VM, all old connections read EOF on both sides, and a new connection works 5 ms after `resume`. Source: "Answer" part 4.
- <Badge text="verified" variant="success" /> Restore from a fresh clone to `wb-guestd` answering gRPC: 4.13 s p50, 4.21 s p95, 20 runs. Source: "Measurements", `results/stats.txt`.
- <Badge text="verified" variant="success" /> A restore while the host is locked fails with "permission denied", with the Secure Enclave key refused in the system log. Source: "Measurements", `results/restore-4g-failed.jsonl`.
- <Badge text="assumed" variant="caution" /> That a working guest, with more memory in use, also restores to `wb-guestd` within the budget. Every state here was an idle guest. The time-to-prompt benchmark of S11-verification-and-spikes measures it.
- <Badge text="assumed" variant="caution" /> That the VM stops with `wb-vmd` if `wb-vmd` exits. Not tested, and no recommendation depends on it.

## What it unblocks

The `wb-vmd` and `wb-guestd` contracts in I52, the vsock RPCs of the walking skeleton (V1-M2-walking-skeleton), and X17-image-build (I28), which gets evidence that `VZMacGuestProvisioningOptions` works on a macOS 27 host and guest.

<details>
<summary>Details and glossary</summary>

**The descriptor is a Unix socket.** On the host, `socket(AF_VSOCK)` fails: only Virtualization talks to the virtual device. It hands each connection out as one end of a Unix socket and copies bytes to the device itself. So the bytes never go through `wb-vmd`, but they do go through Apple's service process, as they would with any design on macOS.

**`wb-vmd` sends the ports with the descriptor.** The process that gets a Unix socket can't ask it which vsock port it came from. `wb-vmd` reads the ports from `VZVirtioSocketConnection` and sends them along, and `wb-hostd` decides which service a connection reaches by that port.

**A restore ends every connection.** It creates a new VM process. The old VM's connections die with it, and the guest, which resumes with its old memory, finds its side of each connection closed. Its listener still works, so `wb-hostd` connects again.

**How the daemon got into the guest.** The spike used the macOS 27 provisioning options to create a user with remote login on the first boot. It then copied the daemon in over SSH and shut the guest down, 40 s in all. That is a spike shortcut: the product's image build is X17-image-build.

- **vsock:** the host-guest socket, a direct channel between the host and the guest that doesn't go through the network.
- **Descriptor:** a number a process uses to refer to an open socket or file. A process can send one to another over a Unix socket (`SCM_RIGHTS`).
- **Half-close:** one side says it's done sending, and can still receive.
- **p50, p95:** the median, and the value 95% of runs stay under.

</details>

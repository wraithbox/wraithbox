## Evidence

- <Badge text="verified" variant="success" /> Under the profile, the helper wrote, read and deleted a `binding/` item, made a Secure Enclave key, kept its token object ID in a `ca/` item, restored it and signed, and fetched `api.anthropic.com` with the chain checked against the system roots. Four runs, the same result. Source: X23-sandboxed-daemons, I61 section, "Run".
- <Badge text="verified" variant="success" /> The network part alone refused the store and the Secure Enclave, and sandboxd reported the two Mach services. Adding them was enough for every store call. Source: the I61 section, "How the profile was found".
- <Badge text="verified" variant="success" /> The certificate check needs `com.apple.trustd.agent` and the metadata of the helper's own bundle directory. Every other rule of the wide I34 TLS profile could be removed. Source: the minimizing script in the I61 section.
- <Badge text="verified" variant="success" /> The profile denies files, the login keychain, listening, UDP other than DNS, and starting programs. Unconfined, the same helper saw the attributes of 166 login keychain items. Source: the I61 section, "Run".
- <Badge text="verified" variant="success" /> A profile with only the Keychain and Secure Enclave services works as the store-only profile, for `wb-credset` and `wb-guestadmin`. Source: the I61 section, "Answer".
- <Badge text="assumed" variant="caution" /> That no untested path, such as a revocation check, needs a service the profile denies. sandboxd reported only some denials. The rules came from removing rules one at a time, not from the log. If one is missing, the check fails and `wb-proxyd` refuses the connection, which fails closed.

## What this unblocks

- I61 closes. It blocks nothing else.
- I261 writes the profile into S04-architecture, after the I49 wave merges.

<details>
<summary>Details and glossary</summary>

**Why the helper's own bundle.** Security.framework reads the metadata of the calling program's bundle before `trustd` checks a chain. The real path of `Contents/Helpers/wb-proxyd.app` goes into the profile as a parameter, worked out before the daemon confines itself, so no path is pasted into the profile text.

**Why the issue's keychain file wasn't used.** I61 was filed before B23-keychain-unsigned and B248-dev-signing were decided. Since then a build signed by a team keeps its items in the data protection keychain behind access groups, and an ad-hoc build has no Keychain backend. The spike measured that setup.

**Glossary**

- **Seatbelt profile:** the rules a macOS process applies to itself, in Apple's profile language. Anything not allowed is denied.
- **Mach service:** a named system service a process talks to, such as the Keychain. A profile allows each by name.
- **Access group:** the label on a Keychain item that says which signed programs may use it.
- **Token object ID:** an opaque value that restores a Secure Enclave key on this Mac only.

</details>

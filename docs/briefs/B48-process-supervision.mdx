Who supervises the host processes, and what running VMs do when `wb-hostd` stops or restarts. Recommended: **A**, `wb-vmd` saves its VMs and exits when it loses `wb-hostd`, and `wb-hostd` restores them when it starts again. The issue proposes **B** instead. ## Options

These cover the one real fork: what running VMs do when `wb-hostd` stops, crashes or is upgraded.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. VMs follow wb-hostd, through saved state

When `wb-vmd` loses its connection to `wb-hostd`, it saves each running VM's state and exits. When `wb-hostd` starts, it restores them. The host-guest socket drops meanwhile, so `wb-guestd` pauses the session's processes and resumes them on restore (S13-guest-confinement, "Layer 1"). A crash and an upgrade take the same path.

- **Cost:** a restore after every `wb-hostd` restart, inside the NFR01-startup budget for a suspended VM (7 s). No protocol for taking over a running VM. Falls back to a hard stop if saving fails.
- **Depends on:** save and restore working with the vsock device and the file-handle network attachment (X02-warm-start).
- **Keeps:** <Badge text="SEC11-root-gains-nothing" variant="success" /> <Badge text="SEC13-bounded-resources" variant="success" />

</div>
<div class="wb-option">

### B. wb-vmd keeps running without wb-hostd

The issue's proposal. `wb-vmd` keeps running when `wb-hostd` dies, and a new `wb-hostd` takes the VMs and their descriptors back. launchd kills a job's leftover process group, so `wb-vmd` needs its own launchd job or `AbandonProcessGroup`.

- **Cost:** a takeover protocol. `wb-vmd` must keep copies of the guest socket and network descriptors. An upgrade still restarts `wb-vmd`, so it doesn't help there, and a new `wb-hostd` must talk to an old `wb-vmd`.
- **Keeps:** <Badge text="SEC11-root-gains-nothing" variant="success" /> <Badge text="SEC13-bounded-resources" variant="success" />

</div>
<div class="wb-option">

### C. VMs stop with wb-hostd

`wb-vmd` stops its VMs at once when it loses `wb-hostd`. Sessions end without their WIP push. Uncommitted work stays in the guest worktree on the data disk until a later session.

- **Cost:** the least code. Every `wb-hostd` crash or upgrade kills running agents mid-task.
- **Keeps:** <Badge text="SEC11-root-gains-nothing" variant="success" /> <Badge text="SEC13-bounded-resources" variant="success" />

</div>
</div>

<Aside type="note" title="Missing from the issue">
**B doesn't help upgrades.** The issue's reason for B is upgrades as well as crashes, but an upgrade replaces `wb-vmd` too. B then still stops the VMs, and also needs a newer `wb-hostd` to talk to an older `wb-vmd`. A uses one path for both, which is why this brief recommends it over the issue's proposal.

**A restart must not reset per-session budgets.** S07-egress-gateway bounds DNS names under wildcards per session (T02-dns-names). If `wb-netd` holds that counter, a guest that finds a crash bug in `wb-netd` gets a fresh budget after each restart. Counters that bound the guest, including approval request counts (I51), belong in `wb-hostd`, or `wb-netd` gets them back from it at start.

**Audit size caps let the guest erase evidence.** S09-policy-credentials-audit says the audit log is "rotated and size-capped". A guest that floods events pushes older records out, which goes against SEC10-audit ("a persisted log the guest cannot alter"). A per-VM event rate limit, with a record of what was dropped, fixes that. Rotation should delete records by age only.

**Process IPC is not all gRPC.** Descriptor hand-off (`SCM_RIGHTS`) can't be sent inside a gRPC message. I52 covers that.
</Aside>

## Sub-decisions

| Item | Recommendation |
|---|---|
| Supervisor | `wb-hostd` runs under the service manager with keep-alive (S12-platforms, "Service manager"). It starts and restarts `wb-netd` and `wb-proxyd` with backoff. A VM whose `wb-netd` keeps failing has no network until the VM stops, and `wb status` says why. |
| Fail closed, visibly | When `wb-netd` or `wb-proxyd` is down, the guest gets resets and refusals, never a path around them. `wb` prints one `wraith box:` line on stderr and `wb status` shows the process state. That line never asks for input, so SEC14-no-fake-approvals is untouched. |
| Skew between host processes | They ship in one bundle at one version. Each refuses a host peer of a different build version at connect, so there are no host-to-host compatibility rules to keep. |
| Skew with `wb-guestd` | Each `.proto` package name ends in a major version (`v1`). `wb-guestd` reports its version at connect. The host refuses a version outside its supported range and updates the guest from the guest tools disk image (S06-vm-lifecycle). The reported version is a guest label: the host uses it only to refuse, never to allow. |
| Upgrades while running | Option A's path: save VMs, replace the bundle, restart, restore. The install side is I49. |
| Host resource limits | Each guest-facing handler gets a rate limit and a size limit per VM: host-guest socket RPCs, DNS queries, new connections, `receive-pack` size and time, audit events, approval requests. Extend SEC13-bounded-resources to say so. That is a stricter control, and still a SEC00-index change. |
| Logs and health | Each daemon logs to `<logs>`. `wb status` lists each process, its restart count, and its last exit reason (NFR06-explained-refusals). |

## The spec change

The spec pull request for I48 adds "Supervision and failure" to S04-architecture, with option C and the sub-decisions above, and the `wb-launcher` duties from the I48 comment on the X23-sandboxed-daemons result. Approving it also approves these choices, which neither the decision nor this brief made. Each row says what the spec chose and the alternative it passed over.

| Choice | The spec says | Passed over |
|---|---|---|
| Guest version rule | `wb-hostd` accepts only a `wb-guestd` of its own build version. Under C every running VM was started by the running bundle and gets its guest tools disk. A range adds nothing in V1. | A supported range, which needs compatibility rules now. It returns if option A is adopted later. |
| Upgrades | Same path as a crash: the VMs stop and their sessions are lost and recovered later. The "Upgrades while running" row above assumed option A. | Saving VMs across an upgrade (option A). |
| Losing `wb-hostd` | Every daemon reads end of file on its control channel as `wb-hostd` gone. `wb-vmd` stops its VMs, `wb-netd` and `wb-proxyd` exit, and `wb-launcher` sends `SIGTERM`, then `SIGKILL` after 5 seconds, and exits. launchd's process group kill is a second layer. | Relying on launchd alone, which works on macOS only. |
| Restart limits | Backoff from 0.5 seconds, doubling to 30 seconds. After 5 exits in 10 minutes `wb-hostd` gives up: the VM has no network until it stops, or for `wb-proxyd`, one more try at the next session start. | Unlimited restarts, which turn a guest-triggered crash into an endless supply of fresh processes. |
| Wildcard budget across a restart | `wb-hostd` holds the total. `wb-netd` writes each debit to its event channel before it answers and refuses the lookup if the write fails, so a crash can't lose a debit. | Keeping the counter in `wb-netd` only, which a crash resets (T02-dns-names). |
| Restarting `wb-netd` without the VM | `wb-hostd` keeps a copy of each VM's packet transport descriptor, never reads or writes it, and hands it to the new `wb-netd`. | Stopping the VM whenever `wb-netd` exits. |
| Telling the user | A native notification once per outage, a `wraith box:` line in non-interactive use, a line in the session summary, and `wb status`. In interactive use `wb` doesn't write into the agent's screen, where a line would garble the display. | The `wraith box:` line in interactive use that the "Fail closed, visibly" row proposed. |
| Audit retention | Deleted by age only, after `audit_retention_days` (default 90), and `wb-hostd` limits events per VM with a count of what it dropped. When a record can't be written, `wb-hostd` stops every VM and refuses session starts until it can write. | A size cap, which a flood turns into deleted evidence. |
| Guest tools disk | `wb-hostd` copies it into the VM's bundle, because `wb-vmd` attaches no disk outside it. A saved state from another build version is deleted before any restore. | Attaching the image in place, which the device-set check refuses. |

Left to I52: the values of the message size, stream and request rate limits on the `wb-guestd` connection, and the version exchange message itself.

## Evidence

- <Badge text="verified" variant="success" /> `wb-hostd` spawns `wb-vmd`, one `wb-netd` per VM, and `wb-proxyd`, and `wb-vmd` hands it the guest socket descriptors (S04-architecture, "Processes" and "Design decisions").
- <Badge text="verified" variant="success" /> When a launchd job exits, "launchd kills any remaining processes with the same process group ID as the job", unless `AbandonProcessGroup` is set (`man launchd.plist`, macOS 27.0.1).
- <Badge text="verified" variant="success" /> When the host-guest socket drops, `wb-guestd` stops the session's process group and resumes it when the link returns (S13-guest-confinement, "Layer 1").
- <Badge text="verified" variant="success" /> The specs already plan to save VM state on idle and restore it (S06-vm-lifecycle, "Warm start"), so A reuses that path.
- <Badge text="verified" variant="success" /> SEC13-bounded-resources reads "CPU, memory and disk of each VM are capped", and nothing bounds the host processes serving a VM (SEC00-index).
- <Badge text="verified" variant="success" /> The audit log is "rotated and size-capped" (S09-policy-credentials-audit, "Audit"), and the wildcard DNS budget is per session (S07-egress-gateway, "DNS").
- <Badge text="verified" variant="success" /> The code has no supervision yet: every daemon under `packages/wraithbox-go/cmd/` and `wb-vmd` prints its version and exits 2. Go and Swift each define their own version string (`internal/version/version.go`, `WraithBoxVM/Version.swift`), so the release build must set both to the same value.
- <Badge text="assumed" variant="caution" /> That a Virtualization framework VM stops when the process that owns it exits. Probable, and a VM run takes minutes to check: add it to X18-vsock-handoff.
- <Badge text="assumed" variant="caution" /> That a macOS guest with a vsock device and a file-handle network attachment can be saved and restored. That is X02-warm-start. If it can't, A falls back to C.

<details>
<summary>Details and glossary</summary>

**What fails closed means here.** The guest's only network path is `wb-netd`, then `wb-proxyd`. If either is gone, guest connections are reset or time out. Nothing else on the host forwards guest traffic, so a crash can't open egress. The decision is only about how visible the failure is and how fast it recovers.

**A restarted wb-netd forgets its DNS answers.** It hands out synthetic addresses per name and remembers them. After a restart, the guest still has cached addresses that the new `wb-netd` doesn't know, so those connections are reset until the guest looks the names up again. This fails closed without special handling, and `wb status` should show it.

**Why the host doesn't trust the guest's version.** `wb-guestd` runs as root in the guest, and guest root is the adversary (T00-index). A forged version can make the host refuse to talk, which only hurts the guest. It can never make the host accept a message it would otherwise reject, because the host validates each message the same way whatever the version.

**Glossary**

- **Supervisor:** the process that starts other processes and restarts them when they exit.
- **launchd and LaunchAgent:** the macOS service manager, and its per-user job definition. It keeps `wb-hostd` running.
- **Saved state:** a snapshot of a running VM's memory and devices on disk, which restores the VM where it left off.
- **Descriptor:** a handle to an open socket or file that one process can pass to another (`SCM_RIGHTS` on Unix).
- **Version skew:** two parts of the system running different versions that must still talk to each other.
- **Backoff:** waiting longer after each failed restart, so a crash loop doesn't use the whole CPU.

</details>

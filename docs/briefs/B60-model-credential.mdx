### A. The model only

The profile allows the `api.anthropic.com` paths Claude Code used and `platform.claude.com` `/v1/oauth/hello`. The token goes to `api.anthropic.com` only. The guest sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, which is meant to turn off telemetry, error reports and the updater, so Claude Code doesn't ask for the other hosts (assumed, see Evidence). A sub-choice decides the event log, which is on the same host as the model and receives the token:

- **A1, guest switch only:** the profile allows `/api/event_logging/v2/batch`. Whether the event log stops then depends on the switch alone.
- **A2, host-enforced (recommended):** the profile leaves out `/api/event_logging/`, so `wb-proxyd` refuses it whatever the guest sets. `/api/eval/` (feature flag evaluation, inferred from the path, with the token) can be left out the same way. Recommended: keep it in, because flags may switch Claude Code features, and what Claude Code does without them wasn't measured.

- **Cost:** a Claude Code update needs a new image. No update notice or changelog in the guest.
- **Gives:** two allowed hosts, the fewest of the options. Datadog doesn't get usage data. With A2, Anthropic's event log doesn't either, whatever the guest sets.
- **Unmeasured:** how Claude Code behaves when the event log path is refused.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" /> <Badge text="SEC05-default-deny" variant="success" /> <Badge text="SEC07-dep-gate" variant="success" />

</div>

- **Gap:** a binary and plugins come in from outside the dependency gate.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" /> <Badge text="SEC05-default-deny" variant="success" /> <Badge text="SEC07-dep-gate" variant="caution" /> a download host outside the gate

## Decision 4: the long-lived token as a supported mode

Whether Wraith Box supports a token from `claude setup-token` as the way a subscription user signs Claude Code in, until I15 settles the browser login. Recommended: **yes, for V1**, bound to `api.anthropic.com` alone, with these costs written into S09-policy-credentials-audit:

- **Lifetime unknown.** `setup-token` calls the token long-lived, without a lifetime, and the run didn't see it expire or refresh. When it expires, the user runs `claude setup-token` on the host again and stores the new token with `wb cred set`.
- **Rotation after a leak.** The token is kept in the host's secret store. If that store leaks, the token works from anywhere until someone revokes it, and the user makes a new one. Where a user revokes it wasn't checked. The spike stored one token and no refresh token, so nothing in Wraith Box renews or replaces it by itself.
- **Bound to one host.** The spike injected on `api.anthropic.com`, `console.anthropic.com`, `platform.claude.com` and `claude.ai`, and only `api.anthropic.com` received the token. The binding names that host alone, and a placeholder anywhere else gets a `403` (S07-06-requests-and-credentials, "Placeholder binding").
- **Not chosen:** no subscription mode in V1, which leaves an SSO user with no API key unable to use Wraith Box until I15 is decided.

## Evidence

- <Badge text="verified" variant="success" /> `-p` answered `pong`, `-p --resume` answered `I replied with "pong".` in the same session, and the interactive session answered one question, all with a placeholder `CLAUDE_CODE_OAUTH_TOKEN`. Source: X01-model-credential, "Answer", and the run's `p.json`, `resume.json` and proxy log.
- <Badge text="verified" variant="success" /> All 36 requests with a credential sent it as `Authorization: Bearer` to `api.anthropic.com`, with `anthropic-beta: oauth-2025-04-20`. The proxy replaced the placeholder in each. Source: the proxy log, X01-model-credential, "Hosts".
- <Badge text="inferred" variant="note" /> That the placeholder went to no host but `api.anthropic.com`. Verified for the `Authorization` and `x-api-key` headers only. The proxy didn't scan other headers, query strings or bodies, which is where S07-06-requests-and-credentials, "Placeholder binding", also looks for a leak. A full-request scan is still to do, in the next run or in the conformance tests of `wb-proxyd`.
- <Badge text="inferred" variant="note" /> That the real token wasn't in any file of the test user's home, and that Claude Code didn't make a Keychain item for it. Both searches found nothing, but this run couldn't tell nothing found from a failed read of the token, or a failed Keychain listing. The proxy read the same item at start, so a failed read is unlikely. `run.sh` now fails in both cases. Source: X01-model-credential, "What Claude Code stored".
- <Badge text="verified" variant="success" /> The updater, the plugin marketplace, the changelog and the reachability checks ran only in interactive sessions. Source: the proxy log's timestamps.
- <Badge text="verified" variant="success" /> The variables `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_TELEMETRY` and `DISABLE_AUTOUPDATER` appear in the Claude Code 2.1.289 binary. Source: a string search of the binary.
- <Badge text="assumed" variant="caution" /> That those variables stop the Datadog, event log, update and changelog requests, and that Claude Code works when those hosts are denied. The spike didn't run either. The model API profile work (I215) or a rerun of the spike with the variable set would show it.
- <Badge text="assumed" variant="caution" /> That a `setup-token` token is valid for longer than a session, and the guest doesn't need to refresh it. The spike didn't see a refresh, and `claude setup-token --help` (Claude Code 2.1.289) calls the token long-lived without giving a lifetime. Source: X01-model-credential, "Measurements".
- <Badge text="assumed" variant="caution" /> That API key mode works the same way, from OpenShell's Claude Code provider (X00-index). The spike saw only that the placeholder goes out as `x-api-key` and is replaced.
- <Badge text="inferred" variant="note" /> That the host's Claude Code and the guest's don't race on a refresh: `setup-token` makes a token of its own, separate from the host's login.

<details>
<summary>Details and glossary</summary>

**The token stays in the proxy, out of the guest.** Claude Code only needs a string that looks like a token. The proxy, which runs on the host, sees each request in clear because it inspects TLS, and swaps the placeholder for the token just before it leaves the Mac. A guest that leaks its placeholder leaks nothing that works anywhere else.

**What `api.anthropic.com` serves besides the model.** The organization's limits, remote managed settings (404 here: none set), feature flags, Anthropic's event log, a bootstrap call that refused this token every time without harm, and the public MCP server registry. Requests to every one of these paths but the MCP registry hold the token. The profile would allow these paths and no others.

**Glossary**

- **`claude setup-token`:** a Claude Code command that signs in with a subscription once and prints a long-lived token, for use where no browser login is possible.
- **`CLAUDE_CODE_OAUTH_TOKEN`:** the environment variable from which Claude Code reads such a token.
- **Placeholder:** a fake value with the token's prefix and length, which the guest holds instead of it.
- **Profile:** the built-in list of hosts and paths `wb-proxyd` allows for one purpose, here the model API.

</details>

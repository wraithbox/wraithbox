title: Can git itself refuse a push that asks for too much memory, so the pack scanner gets simpler?
description: Yes, with conditions. GIT_ALLOC_LIMIT makes git refuse every oversized allocation before making it, but not the CPU time of many deltas under the cap, so the scanner stays for the totals and stops holding entries.
---

<Aside type="tip" title="What we learned">
**Yes, with conditions.** With `GIT_ALLOC_LIMIT` set, both host gits refused every bomb of X26-pre-receive-check before allocating it, in under 0.1 s and 15 MiB, and refused no real push. The limit caps one allocation, not the work: 640 deltas just under the cap cost git 145 s of CPU from a 42 KiB pack. Recommended: set the limit, check at start that git honors it, and keep the scanner for the object count and the per-push total, but let it stream the pack instead of holding each entry. Its memory then depends only on the object count cap. Review added these items: every REF_DELTA's base size counts toward the per-push total, with at most 10,000 of them per push; a push must use git's side channel for messages (`side-band-64k`), and git's own error output is cleaned before it is logged; the size limit (`receive.maxInputSize`) is 1 GiB; a push gets a 60 s idle timeout and a 5 minute watchdog. The values are open decisions in X28-git-alloc-limit.
</Aside>

## Options

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Git's limit and a streaming scanner

Set `GIT_ALLOC_LIMIT` to the per-object cap plus one byte. Check at start that the git found honors it, and refuse pushes if not. The scanner checks each entry's header, forwards the entry at once, and holds back only the pack's checksum. It keeps its caps on wire bytes (1 GiB), object size, the per-push total and the object count, counts the base of every REF_DELTA toward the total, and allows at most 10,000 REF_DELTA entries. Git's `receive.maxInputSize` is 1 GiB as well. A push must ask for `side-band-64k`, and gets a 60 s idle timeout and a 5 minute watchdog.

- **Cost:** one environment variable and a start check. The scanner loses its per-entry buffer and per-entry wire-byte bound.
- **Gives:** two independent memory bounds, so a scanner bug no longer lets a pack ask git for gigabytes. Refusals keep naming their rule.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="success" />

</div>
<div class="wb-option">

### B. Git's limit alone

Set the limit and drop the scanner.

- **Cost:** least code, no parser of guest bytes in `wb-hostd`.
- **Gap:** a 42 KiB pack of deltas under the cap kept git busy for 145 s. A pack under the 1 GiB size limit could hold as many such deltas as git's object table allows, about 1.6 million, which is about 100 hours of it at the measured rate (inferred). Only the watchdog would stop it. The object count cap and named refusals go.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="caution" /> CPU bounded only by the watchdog

</div>
<div class="wb-option">

### C. The scanner as decided on I74, no limit

What S08-workspace-and-git says today: the scanner holds each entry until it passes.

- **Cost:** the scanner's wire-byte bound per entry, and its memory up to one entry.
- **Gap:** git's memory depends on the scanner alone. Where the scanner and git read a pack differently, git can still allocate what the pack asks for.
- **Keeps:** <Badge text="SEC13-bounded-resources" variant="success" />

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> With `GIT_ALLOC_LIMIT=100m`, git 2.56.0 and Apple git 2.54.0 refused one delta of 256 MiB to 2 GiB, 8 deltas of 256 MiB, a delta with 128 MiB of its own data, a delta against a 200 MiB blob in the borrowed repository, and a 400 MiB blob, each in 0.02 to 0.06 s with the git child at 15 MiB or less, leaving nothing in `landing.git`. Without the limit the same packs took 207 to 2,063 MiB. Source: X28-git-alloc-limit, "Memory and time".
- <Badge text="verified" variant="success" /> A pack header declaring 1,638,400 objects or more was refused by the limit before git read an entry. Source: same, "The object table".
- <Badge text="verified" variant="success" /> An object of exactly 100 MiB needs a limit of 104857601, because git adds a byte to the buffer. Source: same.
- <Badge text="verified" variant="success" /> The Go repository's whole history and a one-commit push passed with the limit, with the same memory as without. Source: same, "Cost".
- <Badge text="verified" variant="success" /> 640 deltas of 96 MiB each took 145 s of CPU in git with the limit set, before the `pre-receive` check refused them on the total. A 1 GiB blob streams past the limit. Source: same.
- <Badge text="verified" variant="success" /> Without the pack's checksum, `index-pack` resolved no delta: every delta bomb failed with `early EOF` at 15 MiB or less. Source: same, "S08, no limit, pack without its checksum" rows in `results/x28-run1-homebrew.txt`.
- <Badge text="verified" variant="success" /> `git hash-object --stdin` with `GIT_ALLOC_LIMIT=1k` on 2 KiB exits with 128 and `over limit` in both gits, which is the start check. An unparsable value also exits with 128, with another message, so the check needs both. Source: same, condition 2, `results/x28-probe.txt`. The security review of PR116 reproduced it.
- <Badge text="assumed" variant="caution" /> That later gits, Git for Windows and Linux gits honor the variable the same way. It isn't in `git(1)`, only in git's tests. The start check fails closed if one doesn't.
- <Badge text="inferred" variant="note" /> That the scanner's memory, once it forwards as it reads, is its inflate state plus one size per entry, which the object count cap bounds. Follows from the design, and the fuzz target in S11-verification-and-spikes checks it.
- <Badge text="inferred" variant="note" /> `index-pack --fix-thin` reads and writes one base from `export.git` for each distinct REF_DELTA base not in the pack, before the pre-receive check runs. At about 34 bytes each, 16 MiB names about 490,000 of them, and a pack under the 1 GiB size limit as many as the object count allows. Counting REF_DELTA source sizes and capping their number bounds it. Source: the security review of PR116, from reading git. Not measured here.

## What this unblocks

- The git gateway in `wb-hostd`, towards V1-M4-claude-end-to-end: S08-workspace-and-git no longer waits on I102 for the scanner's scope.

<details>
<summary>Details and glossary</summary>

**Why git's limit doesn't make the scanner unnecessary.** The limit stops one big allocation. A pack can instead hold many deltas that each stay under the cap. Git builds each one in full to check its hash, so the work grows with the number of deltas, while the pack is a few KiB. Only a running total, read before git starts building, stops that early.

**Why the scanner can stream now.** Git reads a pack in two passes. In the first, as bytes arrive, it allocates each object and each delta's instructions from sizes in the entry header. The scanner checks that header before forwarding it. Only after the checksum at the end does git build the deltas. Holding back the checksum gives the scanner time to finish its totals, and git's limit covers anything the scanner gets wrong.

**Glossary**

- **`GIT_ALLOC_LIMIT`:** an environment variable git's test suite uses. Git refuses and exits when one allocation would exceed it.
- **Delta:** an object stored as copy instructions against another object. Its header gives the size of the result.
- **Checksum:** the 20 bytes at the end of a pack that cover everything before them.
- **`index-pack`:** the git program that reads a pushed pack and builds its index.

</details>

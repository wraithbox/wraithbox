title: Does the macOS installer refuse a changed restore image?
description: Yes, with conditions. Apple's signing server declines changed boot components and the restore OS a changed system volume, but every install contacts Apple from a service the wb-vmd-install profile doesn't confine, and an older build that Apple still signs isn't caught.
---

**Answered 2026-11-08.** Source: I262, X30-installer-trust. Affects S17-04-restore-and-release and S04-04-vm-processes. Follow-up: I618.

<Aside type="tip" title="What we learned">
**Yes, with conditions.** A changed kernel cache (three ways) and a changed system volume image failed to install, and Apple's unchanged image installed under the same profile. The refusal comes from Apple's signing server, which `wb-vmd-install` can't reach but Apple's installation service does, on every install. Approving records that in S17-04-restore-and-release and S04-04-vm-processes. An older build that Apple still signs is the gap left, and I618 follows it up.
</Aside>

## What approving commits to

No options to choose from: the installer is Apple's, and the spike measured what it does. Approving accepts the answer and these spec changes:

- It amends the I49 decision, "Only `wb-download` fetches" (S17-03-downloads). Apple's installation service asks Apple's signing server for a ticket on every install, over the host's network. Wraith Box neither audits nor bounds that traffic (S04-08-records-and-bounds, S12-01-platform-interfaces). No `SEC*` control is weakened: `wb-vmd-install` itself still has no network, so SEC12-least-privilege holds.
- S17-04-restore-and-release, "The trust base", names the two checks, as measured for the kernel cache and one byte of the system volume. It marks a failed install when the server can't be reached as assumed, not tested. It says an older build that the server still signs passes, with the follow-up I618.
- S04-10-vmd-install, "`wb-vmd-install`", says the installation service rule reaches a service that calls Apple.

<Badge text="SEC12-least-privilege" variant="success" /> kept: `wb-vmd-install`'s profile is unchanged, and the spike's probe confirmed it had no network. The network use belongs to Apple's service. <Badge text="SEC08-proj-isolation" variant="caution" /> kept with a condition: a changed image doesn't install. The guest OS is Apple's, but it can be an older Apple build (I618).

Confidence is high for the refusals, measured once each. A finding that an install goes on without the signing server would change it.

- <Badge text="verified" variant="success" /> Apple's 27.2 (26B123) image installed under the `wb-vmd-install` profile in 446 s, and the same image with every entry stored again installed in 143 s (X30-installer-trust, "Answer", and [`results/README.md`](https://github.com/wraithbox/wraithbox/tree/ddc9d33177d34209b5c4d1c2ed17d777a608ed9b/spikes/x30-installer-trust/results/README.md)).
- <Badge text="verified" variant="success" /> One changed byte in the kernel cache was declined by the signing server after 9.4 s (server error 94, MobileRestore 3194). The digest the installer sent was the changed file's, not the manifest's ([`c02-kernel-flip.summary.txt`](https://github.com/wraithbox/wraithbox/tree/ddc9d33177d34209b5c4d1c2ed17d777a608ed9b/spikes/x30-installer-trust/results/c02-kernel-flip.summary.txt)).
- <Badge text="verified" variant="success" /> Rewriting the manifest's kernel digests to match didn't help (c06), and neither did a kernel cache Apple signed for a physical Mac of the same build (c04) ([`c06-kernel-flip-manifest.summary.txt`](https://github.com/wraithbox/wraithbox/tree/ddc9d33177d34209b5c4d1c2ed17d777a608ed9b/spikes/x30-installer-trust/results/c06-kernel-flip-manifest.summary.txt), [`c04-kernel-swap.summary.txt`](https://github.com/wraithbox/wraithbox/tree/ddc9d33177d34209b5c4d1c2ed17d777a608ed9b/spikes/x30-installer-trust/results/c04-kernel-swap.summary.txt)).
- <Badge text="verified" variant="success" /> One changed byte in the middle of the system volume image failed the install at 48 %, after 219 s, with "failed to restore APFS image" ([`c03-os-flip.summary.txt`](https://github.com/wraithbox/wraithbox/tree/ddc9d33177d34209b5c4d1c2ed17d777a608ed9b/spikes/x30-installer-trust/results/c03-os-flip.summary.txt), [`quoted-lines.txt`](https://github.com/wraithbox/wraithbox/tree/ddc9d33177d34209b5c4d1c2ed17d777a608ed9b/spikes/x30-installer-trust/results/quoted-lines.txt)).
- <Badge text="verified" variant="success" /> Apple's installation service made five signing server requests in the unchanged install, over the host's network, while the profile denied the calling process a TCP connection ([`quoted-lines.txt`](https://github.com/wraithbox/wraithbox/tree/ddc9d33177d34209b5c4d1c2ed17d777a608ed9b/spikes/x30-installer-trust/results/quoted-lines.txt), [`c00-original.summary.txt`](https://github.com/wraithbox/wraithbox/tree/ddc9d33177d34209b5c4d1c2ed17d777a608ed9b/spikes/x30-installer-trust/results/c00-original.summary.txt)).
- <Badge text="inferred" variant="note" /> The restore OS refuses the system volume because the archive's authentication fails. The guest's own log isn't on the host.
- <Badge text="assumed" variant="caution" /> An install fails when the signing server can't be reached. The spike didn't cut the host's network. The log shows the installer retries on "server not reachable".
- <Badge text="assumed" variant="caution" /> Which older builds the server still signs for a VM. Not measured, I618.

## What this unblocks

- The image build of V1-M7-image-build: the trust base of S17-04-restore-and-release is measured.
- I618: the downgrade gap, filed from this result.

<details>
<summary>Details and glossary</summary>

**How the spike changed an image.** A restore image is a zip archive. The spike wrote a copy with every entry stored uncompressed in the original order, and changed only the entries the case names. A copy with no change (c01) installed, so the zip rewrite isn't what made the other cases fail.

**Why the manifest doesn't matter.** The image's `BuildManifest.plist` lists a digest for each component, but nothing signs it. The installer doesn't trust it: it hashes the files itself and sends those digests to Apple. In the spike, the server declined every digest that wasn't the original file's, an Apple-signed kernel cache of another device among them. Apple documents that the boot chain then checks each component against the ticket ([Apple Platform Security](https://support.apple.com/guide/security/welcome/web), on the boot process of a Mac). The spike didn't test that part, because no changed image got that far.

**Glossary**

- **Restore image (IPSW):** Apple's archive that macOS installs from.
- **Signing server (TSS):** Apple's service that personalizes an install: it signs a ticket that lists the component digests for one device, here the VM.
- **Chip identity (ECID):** the device identifier the ticket is bound to.
- **Restore OS:** the small macOS that runs inside the VM during the install and writes the system volume.

</details>

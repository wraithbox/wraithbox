<Aside type="tip" title="What we learned">
**Yes, with conditions.** On the spike's port 1024, a standard guest user took `wb-guestd`'s place while launchd restarted it, and answered the host for 21.7 s. Ports below 1024 need guest root, and a one-line Seatbelt rule makes vsock sockets fail for the session. The specs now require both, and project users without any way to `sudo` to root. Nothing is left to decide: approve the answer and the spec text.
</Aside>

## The fix the specs now state

The spike found the problem and measured two controls that each stop it. The specs take both, so that one of them failing doesn't reopen the hole. An option the issue named, a check `wb-hostd` makes that a project user can't fake, isn't needed and isn't in the specs.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Port below 1024, plus the Seatbelt rule

`wb-guestd` listens on a vsock port below 1024, and the session profile adds `(deny system-socket (socket-domain AF_VSOCK))`.

- **Cost:** a port number and one profile line. The port rule applies to non-root processes outside the profile too, such as those that LaunchServices or `launchd` start.
- **Keeps:** <Badge text="SEC06-repo-writes" variant="success" /> <Badge text="SEC08-proj-isolation" variant="success" /> <Badge text="SEC10-audit" variant="success" />

</div>
<div class="wb-option">

### B. Seatbelt rule only

The profile denies vsock sockets, and `wb-guestd`'s port stays at 1024 or above.

- **Cost:** none to build, but S13-guest-confinement lists processes outside the profile, and any of them can take the port during a restart.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="caution" /> only for processes inside the profile.

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> A standard user (uid 502, outside the `admin` group) creates vsock sockets, binds any free port from 1024 up, and connects to a host listener. Source: X27-vsock-confinement, "Answer" parts 1 and 2, `results/matrix.jsonl` on the spike branch.
- <Badge text="verified" variant="success" /> Ports 1, 80 and 1023 fail with `EACCES` for both non-root users and work for root. Source: "Answer" part 2, `results/matrix.jsonl`, `results/squat-1023-guest.jsonl`.
- <Badge text="verified" variant="success" /> While the daemon holds its port, every bind variant fails with `EADDRINUSE`, for root too. Source: "Answer" part 3.
- <Badge text="verified" variant="success" /> After `kill -9`, the restarted daemon answers 11.5 to 18.2 ms later. A squatting project user got port 1024 and answered 410 host connections over 21.7 s, while the real daemon's three restarts failed. Source: "Measurements", `results/gap-summary.txt`.
- <Badge text="verified" variant="success" /> `(deny system-socket (socket-domain AF_VSOCK))` makes `socket()` fail with `EPERM`, also added to the agent-safehouse v0.12.0 profiles. `(deny network*)` alone leaves `socket()` working. Source: "Answer" parts 5 to 7, `results/profiles.jsonl`.
- <Badge text="verified" variant="success" /> The port rule isn't in Apple's developer documentation, but the XNU source has it: `bsd/kern/vsock_domain.c` returns `EACCES` for a port below `VSOCK_PORT_RESERVED` (1024) unless `proc_suser` passes, which needs effective user ID 0. A later macOS that drops it fails the conformance check on that image (S11-verification-and-spikes).
- <Badge text="verified" variant="success" /> The spike's project user stand-in had no `sudo`. Its admin account could have become root and bound the port, so S06-vm-lifecycle now requires project users without `admin`, `wheel` or a sudoers rule, and sealing fails on an enabled admin account or an added sudoers entry. Source: X27-vsock-confinement, condition 5.
- <Badge text="assumed" variant="caution" /> That X20-shared-homebrew can work without `sudo` for project users. The maintainer is to confirm this strict default.

## What it unblocks

The `wb-guestd` contract in I52, the vsock RPCs of the walking skeleton (V1-M2-walking-skeleton), and the Layer 2 profile work of S13-guest-confinement, which now has a tested rule for vsock.

<details>
<summary>Details and glossary</summary>

**Why the port matters.** `wb-hostd` opens every connection to the guest (B29-vsock-handoff). It can't see which process answers, so it trusts that the process on `wb-guestd`'s port is `wb-guestd`. That daemon then names the project user behind each request. A process that takes the port could claim any project's identity.

**Why launchd restarts leave a window.** launchd restarts a crashed daemon within milliseconds, but the port is free until then. If another process binds it first, the real daemon fails to start and launchd waits 10 s before the next try.

**Why both controls.** The port rule is enforced by the guest kernel for every non-root process. The Seatbelt rule keeps project processes off vsock altogether, which also covers any other guest port the host connects to later.

- **vsock:** the host-guest socket, a direct channel between the host and the guest that doesn't go through the network.
- **Bind:** claim a port, so that connections to it reach your process.
- **Seatbelt:** macOS's kernel sandbox. A profile lists what a process may do, and its children inherit it.
- **launchd:** the macOS service manager, which starts and restarts daemons.

</details>

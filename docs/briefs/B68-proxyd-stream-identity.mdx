## Options

These are ways to fill in "its own copy of the DNS mapping". Each keeps the per-VM socket you decided, and that socket keeps one VM's streams away from another VM's policy and credentials.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Checked name reports

Before each DNS answer with a synthetic address leaves, `wb-netd` sends the name and address on the VM's socket. `wb-proxyd` keeps the pair only if the name is well formed and allowed by the VM's policy, and the address isn't held for another name. A stream message holds only the address, and `wb-proxyd` looks the name up in its copy.

- **Cost:** one small message per DNS answer, sent without waiting for a reply. A second table per VM in `wb-proxyd`, at most 131,072 entries.
- **Gives:** a `wb-netd` bug that mixes up names or reuses an address too early is refused, not followed.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" /> <Badge text="SEC08-proj-isolation" variant="success" />

</div>
<div class="wb-option">

### B. Name in the stream, checked against policy

The stream message holds the name. `wb-proxyd` checks it against the VM's policy and then the SNI or `Host`, and doesn't keep a table.

- **Cost:** least code.
- **Gap:** it isn't a copy of the mapping, so it doesn't match your decision's wording. A `wb-netd` bug that labels a stream with the wrong allowed name goes through when the guest's SNI matches that name.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" /> <Badge text="SEC08-proj-isolation" variant="success" />

</div>
<div class="wb-option">

### C. wb-proxyd hands out the addresses

`wb-netd` asks `wb-proxyd` for each synthetic address, and the pool moves into `wb-proxyd`.

- **Cost:** a round trip on every DNS answer, and the pool rules (reuse, budget, the same answer for every refusal) split across two processes.
- **Gap:** no more protection than A against a compromised `wb-netd`, which can still ask for any allowed name.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" /> <Badge text="SEC08-proj-isolation" variant="success" />

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> The X23-sandboxed-daemons stand-in passed each stream as a socketpair end with `SCM_RIGHTS` on an inherited Unix socket, at 438 MiB/s. Source: X23-sandboxed-daemons, "wb-netd: gVisor over inherited descriptors".
- <Badge text="inferred" variant="note" /> The new channels follow the rule S04-architecture sets for the `wb-vmd` hand-off: one descriptor per message with fixed fields, refused when the count is wrong. That rule is a design, not built yet. Source: S04-architecture, "The VM provider passes descriptors, not bytes".
- <Badge text="verified" variant="success" /> macOS has no `SOCK_SEQPACKET` for Unix domain sockets: `socketpair` returns `Errno 43 Protocol not supported`. So the hand-off uses `SOCK_DGRAM` on macOS, as S04-architecture already allows. Source: a probe on macOS 27 for this brief, and the code review of PR170.
- <Badge text="assumed" variant="caution" /> That a Unix domain `SOCK_DGRAM` socketpair on macOS keeps message order and fails a send that doesn't fit with an error, never dropping it. The design needs both, so that a name report arrives before any stream to its address. One probe for this brief sent 18 messages, received them in order, and saw the 19th send fail with `ENOBUFS`. A buffer with room for two descriptors, sent three, set `MSG_CTRUNC`. That is one run, not a measurement. I172 measures it on each platform. Until then the spec fails closed, and a send that fails answers `SERVFAIL` or resets the connection.
- <Badge text="inferred" variant="note" /> A compromised `wb-netd` can still hand over a stream under any name its VM's policy allows, within the wildcard budget, because only `wb-netd` sees the guest's DNS queries. Each option leaves that as it is. The spec lists the checks only `wb-netd` makes in "Only narrows", and none of them lets a stream reach a name the policy refuses.
- <Badge text="assumed" variant="caution" /> That waiting for `wb-proxyd` to acknowledge each policy change before `wb-netd` gets it doesn't add a visible delay. No test or spike has timed policy delivery yet. I173 measures it.

## Also in the spec change

These follow from the reviews of PR170 and from the supervision work in I48. Approving the brief approves them too.

- **Transport per platform.** `SOCK_SEQPACKET` on Linux and `SOCK_DGRAM` on macOS, with the ordering property I172 measures.
- **A new socket at each restart.** `wb-hostd` makes a new hand-off socket at each start and restore, and when it restarts `wb-netd` or `wb-proxyd`. A restart keeps the generation, and that equal generation replaces the old socket. `wb-proxyd` gets its end and acknowledges it before `wb-netd` gets its end and before the VM runs.
- **Replay.** On every new socket, `wb-netd` first sends a name report for each live entry of its mapping. That rebuilds `wb-proxyd`'s copy after a `wb-proxyd` restart, and matches the kept copy after a `wb-netd` restart.
- **Address reuse fails closed.** A report for an address the copy holds for another name removes the old entry too and closes streams to it (`address-conflict`). Entries leave the copy only when `wb-netd` releases them, so there is one clock, `wb-netd`'s.
- **Wildcard budget in both layers.** `wb-proxyd` counts the distinct names it accepted under wildcards, per VM and active period, and refuses over the budget. `wb-hostd` keeps that set across a `wb-proxyd` restart. Replays aren't counted twice.
- **Bounds.** Per-socket caps on open streams and undecided messages, a 4 KiB message limit, refusal of truncated messages and cut control data, and the new rules in the rate-limited classes.
- **Policy order.** Every change to the effective policy is applied and acknowledged by `wb-proxyd` before `wb-netd` gets it.

## What this unblocks

- The `wb-netd` to `wb-proxyd` contract in I52 and the proxy work in V1-M2-walking-skeleton.

<details>
<summary>Details and glossary</summary>

**What a compromised `wb-netd` can still do.** It sees every packet from its own VM and can break that VM's traffic. Under option A it can't give a stream a name its VM's policy doesn't allow, and it can't reach another VM's socket, because `wb-hostd` passed it only its own end. Each start, restore and daemon restart gets a new socket, and `wb-proxyd` closes the old one.

**Why the label only narrows.** Once X14-flow-attribution delivers labels, a stream message also holds the program and user the guest reported. Guest root can forge it (T06-forged-labels). So a rule that uses it only takes access away.

**Glossary**

- **Synthetic address:** the made-up address in 198.18.0.0/15 that `wb-netd` answers a DNS query with. The guest never learns the real address.
- **Socketpair:** two connected sockets with no file path, so only the processes that are handed an end can use them.
- **`SCM_RIGHTS`:** the way one process sends an open socket to another over a Unix socket.
- **Generation:** a number that names one run of a VM. Each restore starts a new one, and messages from an older one are refused.
- **SNI:** the host name a TLS client sends in the clear when it connects.

</details>

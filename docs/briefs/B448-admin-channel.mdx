<Aside type="tip" title="What we learned">
**Yes, with conditions.** A second root daemon on its own vsock port gave the host a root shell while `wb-guestd` was booted out, stopped, or killed in a loop, and a standard user never bound its port. Its shell can't do what macOS's privacy controls (TCC) guard, such as deleting a user record. One decision is open: whether to give `wb-guestroot` Full Disk Access. The spec now says it has none.
</Aside>

## The open decision: Full Disk Access for wb-guestroot

TCC, macOS's privacy control, applies to root too. A root daemon gets Full Disk Access only when it is granted, and with System Integrity Protection on, root in the guest can't grant it. The spike's shell couldn't delete a user record, while `sudo` over SSH could, because Remote Login has Full Disk Access.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. No Full Disk Access (the spec now)

The admin shell does root checks such as the data mount cases, and not what TCC guards.

- **Cost:** none. A check that needs a TCC-guarded file is done another way, or not through the admin path.
- **Trade-off:** the narrower daemon, at the cost of a shell that fails where TCC guards.

</div>
<div class="wb-option">

### B. Grant it at the image build

The image build grants `wb-guestroot` Full Disk Access, so its shell matches `sudo` over SSH.

- **Cost:** a grant needs the System Settings dialog in the build VM or a configuration profile, and neither was tried. Each image build would carry that step.
- **Trade-off:** a shell as capable as `sudo` over SSH, at the cost of a broader daemon in the guest. No `SEC*` requirement covers that breadth, since the guest is untrusted either way.

</div>
</div>

**The case for B.** "A look inside a VM whose `wb-guestd` is dead" may need logs or files TCC guards, and a shell that fails there sends the person to SSH, which the product doesn't offer. B makes the admin path the one full root shell. The VM is marked and its system disk replaced after use either way.

Confidence in A is moderate. In the shell, `dsmemberutil`, `diskutil list` and `info`, `mount -u` on an attached image, and `sysadminctl -addUser` worked, and deleting a user failed. Reformatting the data volume, step 4 of I420, wasn't tried. If that or another I420 step needs Full Disk Access, B gains.

## Evidence

- <Badge text="verified" variant="success" /> The stand-in gave a root shell (uid 0, on a PTY) with `wb-guestd` running, booted out, stopped with `SIGSTOP`, and killed whenever it ran, in a 40 s window. In that loop, 44 of 44 tries on its port answered and 44 of 44 on `wb-guestd`'s port were reset. Source: X31-admin-channel, "Answer" item 1, `results/state-*.out`, `results/crash-poll*.jsonl`.
- <Badge text="verified" variant="success" /> A standard user's `bind` of port 1022 failed with `EACCES` on every one of 12,646 tries, during restarts and while the daemon was booted out. Root bound it at once. Source: "Answer" item 2, `results/squat*.out`.
- <Badge text="verified" variant="success" /> `dsmemberutil`, `diskutil` and `mount -u` behaved the same in the admin shell and under `sudo` over SSH. Deleting a user failed in the admin shell with `eDSPermissionError`. The guest's TCC database denies `wb-guestroot` Full Disk Access and allows `sshd-keygen-wrapper`. Source: "Answer" item 4, `results/s1-*.out`, `results/tcc.out`.
- <Badge text="verified" variant="success" /> The two updates at one boot both installed, about 0.2 s apart, and 400 rounds at the same instant left no temporary file. Source: "Answer" item 5, `results/boot5.out`, `results/race.json`.
- <Badge text="verified" variant="success" /> A standard user's vsock connect to the guest's own address hung, and the guest's kernel panicked, 2 times in 2 tries. Source: "Answer" item 3, `results/panic*.out`. I615 narrows it down.
- <Badge text="assumed" variant="caution" /> That a grant (option B) is possible at all without device management, which the spike didn't try. I614 can settle it if B is chosen.
- <Badge text="assumed" variant="caution" /> That `sudo` at a console behaves like `sudo` over SSH. The guest had no console login.

## What it unblocks

I614, which builds the admin path, and through it I420, the in-guest root checks.

<details>
<summary>Details and glossary</summary>

**Why a second daemon.** S15-05-admin-path wants a root shell that shares nothing with the agent paths and still answers when `wb-guestd` doesn't. The spike ran a stand-in for `wb-guestroot` next to the real `wb-guestd` code, each a root LaunchDaemon that launchd restarts.

**The kernel panic.** The session profile already denies vsock sockets to project processes, so this is no new hole for them. A process outside the profile could stop the VM, which is a denial of service in the guest only. The host and its controls stayed up.

- **vsock:** the host-guest socket, a channel between host and guest that doesn't go through the network.
- **LaunchDaemon:** a system service that launchd starts at boot and restarts when it exits.
- **TCC:** Transparency, Consent and Control, macOS's privacy control over files and devices. It applies to root.
- **Full Disk Access:** the TCC grant that lets a process read and change the files TCC guards.
- **SIP:** System Integrity Protection. It keeps root from changing system files, TCC's database among them.

</details>

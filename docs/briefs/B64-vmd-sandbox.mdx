title: Can wb-vmd confine itself and still run a macOS VM?
description: Yes, with conditions. A Seatbelt profile with the VM bundles, the Virtualization service and the framework's sandbox extensions runs install, boot, save and restore. It keeps shared directories out of the guest, but only wb-vmd's code keeps a NAT network out.
---

**Answered 2026-10-06. Awaiting decision on two points.** Source: X25-vmd-sandbox, I64. Affects S04-architecture, S06-vm-lifecycle, S07-egress-gateway, S11-verification-and-spikes and S12-platforms.

<Aside type="tip" title="What we learned">
**Yes, with conditions.** `wb-vmd` confines itself the way the Go daemons do (X23-sandboxed-daemons), and a macOS VM installs, boots, saves and restores under the profile at the same speed. The profile also stops `wb-vmd` from sharing a host directory with the guest. It can't stop a NAT network, which would bypass the egress gateway, so that stays a check in `wb-vmd`'s code, which a unit test, an in-guest check and a static check in CI verify. You decide two things. First, whether each VM gets its own `wb-vmd` (recommended), so a compromise from the isolated VM can't reach the work VM. Second, how `wb-vmd` is started to install an image (recommended: a fixed launcher entry). Accepting merges the spec changes in this pull request with both recommendations.
</Aside>

## Options

The spike settled the mechanism: a Seatbelt profile in process, as for the Go daemons. App Sandbox wasn't needed, and no confinement would weaken SEC12-least-privilege (Details). You choose how many `wb-vmd` processes run, and how one starts to install an image.

### Decision 1: how many wb-vmd processes

<div class="wb-options">
<div class="wb-option" data-recommended>

#### A. One wb-vmd per VM

`wb-launcher` has two fixed entries, `wb-vmd-work` and `wb-vmd-isolated`. Each confines itself to its own VM's bundle.

- **Cost:** a second small process while both VMs run, and `wb-hostd` talks to two. Every spike run already had one VM per process.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="success" /> <Badge text="SEC12-least-privilege" variant="success" />

</div>
<div class="wb-option">

#### B. One wb-vmd for both VMs

As S04-architecture lists it today. The profile allows all of `<data>/vms`.

- **Cost:** none in code. A compromise of `wb-vmd` that starts in the isolated VM, through framework code that runs in `wb-vmd`'s process, reaches the work VM's disks and saved state. That needs a T00-index entry for the residual risk.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="caution" /> <Badge text="SEC12-least-privilege" variant="caution" />

</div>
</div>

### Decision 2: how wb-vmd is started to install an image

<div class="wb-options">
<div class="wb-option" data-recommended>

#### A. A fixed launcher entry

`wb-launcher` has a `wb-vmd-install` entry whose compiled-in profile adds the three install rules. The restore image sits at a fixed path under `<data>/images/`.

- **Cost:** one more table entry. No request chooses the mode or a path.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" />

</div>
<div class="wb-option">

#### B. Install rules in every wb-vmd

Every `wb-vmd` profile carries the install rules, with the image path as a parameter.

- **Cost:** none in the launcher. Every running `wb-vmd` can read the restore image and reach the installation service, which only the image build needs.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="caution" />

</div>
</div>

## What this unblocks

- The `wb-vmd` implementation in `packages/wraithbox-swift`: its profile, the configuration check against the fixed device set, a unit test that passes each refused device to that check, and the static CI check that rejects the NAT, bridged, shared directory, SPICE and audio input classes in `wb-vmd`'s sources.
- I28 (X17-image-build): the image build can run in a confined `wb-vmd`, with the three install rules.
- The V1-M1-spikes-closed exit criterion: one fewer open spike.

<details>
<summary>Details and glossary</summary>

**Why NAT gets past the profile.** A Seatbelt profile limits what a process does itself: which files it opens, which services it looks up. The Virtualization framework runs the VM in a separate service process that Apple confines with its own profile. For most devices, `wb-vmd` hands that service a sandbox extension: a token that grants access to a file or a device class. The profile decides which tokens `wb-vmd` may issue. A NAT network doesn't need a token, because the service sets it up with Apple's vmnet on its own. So `wb-vmd`'s profile has nothing to deny.

**Other ways to confine wb-vmd.** App Sandbox, set by entitlements at signing, would confine `wb-vmd` at launch with a container directory. It wasn't tried, because the in-process profile works. Leaving `wb-vmd` unconfined would give a bug in it all the user's files and the network, and would need a spec change, since it weakens SEC12-least-privilege.

**What the device-set check does.** Before every start and restore, `wb-vmd` compares its own description of the VM with the fixed list in S06-vm-lifecycle, before it creates any Virtualization object, and refuses anything else with the rule in its log and in the error it returns. It runs first because a disk outside the bundle crashes the confined process when the framework tries to open it. A unit test passes it each refused device, a conformance check in the guest looks for exactly one network interface, and a CI check rejects the NAT, bridged, shared directory and audio input classes in `wb-vmd`'s code (S11-verification-and-spikes, S04-architecture).

**Why the CPU name matters.** The framework writes facts about the host into the saved state, among them the CPU name, which it reads with `sysctl`. When the profile denies that read, the saved state records a different value from what an unconfined process sees. The restore then fails with "invalid argument". With the read allowed, states restore between a confined and an unconfined process in both directions (measured), so a later profile change is less likely to strand them. S06-vm-lifecycle already treats an unexplained "invalid argument" as permanent: the state is deleted and the VM cold boots.

**What `wb-vmd` does before confining.** It asks for its cache directory with `confstr`. libSystem gets the answer from a system service once and keeps it, so the framework's later call works without that service. Nothing guest-controlled is read before confining.

**Glossary**

- **Seatbelt:** the macOS kernel sandbox. A profile lists what a process may do, and the kernel denies the rest.
- **Sandbox extension:** a token one process issues to give another access to a file or a class of device. The issuing process's profile decides which tokens it may issue.
- **NAT network:** a virtual network where the host's network stack translates the guest's addresses and forwards its traffic to the internet.
- **virtio-fs:** the device that shares a host directory with the guest.
- **vsock:** the socket between host and guest that `wb-hostd` and `wb-guestd` talk over.
- **Restore image:** the file Apple publishes to install macOS into a VM.

</details>

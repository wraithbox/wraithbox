## Options for forwarding

The issue lists 1 to 3 as options. A is its recommendation with one change to the names, explained below. D, defer both, is this brief's.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Named HTTP proxy, TCP on request

`wb-hostd` serves each forwarded HTTP port at `<port>-<project>.localhost` on one loopback port, routed by the browser's `Host` header. Plain TCP forwarding happens only for a port the user names (`wb forward`, or a project setting).

- **Cost:** a small host proxy and a printed URL instead of `localhost:3000`. Tools that insist on `localhost` itself need the TCP form.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" /> <Badge text="SEC03-no-host-exec" variant="success" />
- **Leaves:** a guest page can still call host loopback services from the browser.

</div>
<div class="wb-option">

### B. Named ports only

Forward only ports the user names, each to the same port on `127.0.0.1`.

- **Cost:** one command or setting per port. Every cookie problem stays for the ports named.
- **Weakens:** <Badge text="SEC04-no-guest-secrets via localhost cookies" variant="caution" />

</div>
<div class="wb-option">

### C. Every port, automatically

What S06-vm-lifecycle implies: every port the guest listens on appears on host `localhost`.

- **Cost:** none for the user. The guest decides what listens on host loopback.
- **Weakens:** <Badge text="SEC04-no-guest-secrets, spec change" variant="danger" />

</div>
<div class="wb-option">

### D. Neither in V1

Leave port forwarding and the clipboard out of V1 and design them later. FR11-port-forward and FR12-clipboard have no milestone today.

- **Cost:** no dev server preview from the host in V1.
- **Keeps:** every control. Nothing new crosses.

</div>
</div>

### The clipboard

| Sub-decision | Recommendation |
|---|---|
| Guest to host | Only through `wb` (a guest command that asks `wb-guestd`), each copy approved through a notification, never in the terminal (SEC14-no-fake-approvals). The approval shows the text with newlines and control characters made visible. |
| OSC 52 | Never. The terminal filter of B37-terminal-boundary drops it, so it can't bypass the approval. |
| Host to guest | Off by default, opt-in per project, with an approval per paste. The approval warns that the text goes into the guest, where SEC04-no-guest-secrets says no secret belongs. |
| Kinds | Plain text only, capped in size. No files, images, or rich text. |

<Aside type="note" title="Missing from the issue">
- **Subdomains of one project share a site.** Under option 3 of the issue, `3000.myrepo.localhost` and `5173.myrepo.localhost` share the site `myrepo.localhost`. `localhost` is not in the Public Suffix List. Its default rule then makes `localhost` the public suffix and `myrepo.localhost` the site. A cookie set for `Domain=myrepo.localhost` then reaches every port of the project. A flat name, `3000-myrepo.localhost`, is a site of its own. A uses the flat name.
- **Host cookies leak into the guest.** The bigger risk of B and C is the other direction: the browser sends cookies of host services on `localhost` to the guest's server. That breaks SEC04-no-guest-secrets, not only the host services.
- **No option stops loopback calls.** A page from any forwarded port can send requests to other host loopback services. Separate names don't change that. Only D does.
- **Host to guest.** The issue covers guest to host only. Host to guest can put a copied password into the guest.
- **Wrong place for threats.** The boundaries and accepted threats are in T00-index, not S03-requirements.
</Aside>

## Evidence

- <Badge text="verified" variant="success" /> S06-vm-lifecycle says only that `wb-guestd` reports listening TCP ports for forwarding to host loopback and "optionally" bridges text clipboard ("`wb-guestd`"). S09-policy-credentials-audit lists clipboard and port-forwarding switches in the project settings ("Settings contents").
- <Badge text="verified" variant="success" /> "Cookies do not provide isolation by port" ([RFC 6265, section 8.5](https://www.rfc-editor.org/rfc/rfc6265.html)).
- <Badge text="verified" variant="success" /> The Public Suffix List has no `localhost` entry, and when no rule matches, the prevailing rule is `*` ([list](https://publicsuffix.org/list/public_suffix_list.dat), [format](https://github.com/publicsuffix/list/wiki/Format)).
- <Badge text="inferred" variant="note" /> So `<port>.<project>.localhost` names share one site per project, and `<port>-<project>.localhost` names don't.
- <Badge text="verified" variant="success" /> macOS resolves `3000.proj.localhost` to `127.0.0.1` and `::1` (`dscacheutil` and `getaddrinfo` on macOS 27).
- <Badge text="inferred" variant="note" /> The proxy in A routes by the `Host` header of the browser's request, which comes from the host, and passes the guest's response bytes through. It doesn't need to parse guest HTTP, though its framing of the stream over the host-guest socket still gets a fuzz target (S11-verification-and-spikes).
- <Badge text="assumed" variant="caution" /> That Safari, Chrome and Firefox all keep cookies for `3000-myrepo.localhost` apart from `localhost`, and refuse `Domain=localhost`. A browser check of under an hour answers it, with no VM needed.
- <Badge text="assumed" variant="caution" /> That browsers let a page on one loopback name send requests to another loopback port (the loopback-calls row). Browser rules for private network access change often.

## What this unblocks

- The spec pull request, with a forwarding and clipboard section in S06-vm-lifecycle, `wb forward` and the clipboard command in S05-cli, the switches in S09-policy-credentials-audit, and both crossings in T00-index.
- A milestone for FR11-port-forward and FR12-clipboard, which have none today.
- Relies on I37 (B37-terminal-boundary) for dropping OSC 52. Without that filter, the clipboard approval can be bypassed.

<details>
<summary>Details and glossary</summary>

**Why plain TCP stays opt-in.** Databases and language servers in the guest don't speak HTTP, so the proxy can't route them by name. Forwarding them to the same port on `127.0.0.1` keeps the issues of B, but only for a port the user named, and `wb status` lists it.

**Port conflicts.** The proxy uses one loopback port for every HTTP forward, so a guest port never collides with a host service. Plain TCP forwards fail with an explanation when the host port is taken (NFR06-explained-refusals).

**Paste-jacking.** Text that looks like one command but holds a newline and a second command runs both when pasted into a shell. Showing newlines and control characters in the approval makes that visible. Many shells also turn on bracketed paste, which stops the newline from running the command.

**Glossary**

- **Loopback, `localhost`:** the host's own network address (`127.0.0.1`). Only programs on the host can reach it.
- **Site:** what browsers use to keep cookies and storage apart: the part of a name one owner can register, such as `example.com`.
- **Public Suffix List:** the list browsers use to find that part (`co.uk` is a suffix, so `example.co.uk` is a site).
- **Cookie:** data a browser stores per site and sends back with each request, often a login.
- **OSC 52:** the escape sequence that lets a program write the terminal's clipboard (B37-terminal-boundary).

</details>

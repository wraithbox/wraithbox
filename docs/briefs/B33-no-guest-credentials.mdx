title: Can the proxy drop every credential the guest sends without breaking its tools?
description: Yes, with conditions. Only Homebrew breaks, and a built-in anonymous binding for ghcr.io fixes it, so no credential from the guest is ever forwarded.
---

**Answered 2026-10-05: yes, with conditions. Awaiting decision.** Source: I33, X22-no-guest-credentials. Changes S07-egress-gateway, S09-policy-credentials-audit, S11-verification-and-spikes and T00-index.

<Aside type="tip" title="What we learned">
Yes, with conditions. Of the 10 read clients measured, only Homebrew breaks when `wb-proxyd` removes every credential the guest sends. Claude Code needs its model binding (X01-model-credential). Recommended: **A**, keep removing them, and inject Homebrew's own anonymous token from the host on `ghcr.io`. Merging also accepts, detailed in S07-egress-gateway:

- A narrower enforcement of SEC04-no-guest-secrets: generic "API-key headers" become the headers a profile names. T10-unnamed-credentials: elsewhere, a guest's own key in another header, parameter or WebSocket field still passes, within the methods policy allows there.
- Credential parameters a git host's profile names (GitLab, Forgejo) are refused in the query string and in form or JSON bodies.
- A credential the host didn't give the guest is a detection finding.
- The open decisions below. The third is new: an approval grants read methods only.
</Aside>

## Options

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Remove all, inject from the host

`wb-proxyd` removes every guest credential it knows the place of, on every request. The package registries profile includes an anonymous binding that sends `Bearer QQ==`, the value Homebrew itself sends, on reads of `ghcr.io` `homebrew/core`, and allows the bottle redirect host `pkg-containers.githubusercontent.com` for reads.

- **Cost:** one built-in binding and one more read-only host. It doesn't add a request or keep state. All 10 read clients passed.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="caution" /> enforced in named places only (T10-unnamed-credentials). <Badge text="SEC06-repo-writes" variant="success" />

</div>
<div class="wb-option">

### B. Forward guest credentials on reads only

Remove credentials on POST, PUT and the other writes, and forward them on GET and HEAD.

- **Cost:** no binding. But `gh` with a placeholder and no binding failed with "Bad credentials", and an attacker's token reached GitHub on every GET, including a token request to `ghcr.io` that asks for push rights.
- **Weakens:** <Badge text="SEC04-no-guest-secrets" variant="danger" /> guest values reach upstream. Needs a spec change.

</div>
<div class="wb-option">

### C. Forward only tokens the host issued

Forward a bearer token only if `wb-proxyd` saw the host's token endpoint issue it, in this session, to a request without credentials.

- **Cost:** `wb-proxyd` reads token responses and keeps per-session state. It fixes clients that ask for a token (`docker`, `oras`), but not Homebrew, which never does.
- **Keeps:** <Badge text="SEC06-repo-writes" variant="success" /> <Badge text="SEC04-no-guest-secrets" variant="caution" /> forwards a guest value, but only an anonymous one.

</div>
<div class="wb-option">

### D. Leave it as it was

Remove all, with no anonymous binding.

- **Cost:** every Homebrew bottle download fails with a 401. Homebrew is the toolchain layer of macOS guests (FR07-toolchain-manifest).
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" /> <Badge text="SEC06-repo-writes" variant="success" />

</div>
</div>

## Open decisions

1. **Cookies on hosts without a built-in profile.** No client measured sent a cookie. The npm registry sets Cloudflare cookies, and npm ignores them. A browser in the guest would send them, and wasn't measured. Recommended: remove `Cookie` on every inspected host, like `Authorization`. The alternative is to remove cookies only where a profile or binding says so, which lets an attacker use its own web session on an approved site.
2. **Which anonymous value for `ghcr.io`.** `ghcr.io` accepted `Bearer QQ==`, and also a random bearer value, for public reads. The proxy can instead fetch an anonymous token from `ghcr.io/token` itself, which is the documented flow. Both passed. Recommended: the fixed value, which is what Homebrew sends and doesn't need a request or cache, with the token flow as the fallback if `ghcr.io` changes.
3. **What an approval grants on a host without a built-in profile.** The specs were silent on this. If an approval granted every method, a guest could use its own token in a parameter no profile names to write to an approved host, such as a Forgejo instance approved for one dependency. Recommended: an approval grants GET, HEAD and OPTIONS. A write method, or a WebSocket upgrade, is a separate approval, which the risk check flags. The alternative, every method, is simpler for the user and leaves that write channel open. Now in S07-egress-gateway, "What an approval grants".

## Evidence

- <Badge text="verified" variant="success" /> With every guest credential removed, `brew fetch` failed: `ghcr.io` answered 401 to each bottle manifest request. With the anonymous binding (either value), it passed (X22-no-guest-credentials, "Clients under each rule").
- <Badge text="verified" variant="success" /> `brew` sends `Authorization: Bearer QQ==` by default (`HOMEBREW_GITHUB_PACKAGES_AUTH` in `Library/Homebrew/brew.sh` of Homebrew 7.0.7) and never asks the token endpoint for a token.
- <Badge text="verified" variant="success" /> git, git LFS, npm, pip, uv, Go, cargo and SwiftPM passed under every rule, with and without a placeholder token configured.
- <Badge text="verified" variant="success" /> `gh` with a placeholder token passed when it was removed and failed with 401 when it was forwarded on reads.
- <Badge text="verified" variant="success" /> Anonymous credentials can't write to `ghcr.io`: a blob upload with `QQ==` or with an issued anonymous token got 401, and the token endpoint refused `push` without credentials.
- <Badge text="verified" variant="success" /> GitLab reads a token from `?private_token=`, `?private%5Ftoken=` and `?access_token=`, and from `private_token` in a form or JSON body (401 for a fake value). Upper-case `PRIVATE_TOKEN` is ignored. Forgejo on `codeberg.org` reads `?token=` and `?access_token=`. GitHub refuses `?access_token=` itself (400).
- <Badge text="inferred" variant="note" /> Refusing those parameters stops an attacker's token there. The spike proxy removed headers but never refused a parameter, so this follows from the probes and wasn't run.
- <Badge text="verified" variant="success" /> git LFS and Homebrew bottle downloads have signatures in the query string, so a rule that strips every token-like parameter would break them. `wb-proxyd` can't tell who signed a URL, so the approval risk check flags shared object-storage hosts.
- <Badge text="verified" variant="success" /> Each bottle download redirects to `pkg-containers.githubusercontent.com`, which the profile now allows for reads.
- <Badge text="assumed" variant="caution" /> That `ghcr.io` keeps accepting a fixed bearer value for public reads. Homebrew relies on it, and the token-flow fallback was measured.
- <Badge text="assumed" variant="caution" /> That browsers in the guest are rare enough to remove cookies everywhere, which wasn't measured. Nor were pnpm, yarn, bun, RubyGems, Maven, Gradle or curl with `.netrc`.

## What this unblocks

- Credential replacement in `wb-proxyd` (SEC04-no-guest-secrets), to the rewritten S07-egress-gateway bullet.
- Homebrew in macOS guests (FR07-toolchain-manifest).
- Part of the exit criterion of V1-M1-spikes-closed.

<details>
<summary>Details and glossary</summary>

**Why a fixed value isn't a secret.** `QQ==` is the base64 of the letter "A". Homebrew ships it to every user, and `ghcr.io` treats it as anonymous. Putting it in a binding only means the value comes from the host instead of from the guest.

**Why not trust tokens the host issued.** A token that `ghcr.io` issues to a request without credentials can only read public images, so forwarding it would be safe. But Homebrew never asks for one. The rule would fix nothing that matters here, and it costs the proxy a parser and per-session state.

**Why refuse parameters instead of removing them.** A client has no reason to put a GitLab token in the address or the body when its placeholder goes in a header. Rewriting a body or an address changes what the server sees without the client knowing. A `403` that names the rule fails the request visibly, and the client's error points at the cause. Both a refusal and a removal are logged.

**Glossary**

- **Bearer token:** a credential sent as `Authorization: Bearer <value>`. Whoever holds it is let in.
- **Binding:** host-side configuration that tells `wb-proxyd` which credential to inject for which host and paths (S09-policy-credentials-audit).
- **Placeholder:** a fake value in the guest where a tool expects a credential. `wb-proxyd` replaces it.
- **Token flow:** how a container registry hands out access. A request without a token gets 401 with an address to ask, the client asks there, and sends the token it got.
- **Presigned URL:** a download address with a signature in it, issued by the server, which works for a short time without other credentials.

</details>

## Options

These are what a failure on a VM's hand-off socket does once `wb-proxyd` has accepted it: `wb-netd` closed its end, a receive failed, the version record couldn't be sent, or a `StreamReset` couldn't be sent. A fault in `wb-hostd`'s own message still ends the control channel in each option, as you decided in I576.

<div class="wb-options">
<div class="wb-option">

### A. Close that socket, report it, end that wb-netd (chosen)

`wb-proxyd` closes the socket and its streams and sends one `HandoffSocketClosed` with the rule. `wb-hostd` ends that VM's `wb-netd` and counts the exit toward its restart limit. Before V1-M6, that stops the VM.

- **Cost:** two rules added to `HandoffSocketClosed`. A guest that stalls its streams can stop its own VM.
- **Gives:** every lost socket has a record and an end. The other VM keeps its network.
- **Keeps:** <Badge text="SEC10-audit" variant="success" /> <Badge text="SEC13-bounded-resources" variant="success" />

</div>
<div class="wb-option">

### B. End wb-proxyd's control channel (rejected)

Treat any socket failure as I576 treats a refused `HandoffSocket`: `wb-proxyd` ends, and every VM's egress with it.

- **Cost:** least code. Today's code already does this for a version record it can't send.
- **Gap:** a guest that can make its socket fail takes the other VM's network down too (T14-shared-proxyd).
- **Keeps:** <Badge text="SEC10-audit" variant="success" /> <Badge text="SEC13-bounded-resources" variant="caution" />

</div>
<div class="wb-option">

### C. Close that socket only, tell no one (rejected)

What the code does today for an unsent reset and a closed peer. The VM keeps running, but its traffic doesn't reach `wb-proxyd`.

- **Cost:** none.
- **Gap:** `wb-hostd` doesn't know the VM has no egress, so it neither restarts `wb-netd` nor shows the outage. No audit record says why.
- **Keeps:** <Badge text="SEC10-audit" variant="danger" />

</div>
</div>

**The case for B.** It is the smallest rule: any trouble on the control side ends `wb-proxyd`, and the supervisor restarts it. Each VM then gets a new socket, so no state is kept past a fault, and there is nothing to number or match. Until V1-M6 there are no restarts, so A and B both stop VMs. A only stops fewer of them.

**Confidence:** high. The reviews found failures that come from `wb-proxyd` or the host and would have charged a `wb-netd`: an `ack-timeout`, a receive that fails with an error, and a version record that can't be sent. S07-20-handoff-sockets ("Who a failure is charged to") now charges these to `wb-proxyd`. A `StreamReset` that `wb-netd` refuses is a bug in `wb-proxyd` too.

## Evidence

- <Badge text="verified" variant="success" /> `wb-proxyd` closes a VM's socket when a `StreamReset` can't be sent, and logs only `stream-reset-failed`. Source: `internal/proxyd/handoff/socket.go:439-453`.
- <Badge text="verified" variant="success" /> `HandoffSocketClosed` takes only the rule `name-report-malformed`. Source: `internal/egressmsg/control.go:10`, `control.proto`.
- <Badge text="verified" variant="success" /> A version record that `wb-proxyd` can't send on a new socket ends its control channel for every VM. Source: `internal/proxyd/handoff/receiver.go:303`.
- <Badge text="verified" variant="success" /> `wb-netd` already resets a stream whose guest takes no bytes for 60 s (`guest-write-timeout`), so I536's zero-window guest is bounded on that side. What's left is a bound in `wb-proxyd` for a `wb-netd` that stops reading. Source: `internal/netd/handoff/stream.go:21-25`, since I647.
- <Badge text="verified" variant="success" /> `wb-netd`'s hand-off sender records with no event channel, so its refusals miss the audit log. Source: `internal/netd/handoff/sender.go:107`, I730.
- <Badge text="verified" variant="success" /> `wb-vmd`'s acknowledgment reader stops at the first `recvmsg` error or cut control data. Source: `Sources/WraithBoxVMD/HandoffKeeper.swift:199`, I751.
- <Badge text="inferred" variant="note" /> The flaky test of I731 closes the end it passed to `wb-netd` at once, which the keep-until-held rule forbids. Source: `cmd/wb-netd/child_darwin_test.go:229-237`.
- <Badge text="verified" variant="success" /> An answer to the VM's end that waited on the event channel could be late, and a record queued before it could name a stopped VM. Either ends the shared `wb-proxyd`. Source: security review of PR758, F1, with `TestProxydNamesStoppedVM` and `TestProxydHoldEndsWithTheVM`. So S07-21-vm-end has `wb-proxyd` answer without waiting on delivery, and name its last record.
- <Badge text="assumed" variant="caution" /> An honest `wb-proxyd` closes a VM's sockets and streams and queues its records within the acknowledgment deadline. I512's tests measure it.

## Also in the spec change

Approving the brief approves these too.

- **The rule for passing a socket, in one place** (S04-12-descriptor-passing). A sender keeps its copy until the receiver shows it holds it, for every leg, with the proof and the bound per leg. Pipes and descriptors inherited at spawn are exempt.
- **A bad acknowledgment is skipped.** A lost one runs to its bound. A wrong, duplicate or late one is refused and the reader goes on. A reader of acknowledgments only ends when its peer closes, or after a run of failed receives (I751).
- **States of a socket** (S07-20-handoff-sockets): offered, acknowledged, serving, and four final states. `wb-hostd` holds its copies to each deadline.
- **The socket number and `HandoffSocketHeld`**, as you decided in I728 and I729. `HandoffSocketHeld` doesn't name the VM, because `wb-netd`'s channel is its VM's.
- **A VM's end is its own exchange** (S07-21-vm-end). `wb-hostd` sends `HandoffSocketEnd` before it stops `wb-netd`, naming the highest socket number it offered. It is valid from any socket state, a refused start included, and its answer is never stale. The answer names `wb-proxyd`'s last event record for the VM, and `wb-hostd` ends the VM's events only after reading up to it, under the stop allowance. No answer by the deadline ends `wb-proxyd` (`handoff-end-timeout`), and lost records are recorded (`proxyd-records-lost`).
- **Who a failure is charged to.** Failures a guest can cause end that VM's `wb-netd` (`handoff-netd-ended`). Failures of `wb-proxyd` or the host end `wb-proxyd` (`handoff-proxyd-ended`), never charging a `wb-netd`. `wb-proxyd` refuses to start unless its descriptor limit covers every slot's caps.
- **Stream bounds.** `wb-proxyd` gets a write deadline longer than `wb-netd`'s guest bound (`stream-write-timeout`). A stream where neither side sends is bounded by the caps, not by time.
- **Audit.** A table of which rule each process records, and which stay in the daemon log. A reader keys on the record's `sender` and rule together.

## Open points

- **Enforce the audit table.** `wb-hostd` checks only a rule's form, so a compromised `wb-netd` can write records about its own VM under another process's rule name. `sender` is stamped from the channel, so none is forged under another sender. The spec has readers key on both. Whether `wb-hostd` also refuses a rule outside the sender's row is yours to decide (security review of PR758, F7).
- **I741.** Whether one VM's audit budget may hold `wb-proxyd`'s event channel for the other VM stays open. The end of S07-21-vm-end holds under either outcome. With the hold, `wb-hostd` reads past it under the stop allowance, and without it nothing holds.

<details>
<summary>Details and glossary</summary>

**Why the number.** A `wb-netd` restart gives a VM a new socket in the same generation. Without a number, a late notice about the old socket can end the new `wb-netd`, or fail its start with a false cause (I728).

**Why the strict side for an unsent reset.** A guest that stops reading while `wb-netd` lags can fill the socket, so it can cause one. Counting the restart keeps a guest from looping it for free (I571's triage).

**Glossary**

- **Hand-off socket:** the socketpair that carries one VM's streams and name reports from its `wb-netd` to `wb-proxyd`.
- **`SCM_RIGHTS`:** the way one process sends an open socket to another over a Unix socket.
- **Generation:** a number for one run of a VM. Each start or restore raises it.
- **Acknowledgment:** a message from the receiver that says it holds what it was sent.

</details>

<Aside type="tip" title="What we learned">
**Yes, with conditions.** A project user that `wb-guestd` starts from root, never logged in at the screen, can build macOS and iOS apps, build and test SwiftPM packages with `swift`, sign apps to run locally, boot an iOS simulator, and run iOS unit and UI tests on it. Every `xcodebuild test` on macOS, a SwiftPM package's included, and launching a macOS app fail without a console (GUI) session. Decision 1 is whether v1 offers them at all. Under the draft Seatbelt profile, builds and `simctl` need a short list of exceptions. iOS tests only finished when the profile allowed nearly everything, and the simulator runs outside the profile anyway.
</Aside>

## Decision 1: macOS tests through xcodebuild in v1?

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. Not in v1

Nothing tells `wb-hostd` before a session that it will run one, so there is nothing to refuse it on. The limit is documented, and `wb` turns the `testmanagerd` error into an explained message that names it. Everything else in Xcode works in either VM.

- **Cost:** macOS app projects can build but not run their tests in a session.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="success" />, no automatic login or stored password in any image.

</div>
<div class="wb-option">

### B. A console session in the isolated VM

The isolated VM logs one project user in at its screen. I195 designs and measures it.

- **Cost:** a design for logging in without a stored password, a spike, and one project per console session.
- **Keeps:** <Badge text="SEC04-no-guest-secrets" variant="caution" /> only if the login needs no password left in the guest.

</div>
</div>

## Decision 2: simulators and the profile

The simulator can't be confined by the session's profile, and `xcodebuild test` on it needed a profile that allows nearly everything. I196 holds the design.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. A simulator profile, stated as unconfined

A project that uses simulators gets the broad profile, and S13-guest-confinement says that its sessions have no file system confinement from Layer 2.

- **Cost:** none to build. Weaker defense in depth for those projects.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="success" />, which rests on the project user.

</div>
<div class="wb-option">

### B. Keep looking for a narrow profile

Bisect further, and confine simulator services some other way.

- **Cost:** more spike time, with no path found for the simulator's own processes.
- **Keeps:** <Badge text="SEC08-proj-isolation" variant="success" />

</div>
</div>

## Evidence

- <Badge text="verified" variant="success" /> Builds, SwiftPM, ad hoc and keychain signing, `simctl` and iOS unit and UI tests pass for a never-logged-in user, started with `setuid` or `launchctl asuser`. Source: X06-guest-xcode, "Answer", `results/final-matrix.txt`.
- <Badge text="verified" variant="success" /> macOS tests fail because `testmanagerd` loads only in `LoginWindow` and `Aqua` sessions, and test hosts launch into a missing `gui/<uid>` domain. Source: "Answer" part 3.
- <Badge text="verified" variant="success" /> A write the profile refused succeeded through `simctl spawn`. Source: "The draft profile and its exceptions", `results/final-tasks.jsonl` (`escape`).
- <Badge text="verified" variant="success" /> With the p1 exceptions, `xcodebuild test` on a simulator hung, and it finished with p2. Source: `results/final-matrix.txt`, `results/g3-bisect-tasks.jsonl`.
- <Badge text="verified" variant="success" /> Xcode installs from a copy with no Apple ID, and the iOS runtime downloads with no Apple ID. Source: "Measurements".
- <Badge text="assumed" variant="caution" /> That a console session can be had without a password in the guest. Not measured: I195.
- <Badge text="assumed" variant="caution" /> That the product image can get Xcode and the runtimes as the spike did. I194.

## What it unblocks

FR06-native-tools for Xcode projects, the Xcode image variant (I194), and the guest confinement work of S13-guest-confinement (I196). I43 (VM slots) no longer needs room for GUI work beyond macOS app tests.

<details>
<summary>Details and glossary</summary>

**Why simulators work but macOS tests don't.** The simulator's services are started by launchd in the user's own background domain, which exists for any user that runs a process. The macOS test daemon is only allowed in a logged-in screen session, and macOS launches the app under test into that session too. A project user never has one.

**Why the profile can't hold the simulator.** A Seatbelt profile applies to a process and its children. The simulator's processes are started by launchd, not by the session, so they never get it.

- **Seatbelt profile:** macOS's kernel sandbox rules for a process tree (S13-guest-confinement, Layer 2).
- **Console session:** a user logged in at the screen (`Aqua`), with WindowServer access.
- **launchd domain:** the set of services launchd runs for the system, a user in the background, or a logged-in user's screen session.
- **Sign to run locally:** an ad hoc signature, with no certificate, which is enough to run on the same Mac.

</details>

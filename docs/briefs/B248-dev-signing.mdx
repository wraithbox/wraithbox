---
title: Can development builds signed by the developer's own team share Keychain items across an update?
description: Yes, with conditions. Helpers signed by a team that Xcode lists as a free personal team share the data protection keychain behind one access group across a rebuild, with no dialog, when each helper is a bundle of its own. Recommended - the Keychain backend refuses builds that a team didn't sign.

## Decision: a build that isn't signed by a team

CI, a bare `go build`, and a contributor without an Apple ID make ad-hoc signed builds. B23-keychain-unsigned gave them a keychain file that locks after each update. With X29-dev-signing answered, that file is only needed for these builds.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. No Keychain backend without a team signature

`wb setup` refuses the Keychain backend for an ad-hoc build and says why: sign in to Xcode and build once. The 1Password backend still works. The keychain file, the `unlock` item and "After an update" leave S15-least-privilege.

- **Cost:** a contributor without an Apple ID uses 1Password or has no store. Tests that need the Keychain run on a signed build.
- **Gives:** one Keychain model, the one release builds use. Less spec and code.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="success" /> <Badge text="SEC14-no-fake-approvals" variant="success" />

</div>
<div class="wb-option">

### B. Keep the ad-hoc keychain file as well

Team-signed builds use the access groups. Ad-hoc builds keep the keychain file of B23-keychain-unsigned, which fails closed after each update.

- **Cost:** two Keychain models in the spec, the code and the tests. The `unlock` item and the "After an update" status codes stay.
- **Gives:** a store for builds without an Apple ID.
- **Keeps:** <Badge text="SEC12-least-privilege" variant="caution" /> by build hash, until the next update <Badge text="SEC14-no-fake-approvals" variant="success" />

</div>
</div>

Approving the answer also accepts the team-wide grant in development builds: the free profile grants `TEAMID.*`, and no setting narrows it. Release builds, signed with Wraith Box's Developer ID, don't share it with anyone.

## Evidence

- <Badge text="verified" variant="success" /> Helpers signed by the team share a generic password, a wrapped Secure Enclave key and a permanent one in the group, after a rebuild too, with no dialog. Source: X29-dev-signing, "Keychain" and "After a rebuild".
- <Badge text="verified" variant="success" /> A plain executable in `Contents/MacOS` is killed with -413 "No matching profile found". A bundle of its own under `Contents/Helpers` runs. Source: X29-dev-signing, "Where a helper can be".
- <Badge text="verified" variant="success" /> Ad-hoc callers get -34018 or see nothing, one that claims the group is killed, and a helper of the same team with another group gets -34018. Source: X29-dev-signing, "Other callers".
- <Badge text="verified" variant="success" /> A LaunchAgent and a symbolic link on `PATH` both start a helper that reaches the group. Source: X29-dev-signing, "How a helper is started".
- <Badge text="verified" variant="success" /> The first build had to be in the Xcode app, because `xcodebuild` couldn't register the Mac. Source: X29-dev-signing, "Getting a certificate and a profile".
- <Badge text="assumed" variant="caution" /> That an Apple ID that never had a membership gets the same profile, valid for a year. The team used belongs to a lapsed membership, which Xcode listed as a free personal team. The first contributor without a membership confirms it.
- <Badge text="assumed" variant="caution" /> That another team's helper can't reach the group. No second team was available. A profile grants only groups under its own team's prefix.
- <Badge text="assumed" variant="caution" /> That an expired profile makes the helpers fail at launch, as a missing one does. The store then fails closed.

## What this unblocks

- I61: the `wb-proxyd` sandbox rules for the data protection keychain, in X23-sandboxed-daemons.
- I49: install and upgrades, which sign the local bundle.
- I252: the spec change in S10-tech-stack (helper bundles), S15-least-privilege, S09-policy-credentials-audit and S12-platforms (developer setup).

<details>
<summary>Details and glossary</summary>

**Why each helper needs its own bundle.** The entitlement for an access group is restricted: macOS lets a program use it only if a provisioning profile allows it. macOS looks for the profile in the bundle whose main executable is starting. A plain executable next to the app's own isn't the main executable of any bundle, so it has no profile and is killed at launch.

**What a developer does once.** Sign in to Xcode with an Apple ID, and build a small project once in the Xcode app with "My Mac" as the destination. Xcode makes the certificate, registers the Mac and downloads the profile. After that, `mise run build` can sign from the command line.

**Glossary**

- **Team:** the signing identity behind an Apple ID. Xcode gives an Apple ID a free personal team. A paid membership is a team too.
- **Provisioning profile:** a file Apple signs that lists the entitlements a team may give its programs on the listed Macs.
- **Access group:** an entitlement that lets programs of one team share Keychain items.
- **AMFI:** the part of macOS that checks a program's signature and entitlements at launch.
- **Ad-hoc signed:** signed without a certificate. The signature only records the binary's hash.

</details>

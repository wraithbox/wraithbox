**Decided 2026-10-04: A. The work VM stays, the isolated slot is lent out.** The decision and its reasons are in the I43 comment that starts `Decision (2026-10-04):`. Source: I43. Affects S06-vm-lifecycle, NFR05-two-macos-vms, NFR06-explained-refusals and SEC08-proj-isolation. Related: I50 (the same limit on development Macs).

<Aside type="tip" title="You are deciding">
Which uses of a running macOS VM `wb-hostd` admits, in what order, and what it suspends or refuses when both slots are taken. Recommended: **A**, the work VM is never touched, and image builds and update checks borrow the isolated slot only while no session runs there. That adds an admission section to S06-vm-lifecycle. Placement of Xcode work that needs a GUI login waits for X06-guest-xcode (I20).
</Aside>

## Options

The issue gives a proposal. The other options are the brief's.

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. The work VM stays, the isolated slot is lent out

An image build or update check takes the isolated slot. If no session runs in the isolated VM, `wb-hostd` saves its state and stops it, then restores it afterward. If a session runs there, `wb` refuses, names the session, and says how to end it. When another program holds a slot, the start fails and `wb` says that a macOS VM outside Wraith Box is running.

- **Cost:** an admission section in S06-vm-lifecycle and a small queue in `wb-hostd`. Untrusted sessions wait during a build.
- **Keeps:** <Badge text="NFR05-two-macos-vms" variant="success" /> <Badge text="NFR06-explained-refusals" variant="success" /> <Badge text="SEC08-proj-isolation" variant="success" />

</div>
<div class="wb-option">

### B. Refuse when both slots are taken

A build or update check runs only when a slot is free. Otherwise `wb` refuses and tells the user to run `wb vm stop`.

- **Cost:** less code. The user stops VMs by hand before each build.
- **Keeps:** <Badge text="NFR05-two-macos-vms" variant="success" /> <Badge text="NFR06-explained-refusals" variant="success" />

</div>
<div class="wb-option">

### C. Take whichever slot is idle

A build takes whichever slot has no running session, the work VM's included.

- **Cost:** builds start more often without waiting. Trusted sessions, the common case, wait for a build to finish.
- **Keeps:** <Badge text="NFR05-two-macos-vms" variant="success" />

</div>
<div class="wb-option">

### D. Leave the spec as is

S06-vm-lifecycle says `wb-hostd` "performs admission control and reports a clear error", with no order.

- **Cost:** none now. Each builder decides the order, and the image build work in V1-M2-walking-skeleton has no rule to follow.
- **Weakens:** <Badge text="NFR06-explained-refusals" variant="caution" />

</div>
</div>

<Aside type="note" title="Missing from the issue">
**GUI work next to untrusted repositories is already in the spec.** S06-vm-lifecycle ("VMs") puts "work that needs a GUI login session" in the isolated VM today. For a trusted project that puts its code in the same VM as untrusted repositories, where guest root can read other projects' clones (T05-cross-proj-clones). The isolated VM exists to avoid exactly that. Until X06-guest-xcode answers, that sentence should read as open, not decided. If a GUI login is needed, the choices are: the isolated VM's console user (accepting T05-cross-proj-clones for those projects), a console login for one project user at a time in the work VM, or giving a GUI project the isolated slot alone while untrusted sessions wait.

**`wb-hostd` can't count other programs' VMs.** It learns about them when a start fails with the framework's limit error. Admission for those is "try, then explain", not a check ahead of time.

**Spike code skips admission.** Agents' spike VMs (X02-warm-start, X17-image-build and others) drive the Virtualization framework directly, before `wb-hostd` exists. I50 covers them with a lock on each development Mac. Both rules should name the same limit and the same error. A refusal then reads the same on a development Mac and in `wb`.
</Aside>

## Evidence

- <Badge text="verified" variant="success" /> The Virtualization framework has an error for "an attempt to start a virtual machine (VM) exceeded the limit of the number of running VMs the framework allows", `VZErrorVirtualMachineLimitExceeded` (`VZError.h`, macOS 27 SDK).
- <Badge text="verified" variant="success" /> S06-vm-lifecycle ("VMs") gives the two slots to the work VM and the isolated VM, counts VMs "started by other software", and has `wb-hostd` perform admission control. S04-architecture lists admission control under `wb-hostd`.
- <Badge text="verified" variant="success" /> Images are built locally on each host (V1-07-local-images). Every image build therefore takes a slot on the user's own Mac.
- <Badge text="verified" variant="success" /> Image updates swap the system disk for a fresh clone (S06-vm-lifecycle, "Images"). A test boot before the swap is the issue's idea, and S06-vm-lifecycle doesn't have it yet.
- <Badge text="verified" variant="success" /> Whether a saved state can be restored reliably, and reused, is X02-warm-start (I16).
- <Badge text="assumed" variant="caution" /> That a VM whose state is saved and which is stopped no longer counts against the limit. Option A depends on it. X02-warm-start can confirm it in passing.
- <Badge text="assumed" variant="caution" /> That no public API lists macOS VMs other programs run. If one exists, `wb` can name them in the refusal.
- <Badge text="assumed" variant="caution" /> Whether Xcode builds and simulators need a GUI login. That is X06-guest-xcode (I20).

## What this unblocks

- The admission section in S06-vm-lifecycle, now, for builds, update checks, and other software.
- GUI placement, after X06-guest-xcode (I20). I43 is blocked by it.
- `wb image build` in V1-M2-walking-skeleton, which needs a slot rule.
- I50, which applies the same limit to agents on development Macs.

<details>
<summary>Details and glossary</summary>

**Why the work VM keeps its slot.** Every trusted project shares the work VM (S06-vm-lifecycle), so stopping it interrupts the most sessions. The isolated VM is used less, and an untrusted session waiting for a build is the smaller cost.

**Why the order matters for builds.** An image build installs macOS from a restore image and can take long (X17-image-build measures it). Under A the isolated VM is stopped for that whole time, so `wb` should say how long, once X17-image-build has a number.

**Glossary**

- **Slot:** one of the two macOS VMs a Mac may run at once.
- **Work VM:** the VM for every trusted project, one guest user per project.
- **Isolated VM:** the VM for untrusted repositories and for projects assigned to it.
- **Admission control:** the rule in `wb-hostd` that decides whether a VM may start, and what to stop or refuse.
- **Saved state:** a VM's memory and devices written to a file so it can stop and later resume from that point.
- **GUI login:** a user logged in at the guest's graphical console, which some Xcode features may need.

</details>

# S12-05 - WSL

**Purpose:** How `wb` works inside a WSL 2 distribution on a Windows host
(FR16-wsl).

## Design

On a Windows host, `wb` inside a WSL 2 distribution is a **client** of
the Windows host's `wb-hostd`.

### Detection

Linux `wb` checks for WSL (`internal/platform`). In WSL it never starts
services or VMs inside the distribution.

### Channel

1. `wb` starts the Windows `wb.exe relay` through WSL interop.
2. `wb` speaks gRPC over the relay's standard input and output.
3. `wb.exe` connects to `wb-hostd` over its named pipe, as the Windows
   user.

Authentication is then the same as in native use. This doesn't need
networking configuration in WSL. A Hyper-V socket channel is a possible
later optimization (spike X12-wsl-channel).

### Terminal

The WSL-side `wb` owns the terminal. It relays the terminal inside the
gRPC stream, so Windows console behavior doesn't apply.

### Repository

The repository stays in the WSL filesystem, and `wb-hostd` never reads
it (S08-10-wsl).

- `wb.exe` fetches the selected refs into the Windows-side `export.git`,
  as its only writer. It fetches from a `git upload-pack` that it starts
  in the distribution through `wsl.exe`. So `wb-hostd` is never the
  fetch client.
- `wb land` and `wb diff` fetch in the distribution from a
  `git upload-pack` on the Windows-side landing repository. `wb.exe`
  runs that `upload-pack` after it checks the repository.

### Project identity

A project's identity includes the distribution name (S05-cli). The same
path in two distributions is then two projects.

### Requirement

The Windows side must have Wraith Box installed and `wb setup` done. The
WSL-side `wb` explains this if `wb.exe` is missing.

## Decisions

### No services or VMs inside WSL

- **Why:** the WSL distribution shares one kernel with every other
  distribution of the user, so it isn't a sandbox
  (SEC01-separate-kernel).

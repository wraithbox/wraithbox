# S08-10 - WSL

**Purpose:** How the fetches of the git round trip cross between a WSL
distribution and the Windows side.

## Design

When `wb` runs inside WSL (S12-platforms), the repository is in the WSL
distribution. `export.git` and `landing.git` are on the Windows side.
Both fetches cross between the two with `git fetch
--upload-pack=<command>`:

| Fetch | Runs on | Its `upload-pack` runs on |
|---|---|---|
| Export update | the Windows side, `wb.exe relay` | the WSL side, `wb upload-pack-relay` |
| Land and diff | the WSL side, `wb` | the Windows side, `wb.exe landing-upload-pack` |

Everything else in S08-workspace-and-git is the same under WSL.

### The command is shell text

Git runs the `--upload-pack` value as a POSIX shell command line, with
`sh -c`. On the Windows side that is the `sh` of Git for Windows. Git
appends the fetch's path as the last word.

The side that composes the value:

1. checks each project ID and session ID in it against its format;
2. single-quotes every word the way git's `sq_quote_buf` does. The
   word goes in single quotes, with each `'` in it written as `'\''`
   and each `!` as `'\!'`.

The quoting covers the program's path, the distribution and user
names, the repository's path and the IDs. No word can expand or split.

- The path of `wsl.exe` is written with forward slashes, which `sh`
  doesn't read as escapes.
- The first word is an absolute path. Git then doesn't look up a remote
  helper, and the shell doesn't search `PATH` for the program.

The Git for Windows `sh` converts arguments that look like POSIX paths
into Windows paths when it starts a program that isn't an MSYS program,
such as `wsl.exe`. `/usr/local/bin/wb` or `/home/<user>/repo` would then
reach the distribution as Windows paths. `MSYS_NO_PATHCONV=1` turns that
conversion off. The Windows-side fetch runs with it in its environment.

### The placeholder path

The fetch's path is a placeholder that the program ignores. But git
reads an existing bundle file at that path as a bundle, and then
ignores `--upload-pack` (reproduced with git 2.56.0 for I67). So the
composing side:

1. creates a new empty directory, readable only by the user, in its
   temporary directory;
2. uses `wb-relay` in it as the placeholder;
3. checks with `lstat`, right before the fetch, that the placeholder
   doesn't exist.

The check guards against a file that is already there. Between the
check and git's own `stat`, only a process of the user can create one,
because only the user can write the directory.

T00-index trusts the user's processes. On Windows they include
`wb-hostd`, until I190 gives it a profile there. What it could gain
depends on the side:

- The WSL-side placeholder belongs to the land and diff fetches. A
  bundle there puts objects and refs of its choosing in a landed branch
  or the `wb diff` scratch repository. T16-hostd-landing already covers
  that.
- The Windows-side placeholder belongs to the export update. A bundle
  there puts objects and refs of its choosing in `export.git`, which
  T16-hostd-landing doesn't cover. On Windows that adds nothing until
  I190, because without a profile `wb-hostd` can already write
  `export.git` there.

### Fetch settings

Each fetch runs with the settings of S08-06-landing-on-the-host,
"Fetch settings": `GIT_PROTOCOL_FROM_USER=0`, `protocol.allow=never`,
`protocol.file.allow=always` and `--no-recurse-submodules`.

### Export update

The WSL-side `wb` starts `wb.exe relay` on the Windows side
(S12-platforms, "WSL"). The relay runs as the Windows user, outside any
sandbox. It is the `wb` of S08-02-export-repository and
S08-07-repository-lifecycle for `export.git`, with the Windows host git
(S08-08-host-git).

1. It takes the export lock over `wb-hostd`'s named pipe.
2. Under the lock it checks the layout and `config` of `export.git`.
3. It fetches, deletes refs, and runs the shrink steps and the prune.

Its `--upload-pack` command is `wsl.exe` from the Windows system
directory, with:

- the distribution and the Linux user of the WSL-side `wb`;
- `--exec` and the WSL-side `wb`'s absolute path;
- the subcommand `upload-pack-relay`;
- the repository's path.

The WSL-side `wb` sends those values. `wb.exe` takes none of them from
`wb-hostd`.

In the distribution, `wb upload-pack-relay` checks that the path is the
git common directory that the rules of S05-cli ("Naming") give for that
path. Then it runs `git upload-pack` on it, with `GIT_NO_LAZY_FETCH=1`
and its own git, which it resolves and checks by S08-08-host-git. WSL
interop carries the standard input and output.

### Land and diff

The WSL-side `wb` runs the fetch of S08-06-landing-on-the-host in the
distribution. It fetches into the user's repository, or the scratch
repository of `wb diff`.

Its `--upload-pack` command is `wb.exe`, at the path the WSL-side `wb`
uses to start the relay, with the subcommand `landing-upload-pack`, the
project ID, and the session ID. `wb.exe` then:

1. checks both IDs against their formats again;
2. derives the landing repository's path itself;
3. runs the checks of S08-06-landing-on-the-host on it;
4. runs `git upload-pack` on it with the Windows git.

## Decisions

### `wb-hostd` stays out of both streams

- **Why:** `wb-hostd` then never becomes the fetch client of an
  `upload-pack` on the user's repository. Over protocol v2 that client
  could ask for any object of the repository by its ID
  (X07-git-round-trip).

### One writer for `export.git`, on the Windows side

The WSL-side `wb` doesn't write `export.git` over the cross-OS file
share. `export.git` has one writer, on the Windows side, with the
Windows git.

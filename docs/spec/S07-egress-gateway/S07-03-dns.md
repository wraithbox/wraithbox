# S07-03 - DNS

**Purpose:** How `wb-netd` answers the guest's DNS queries: synthetic
addresses, the name form, negative answers and the wildcard budget.

## Design

`wb-netd` answers DNS, on UDP and TCP port 53 on the gateway only.
How it refuses a name, and the hold before each refusal, are on
S07-12-dns-refusals.

### Synthetic addresses

`A` queries for allowlisted names are answered with a **synthetic
address** from a reserved range, 198.18.0.0/15. The address is
allocated per name, and remembered with a TTL.

Real upstream addresses are never revealed to the guest. Before each
such answer leaves, `wb-netd` reports the name and address to
`wb-proxyd` (S07-04-stream-hand-off).

### Synthetic pool

Each VM has the 131,072 addresses of 198.18.0.0/15. An address is
never given to another name:

- while a connection to it is open;
- before its TTL plus a guard interval has passed since its last
  answer.

When no address is free, a new name gets `SERVFAIL`, logged with the
rule `synthetic-pool-full`.

Inspected plain HTTP requires the `Host` header to equal the name
mapped to the synthetic address.

### Other record types

For allowlisted names:

- `AAAA`, `HTTPS` and `SVCB` queries get an empty answer;
- other record types are refused.

The macOS resolver asks for `HTTPS` before most `A` queries. The
spike refused `HTTPS`. The empty answer is a choice nobody measured
(B17-network-path).

The empty answer gives no `HTTPS` record that could hold an encrypted
ClientHello configuration, or an HTTP/3 hint that `wb-proxyd` can't
honor. Giving no `HTTPS` or `SVCB` record is a deliberate
compatibility measure: clients that look up ECH keys in DNS don't try
ECH. It isn't a control against a guest that brings its own ECH keys
(S07-17-tls-and-tunnels, "Encrypted ClientHello").

### Local answers

`wb-netd` answers these names itself:

- every name under `.arpa`: reverse lookups, `_dns.resolver.arpa`,
  `ipv4only.arpa`, `home.arpa`;
- every name under `.local`.

The answer is `NXDOMAIN` or an empty answer, with no approval event.
It is logged.

An idle macOS guest asks for its own reverse name and for
`_dns.resolver.arpa` after each lease (X03-network-path).

### Name form

The form is checked on the labels as they are on the wire:

- Each label is 1 to 63 bytes of ASCII letters, digits and hyphens
  only. So no label holds a dot byte or any other byte.
- The name is at most 253 bytes, written with dots between its
  labels.
- Letters compare case-insensitively.

Outside the local answers above, a query whose name breaks the form
gets `NXDOMAIN` with the rule `dns-name-form`. That check comes before
any other.

Such a name raises no approval event, and stays off every learn list.
So no control byte or non-ASCII character from a name reaches a
notification, `wb status` or `wb learn report`.

The policy loader and `wb allow` refuse a host that fails this rule.
For a wildcard host they check the part after its leading `*.`. The
refusal has the same rule name, and an error that names the host and
the character or length at fault (NFR06-explained-refusals). So an
allowed host never loads and then fails to resolve.

### IP literals

A name whose last label is all digits, or is a hexadecimal number
starting with `0x`, is an IPv4 address in a form some resolvers
accept. It fails the name form rule as above:

- a query gets `NXDOMAIN` with the rule `dns-name-form`;
- the policy loader and `wb allow` refuse it as a host.

An IPv6 literal has colons, and already fails the LDH rule. So no
policy host names an address (SEC05-default-deny).

### Negative answers

Every `NXDOMAIN` that `wb-netd` sends, the local answers included,
carries an SOA record for the root zone in its authority section. The
record has a TTL of 0 and a `MINIMUM` of 0, and is the same every
time.

A resolver caches a negative answer for the smaller of the two (RFC
2308). So the guest doesn't cache a refusal, and a lookup after a
later approval reaches `wb-netd` and succeeds.

- *Allowed names.* An empty answer for an allowed name (`AAAA`,
  `HTTPS`, `SVCB`) has the same SOA record, with the TTL and `MINIMUM`
  of that name's `A` answer. So the guest doesn't ask for those types
  more often than for `A`. An empty local answer has the zero SOA
  record.
- *Program caches.* The SOA record doesn't reach a negative cache
  inside a program, such as Java's (10 seconds by default). Such a
  program's lookups of a name fail until its cache expires.

### Wildcard budget

Wildcard allowlist entries are bounded. Each VM may resolve at most a
fixed number of new names under wildcards in an active period
(S07-01-per-vm-policy).

- Failed lookups count against that budget, because names themselves
  can carry data (T02-dns-names).
- Parallel sessions in the VM share the budget.
- A name past the budget is refused with the rule `wildcard-budget`.

The name length is limited ("Name form"). A query over the VM's query
rate limit is refused with the rule `dns-query-rate`.

## Decisions

### Zero-TTL negative answers

Every `NXDOMAIN` carries the root SOA record with TTL and `MINIMUM` 0.

- **Why:** the guest doesn't cache a refusal, so a lookup after a
  later approval succeeds.
- **Decided:** I51 (B51-approval-flow).

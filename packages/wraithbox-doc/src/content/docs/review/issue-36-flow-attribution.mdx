Whether the host keeps network grants and credentials apart for trusted projects in the shared work VM. Recommended: **A**, enforce per VM and write the gap down as a risk. That rewrites S6-repo-writes and S8-proj-isolation, so it is a spec change. It unblocks issue #51.

## Options

<div class="wb-options">
<div class="wb-option" data-recommended>

### A. The VM is the enforced unit

The host enforces the union of every work-VM project's grants and credentials. Per-project and per-session rules narrow that union using a label the guest reports, recorded as untrusted. A new residual risk in spec 003-requirements says so.

- **Cost:** spec wording only, in specs 003-requirements, 007-egress-gateway and 009-policy-credentials-audit. Per-project credentials look stronger than they are, so `wb policy explain` must say who can reach each one.
- **Weakens:** <Badge text="S6-repo-writes per VM" variant="danger" /> <Badge text="S8-proj-isolation network" variant="danger" />
- **Keeps:** <Badge text="S4-no-guest-secrets" variant="success" /> <Badge text="S5-default-deny" variant="success" /> <Badge text="S11-root-gains-nothing" variant="success" />

</div>
<div class="wb-option">

### B. Project secrets only in a VM of their own

The work VM gets only credentials and write grants that every project in it shares. A project with its own token runs alone in the second VM slot.

- **Cost:** macOS runs at most two macOS VMs (N5-two-macos-vms). The second slot also hosts untrusted repositories, so only one such project runs at a time, and untrusted work waits meanwhile.
- **Keeps:** <Badge text="S6-repo-writes" variant="success" /> <Badge text="S8-proj-isolation" variant="success" />

</div>
<div class="wb-option">

### C. Host-verifiable attribution

Give each project user its own virtual network card, and route by user inside the guest.

- **Cost:** guest root controls the routing, so under the threat model this is the same as A. It does stop a non-root agent.
- **Not viable alone:** <Badge text="S6-repo-writes per VM under root" variant="caution" />

</div>
</div>

<Aside type="note" title="Missing from the issue">
Option A narrows per project only once a label exists, and today the only planned label source is the Network Extension of spike X14-flow-attribution. That needs an Apple Developer ID entitlement and is unproven. The macOS packet filter (`pf`) in the guest can match connections by the user that owns the socket. In principle it could give each project user its own source address, which `wb-netd` would then see. That would be a second label source for A, with no Apple entitlement. Guest root can change `pf` rules, so it stops a non-root agent only, like the X14-flow-attribution label. It is untested and would need a spike.
</Aside>

## Evidence

- <Badge text="verified" variant="success" /> `wb-netd` leases one IPv4 address per VM and accepts only that VM's MAC address (spec 007-egress-gateway, "Addressing").
- <Badge text="verified" variant="success" /> Spec 007-egress-gateway still says each stream is "tagged with VM, project, session, hostname, and port" ("Connections"), with no source for the project and session.
- <Badge text="verified" variant="success" /> All trusted projects share the work VM, each as its own guest user (spec 006-vm-lifecycle, "VMs" and "Projects and sessions").
- <Badge text="inferred" variant="note" /> So before any label exists, project B's agent can use project A's credential binding without guest root. Specs 007-egress-gateway and 009-policy-credentials-audit don't say how the host would tell the two users' connections apart.
- <Badge text="verified" variant="success" /> Work returned through git is not affected: pushes to the landing repository go over the host-guest socket, not the network (spec 008-workspace-and-git, "Out of the guest").
- <Badge text="verified" variant="success" /> Guest labels can only narrow host rules, and guest root can forge them (spec 013-guest-confinement, "Principle", and risk R6-forged-labels). Program narrowing is off until X14-flow-attribution (spec 009-policy-credentials-audit, "Program narrowing").
- <Badge text="verified" variant="success" /> A project can already be assigned to the isolated VM slot in its settings (spec 009-policy-credentials-audit, "Settings contents"), which is what option B builds on.
- <Badge text="verified" variant="success" /> The macOS packet filter documents a `user` rule option that matches "packets of sockets owned by the specified user" (`man pf.conf` on macOS 27.0.1).
- <Badge text="assumed" variant="caution" /> That `pf` per-user rules can give each project user a distinct source address inside a macOS guest. Testing it needs a VM, so it would be a spike.
- <Badge text="assumed" variant="caution" /> That the X14-flow-attribution Network Extension can be approved in the image without MDM and sees every relevant flow. That is spike X14-flow-attribution (issue #10).

## What this unblocks

- Issue #51, the approval flow, which is blocked by this issue.
- The spec pull request that rewrites spec 003-requirements (a new residual risk), spec 007-egress-gateway ("Connections") and spec 009-policy-credentials-audit (effective policy per VM).
- The priority of X14-flow-attribution (issue #10): under option A it decides whether v1 has any per-project narrowing at all.

<details>
<summary>Details and glossary</summary>

**Why the issue rules out option C.** Spec 003-requirements assumes the agent may hold root in the guest. Anything inside the guest that decides which network card or address a connection uses, root can change. So routing by user protects against an agent without root, and against nothing more. That is the same protection a guest label gives in option A.

**A related question.** The git transport over the host-guest socket has the same problem: `wb-hostd` learns which project a push is for from `wb-guestd`, which runs in the guest. Risk R5-cross-proj-clones covers that today ("changes still return only as reviewable branches").

**Glossary**

- **Work VM / isolated VM:** the two VM slots per guest OS. Trusted projects share the work VM. Untrusted repositories, and projects assigned to it, use the isolated VM.
- **Project user:** the guest account each project runs as. It keeps projects' files apart, but not their network traffic.
- **Credential binding:** a host-side rule that swaps a placeholder in a request for a real token, for named hosts and paths. The token never enters the guest.
- **Label:** information the guest attaches to a connection, such as the program or project that opened it. The host can use it to deny more, never to allow more.
- **Guest root:** full control of the guest operating system. The threat model assumes an attacker can get it.
- **Residual risk (`R*`):** a known gap that spec 003-requirements documents rather than closes.
- **Network Extension:** a macOS mechanism that lets a guest-side program see every connection and the process behind it. Spike X14-flow-attribution tests it.
- **`pf`:** the packet filter built into macOS, configured by root.

</details>

# F: ways V1 could be secure and to spec but annoying or useless

Ranked by likelihood times impact for the first user, the maintainer, on
day one. L = likelihood, I = impact (H/M/L). "Covered by" is the spec or
issue that addresses the risk. "Nothing" means no spec, test or issue measures it.

| Rank | Risk | L | I | Evidence | Covered by |
|---|---|---|---|---|---|
| 1 | **The work loop differs from host Claude Code.** The host editor or IDE can't see files while the session runs. No `/ide`, no port forwarding (a dev server can't be opened in the host browser), no clipboard (`/copy` lost, OSC 52 dropped), links dropped from screen, notifications become a bell. No MCP servers (`.claude.json` never crosses), no plugins, hooks, status line or output styles. Work is seen only after `wb diff` and `wb land`. Closing the terminal ends the session (no detach). Each session gets a fresh worktree, so ignored local files (`.env.local`, build caches, `node_modules`) aren't there | H | H | V1-08-no-forward-clipboard, S05-00 "Controls" (FR01 holds "except `/copy`, notification text, links and the window title"), S14-00 "Out of scope", S14-04 "`/ide`", S06-08 "Worktree per session", FR04 carries only untracked-not-ignored files | Decided deliberately (I38, I45, I46). **Nothing** measures whether the loop is acceptable for daily work |
| 2 | **The forge workflow is cut.** The guest has no forge credential. GraphQL mutations are refused while the allowlist is empty, so `gh pr create` and `gh issue comment` fail in the guest. Work returns as a branch the user lands, merges and pushes by hand. The maintainer's own process (agents that open PRs, comment on issues, run waves) can't run inside `wb claude` in V1 | H (for this maintainer) | H | #502 "Done when": `gh pr create` is a mutation, refused. S07-11 "git hosting". FR03 | By design (SEC06). General bindings (M5.9) could add a GitHub token binding, but the GraphQL lock stays (S09-02). **Nothing** says how the maintainer is meant to work this way |
| 3 | **Approval prompts during normal work.** Every name outside git hosting, the model API and the package registries is held 4 s at DNS, then refused unless approved in that window. So the first attempt usually fails and the agent has to retry. Docs sites, GitHub release assets (used by `mise install`, many installers), CDNs, `raw.githubusercontent.com`, and Claude Code's WebFetch (the model API profile has no entry for it, and the spec never mentions WebFetch) all hit it. Write methods need a separate approval. Notifications need a native helper that isn't designed yet (M5.4) | H | M-H | S09-10 "4 seconds", S07-11 built-in profiles, S07-17. Rate and pending caps exist (S09-10 "Limits") to bound fatigue, not to reduce it | FR09, FR10 learn mode (refused while another project has a session in the VM). **Nothing** counts prompts per day or tests WebFetch |
| 4 | **Start time and per-session setup.** No warm start until M6.4. Cold start through `wb vm start` measured 14.1 s and 19.4 s to the guest daemon, against a 10 s goal. A first project session adds export and clone (33 s for 426 MiB), reconcile and carry-in. Each new session has a fresh worktree, so `npm ci` or a build runs again at 71% of host speed. Every `wb vm stop` waits 30 s (#414) | H | M | C11 runs (#288), X07, X05, #414. NFR01 and NFR02 are goals outside the gate (I111, I19) | M6.4, M6.7 benchmarks. #86 and #97 post-V1 |
| 5 | **The dependency gate breaks lockfile installs.** A lockfile that pins a version younger than 7 days is refused at download (2 of 10 projects in X21), and so is one with a CRITICAL CVE (2 of 10). The Wraith Box repository itself sets a 7-day Dependabot `cooldown` for every ecosystem (`.github/dependabot.yml`), so its own lockfiles would mostly pass. A repository that doesn't, or a version added by hand, would be refused. Go modules from git hosts and Homebrew bottles aren't gated, so protection is uneven | M-H | M | X21 tables. | 6 | **Tools missing in the guest.** The agent can't `brew install` (the prefix belongs to `_wbtool`). A new system disk (each Claude Code update) drops project formulae, so the next session reinstalls them. `pip` needs `--break-system-packages` or a venv | M-H | M | X20, S06-01 "The manifest is data", "A new system disk" | FR07, M5.11, #180 |
| 7 | **Xcode and Swift.** No macOS `xcodebuild test` (SwiftPM through `xcodebuild` included), no launching macOS apps. ## What makes "done to spec but useless" plausible here

- **No exit criterion measures use.** Every V1 milestone exit cites requirement
  IDs (V1-initial "Milestones"). None asks for a day of real work, a timed
  first run, or a count of prompts. M6.7 benchmarks don't gate.
- **The friction is mostly by design.** Risks 1, 2, 3, 5, 7 and 9 come from
  decided controls (SEC02, SEC05, SEC06, SEC07, V1-08). They can't be fixed
  late without a spec change, so finding them only at the release gate is costly.
- **The integration is late.** `wb claude` has no code yet. The first prompt
  (M4.10 and the launch part of M4.12) comes after M3, M7 and the first M4
  packages, so the first chance to feel the loop is near the end of V1.
  The implementation plan does put the first prompt on the fixture bundle
  before the git work, which helps.
